# 代储代销批量销售设计方案（形态二专项）

> 版本：V1.2（待评审稿）
> 日期：2026-09-14
> 本期形态：多条代储订单 → 同一采购商
> 涉及端：金融助手后台、市场助手（一期渠道）
> 基准原型：`金融助手-代储代销-整合版-2.8.html`
> 状态：方案已落地到原型（见第 11 节改造点清单）

## 1. 方案背景

代储代销的销售环节由平台代供应商完成。当前实现为**定向销售**：运营在代储订单列表点击「销售」，弹出表单，选择单个客户、填写单价与数量，提交后生成一张销售订单。

实际业务中有一个高频场景：**同一个采购商一次要多个 SKU**。例如采购商同时要 iPhone 15 Pro、华为 Mate 60、iPad Air，这三批货分别来自三条代储订单。按现有实现，运营需要重复打开三次弹窗、三次选择同一个采购商与同一个收件地址，生成三张互不关联的销售订单。

| 问题 | 表现 |
|---|---|
| 重复录入 | 同一采购商、同一地址要填三遍 |
| 无法整批追溯 | 三张单散落在销售订单列表中，看不出是同一次交易 |
| 金额无法整批核对 | 划扣保证金、仓储费、服务费分散在三条记录里，无法一次看到本次交易总额 |
| 缺少影响面提示 | 提交前看不到此次下单会占用多少库存、产生多少划扣 |

本方案将这一动作升级为**销售批次**：一次提交生成 N 张销售订单，N 张单共享同一批次号。

## 2. 建设目标

1. 支持在代储订单列表勾选多条订单，一次性向同一采购商提交下单。
2. 一个批次生成 N 张销售订单，共享批次号，可在销售订单管理中按批次回看与对账。
3. 批次内实时展示每条订单的可售库存、最低销售单价与金额汇总，提交前完成逐行校验。
4. 批量生成的销售订单各自独立走原有流程（支付、出库指令、清结算），批次号仅用于追溯，不改变单据粒度。

## 3. 范围与入口

### 3.1 本期范围

- 代储订单管理列表新增勾选列、可售库存列与工具栏批量入口。
- 新增批次销售弹窗：抬头统一采购商信息，明细区逐条代储订单填写单价与数量。
- 销售订单管理新增销售批次号筛选、列展示与同批次分组。
- 提交接口由单张扩展为批量，同步市场助手。
- 补充规则说明文案。

### 3.2 暂不纳入本期

- **形态一（一条代储订单 → 多个采购商）**：作为二期扩展，模型已预留（见第 5.4 节）。
- 分销平台、购机通渠道（二期，仍保持禁用）。
- 批次级审批流（本期沿用 `PERM-SALE-001` 销售管理员权限直接提交）。
- 批次内单据的部分撤销与改单（本期仅支持整批作废，且仅限全部未支付时）。

## 5. 批次模型

### 5.1 结构

```
销售批次（抬头，1 个）
├─ 销售批次号、销售渠道、提货方式、采购商、收件地址、提交人、提交时间
└─ 分配明细（N 条，每条对应一条勾选的代储订单）
   └─ 代储订单编号 · 供应商 · 货物信息 · 所在仓库 · 业务归属人
      · 评估单价 · 保证金比例 · 服务费率 · 仓储费单价 · 可售库存
      · 销售单价 · 销售数量 · 本次划扣保证金 · 本次仓储费 · 本次服务费
```

抬头只承载**全批真正共用**的采购商侧信息，明细行承载**随代储订单变化**的全部字段。

### 5.2 关键约束：仓库与业务归属人逐行不同

**同一批次的多条代储订单，仓库与业务归属人可能不同，必须逐行承载，不能提到抬头。**

这两项是代储订单自身的属性，在数据模型上已挂在代储订单表 `fa_storage_order`（及仓单表 `fa_storage_warehouse_receipt`）上：

| 字段 | 所属表 | 说明 |
|---|---|---|
| `warehouse_id` / `warehouse_name` | `fa_storage_order` | 所在仓库，如「上海监管仓」 |
| `business_owner_id` | `fa_storage_order` | 业务归属人，审核环节（审核弹窗）录入 |
| `deposit_rate` | `fa_storage_order` | 保证金比例，逐单不同 |
| `service_rate` | `fa_storage_order` | 服务费率，逐单不同 |
| `storage_fee` | `fa_storage_order` | 仓储费单价，逐单不同 |
| `stock_in_quantity` | `fa_storage_order` | 入库数量 |
| `evaluate_price` | `fa_storage_order` | 评估单价 |

因此弹出窗内这两项**逐行带出、只读展示**，不做全批统一；金额相关的 `deposit_rate` / `service_rate` / `storage_fee` 同样逐行取值计算，不能使用全局常量。

> 这也说明现有定向销售弹窗（行 951）把「仓库选择」做成运营手工下拉是不合适的——仓库应由所选代储订单决定，而非自由选择。相关改造见第 11 节第 10 条。
>
> ⚠️ **该调整会与 PRD 定稿冲突，需同步修订**：`4.prd定稿/specs/代储代销-代储订单与定向销售.md` 的「创建销售订单提交」接口把 `warehouseCode` 定义为**必填入参**（行 105，注释为「仓库选择，下拉选择入库仓库」），`businessOwnerId` 亦为入参（行 104）。按本方案，两者应改为**由代储订单号推导的服务端派生值**，不再作为前端入参。定稿 spec 与 §Constraints（行 123、145、151）中关于「仓库选择为下拉必填」的描述需一并更新。

### 5.3 编号规则

| 单据 | 规则 | 示例 |
|---|---|---|
| 销售批次号 | XSP + YYYYMMDD + 3 位流水号 | XSP20260914001 |
| 销售订单号 | XS + YYYYMMDD + 4 位流水号（沿用现有） | XS20260914001 |

### 5.4 收敛为形态二后自然消解的两个冲突

V1.0 中「未付款阻塞」与「划扣归属」是必须决策的难题，其根源是**同一代储订单在一个批次内出现多次**。形态二下每条代储订单在一批中只出现一次，两处冲突随之消解：

| V1.0 的冲突 | 形态二下的情况 |
|---|---|
| 一次生成 N 张单、生成时全是「待支付」，违反「前单未付款不能再发起销售单」 | 批内每张单对应不同的代储订单，彼此不构成「前单」。规则自然满足，仅需在**勾选阶段**排除已有未付款销售单的代储订单 |
| 「全部销售完」划扣额依赖「已收保证金」，批量下随付款顺序变化 | 该分支只在一行吃满该代储订单全部剩余库存时触发，对应唯一一张销售单，无顺序歧义。仅需明确「已收」口径（见第 10 节决策二） |

### 5.5 二期扩展预留

形态一 = 允许明细行覆写抬头的采购商与收件地址。届时明细行增加两个可编辑字段，抬头保留为默认值，不需要改动批次模型与提交接口。

### 6.2 交互要点

1. **抬头只收采购商侧信息**：销售渠道、提货方式、采购商、收件地址一次填写，避免重复录入。
2. **仓库与归属人逐行带出**：随勾选的代储订单自动带出，只读。仓库不同的行在视觉上分组提示，便于运营预判会拆成几个发货动作。
3. **逐行算价与预填**：每条代储订单的评估单价、保证金比例、服务费率、仓储费单价、保证金拨付日期均不同，最低销售单价逐行计算后**直接预填进销售单价输入框**。
4. **逐行校验**：销售单价低于该行最低销售单价时行内标红并提示最低价；销售数量超过该行可售库存时标红。
5. **实时汇总（本期暂不展示）**：销售总额、划扣保证金、仓储费、服务费、剩余金额的计算逻辑已实现并随输入实时更新，但汇总区当前在弹窗中隐藏，不对外展示（见第 14 节）。
6. **剩余提示**：明细行展示「可售库存」，提交后该代储订单若有剩余，状态转「销售中」而非「已完结」。
7. **跨供应商 / 跨仓提示**：若本批涉及多个供应商或多个仓库，在明细表下方提示（如「跨供应商 / 跨仓提示：本批代储订单涉及 3 个供应商、3 个仓库。将按仓库拆分生成 3 个出库指令，由各仓库分别发货至同一收件地址，采购商将收到多个包裹。」）。抬头按不一致的维度切换：仅跨仓为「跨仓提示」、仅跨供应商为「跨供应商提示」、两者都有为「跨供应商 / 跨仓提示」。档口自提时文案改为生成提货码、需分别到各仓库提货（详见第 10 节决策一）。
8. **下单前二次确认**：点击「确认下单」时，若本批供应商或仓库不一致，弹出确认框复述同样的拆分说明，运营确认后才生成销售订单；一致时直接下单不打断。
9. **一键复用**：单条勾选时该弹窗等价于现有定向销售，可让「销售」按钮也以同一弹窗打开，逐步替换 `modal-direct-sale`。

| 字段 | 来源 | 校验规则 |

| 代储订单编号 | 勾选带入 | 否 | 拨付状态必须为「已拨付」 |
| 供应商 | 订单带出 | 否 | — |
| 品类 | `fa_storage_order.category` | 否 | — |
| 品牌 | `fa_storage_order.brand` | 否 | — |

| 规格 | `fa_storage_order.common_sku` | 否 | — |

| **业务归属人** | `fa_storage_order.business_owner_id` | 否 | 逐行带出，取审核时录入的值 |
| 评估单价 | `fa_storage_order.evaluate_price` | 否 | 最低销售单价的算价基准 |
| 保证金比例 | `fa_storage_order.deposit_rate` | 否 | 逐行取值，用于最低单价与划扣计算 |
| 服务费率 / 仓储费单价 | `fa_storage_order.service_rate` / `storage_fee` | 否 | 逐行取值，不使用全局常量 |
| 可售库存 | 计算得出 | 否 | 入库数量 − 历史已销售 / 已占用 |

| 销售数量 | 手工输入 | 是 | 必填；正整数；≤ 该行可售库存 |
| 小计 | 计算得出 | 否 | 销售单价 × 销售数量 |

> 形态二下行数固定、每条代储订单只出现一次，因此**不需要跨行合计校验**（V1.0 中为形态一设计）。每条明细行独立校验即可。

### 7.4 提交前校验

1. 至少 1 条明细行（即至少勾选 1 条代储订单）。
2. 抬头四项必填项齐全。
3. 逐行：销售单价 ≥ 最低销售单价，销售数量为 1 ~ 可售库存之间的整数。
4. 提交前二次拉取各代储订单可售库存，防止并发超卖。
5. 提交前复核各代储订单仍无未付款销售单。
6. 供应商或仓库不一致时，二次确认后方可提交（见第 6.2 节第 8 点）。

### 7.5 批次汇总区

> **本期不展示**：下列口径已在原型中实现并随输入实时计算，但汇总区在弹窗中隐藏（见第 14 节）。保留口径定义，供后续恢复展示或评审核对金额使用。

| 汇总项 | 口径 |
|---|---|
| 明细条数 / 分配总数量 | Σ 各行销售数量 |
| 涉及仓库数 | 去重后仓库数量，> 1 时给出拆分提示 |
| 销售总额 | Σ 各行销售单价 × 销售数量 |
| 本次划扣保证金 | 见第 8 节 |
| 本次仓储费 / 本次服务费 | Σ 各行计算结果 |
| 剩余金额 | Σ（实际销售单价 − 单台最低销售单价）× 销售数量 |

## 8. 金额与划扣口径

规则沿用原型说明区（行 536–555）与清结算规则（行 656–665）。批量销售的差别在于**每一项从「单张单据的公式」变为「整批求和」，且所有比例与费率逐行取该代储订单的值**。

### 8.1 最低销售单价（逐行计算）

| 项目 | 公式 |
|---|---|
| 单台服务费 | 评估单价 × 保证金比例 × 服务费率 ×（下单付款日期 − 保证金拨付日期 + 1） |
| 单台仓储费 | 仓储费单价 ×（下单付款日期 − 保证金拨付日期 + 1） |
| **单台最低销售单价** | max（评估单价 × 保证金比例 ×（1 + 服务费率），评估单价 × 保证金比例 + 单台服务费 + 单台仓储费），保留两位小数，向上取 |

其中评估单价、保证金比例、服务费率、仓储费单价均取该行代储订单的值。

### 8.2 本次划扣保证金

| 场景 | 口径 |
|---|---|
| 该代储订单本次**未全部销售完**（本行数量 < 可售库存） | 评估单价 × 保证金比例 × 本行销售数量 |
| 该代储订单本次**全部销售完**（本行数量 = 可售库存且为最后一笔） | 拨付保证金总额 − 已收保证金 |

其余两项按行算出后求和：

- `本次仓储费 = Σ 单台仓储费 × 销售数量`
- `本次服务费 = Σ（单台最低销售价 × 销售数量 − 本次划扣保证金 − 本次仓储费）`

## 9. 状态流转与联动

批量提交后，N 张销售订单各自独立走原有流程，批次号仅用于追溯：

```
勾选代储订单 → 批次销售弹窗填写 → 提交 → 生成 N 张销售订单（待支付）
→ 采购商支付 → 出库指令/提货码 → 清结算分账
```

需同步联动的对象：

| 对象 | 变化 | 是否需改造 |
|---|---|---|
| 销售订单 | 新增 N 条记录，写入批次号 | 新增字段 |
| 代储订单 | 状态由「已拨付」转「销售中」；本行数量吃满可售库存时转「已完结」 | 复用现有枚举 |
| 电子仓单 | 部分分配 → 部分释放；全部分配 → 已核销 | 需先定口径（见决策四） |
| 出库指令 | 按销售订单粒度各自生成；跨仓批次自然拆成多个指令与提货码 | 无需改造 |
| 清结算 | 按销售订单粒度各自生成，逻辑不变 | 无需改造 |
| 市场助手 | 接收批量推送的销售单 | 接口调整 |

## 10. 待决策事项

### 决策一：跨仓批次的出库与提货拆分（需优先拍板）

仓库逐行不同是**既定事实**（见第 5.2 节），因此同一批次跨仓是常态。需要确定跨仓时的履约方式：

| 提货方式 | 跨仓时的表现 |
|---|---|
| 快递物流 | 多个仓库分别发货至同一收件地址，采购商收到多个包裹——可接受 |
| 档口自提 | 需分别到多个仓库提货，生成多个提货码——采购商体验受影响 |

**建议**：允许跨仓。快递物流按仓库拆分发货；档口自提时在弹窗汇总区明确提示「本批涉及 N 个仓库，将生成 N 个提货码」。若业务上不接受自提跨仓，则在勾选阶段按仓库限制同批。

### 决策二：「已收保证金」的口径

「全部销售完」分支依赖 `拨付保证金总额 − 已收保证金`，而该口径在行 549 的括号中被写作「已付款销售单 + 未付款销售单」。需明确本批自身生成的那张未付款单是否计入「已收」——若计入，会出现自身抵扣自身的循环。

**建议**：「已收」仅统计**已支付**的销售单；本批生成的待支付单不计入。

### 决策三：费率取值口径（存量问题）

服务费率与仓储费单价在代储订单表上**已是逐单字段**（`service_rate`、`storage_fee`），但原型文档里出现了多个互相矛盾的口径：

| 项目 | 出处 | 取值 |
|---|---|---|
| 服务费率 | 最低单价公式（行 544） | 0.2% |
| 服务费率 | 清结算规则（行 649） | 1% |
| 服务费率 | 代储订单表实际字段值 | 0.00025 / 0.0003 等 |
| 仓储费单价 | 划扣说明（行 543） | 未给值 |
| 仓储费单价 | 清结算规则（行 662） | 10 元/台/天 |

**建议**：统一以代储订单表字段为准，逐行取值，不在原型或文档中写死常量；同时校准清结算侧（行 649、662）的说明文案。

### 决策四：仓单状态由分配还是出库触发

仓单说明（行 365–366）将「部分释放 / 已核销」解释为**销售出库**的结果；但批量销售提交时仅为「分配」，货物尚未出库。

**建议**：明确区分两级——提交分配时仓单进入「已质押（部分占用）」，实际出库后才转「部分释放 / 已核销」；或按现有口径统一改为出库触发，弹窗内不承诺仓单状态。

## 12. 验收要点

1. 勾选 3 条不同 SKU 的代储订单，向同一采购商提交，生成 3 张销售订单并共享同一批次号。
2. 销售订单列表中同批次 3 张单连续排列并带分组标识，批次号可点击筛选出该批全部单据。
3. 勾选的订单分属不同仓库、不同业务归属人时，弹窗明细行逐行正确带出，抬头不出现这两项。
4. 某行销售数量超过该行可售库存时标红并阻止提交；销售单价低于该行最低销售单价时同样拦截。
5. 待拨付、已完结、或存在未付款销售单的代储订单，在列表中不可勾选。
6. 某行数量等于该行可售库存时，提交后该代储订单状态转「已完结」；小于时转「销售中」。
7. 批次汇总的销售总额、划扣保证金、仓储费、服务费、剩余金额与逐行结果相加一致。
8. 批量生成的 N 张单，后续支付、出库指令、清结算各自独立走通，互不阻塞。

| `batchConflictText(scope)` | 由 `scope` 生成提示与确认框共用的文案；仅列出数量 > 1 的维度，避免出现「1 个仓库」这类噪声 |
| `isSelfPickup()` | 读取提货方式单选值，切换自提 / 快递文案 |
| `submitBatchSale()` | 校验通过后按 `scope` 判定是否 `confirm()`，取消则 `return` 不生成单据 |
