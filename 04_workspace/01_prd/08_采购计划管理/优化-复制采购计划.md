# 优化需求：采购计划「复制」功能

> 关联文件：`采购计划管理.html`（原型）、`采购计划管理-PRD.md`（需求文档，本系统唯一 PRD）、`采购计划管理-复制采购计划-PRD.md`（本功能独立 PRD）
> 状态：**方案待拍板**，未开始实现

---

## 一、需求背景与目标

采购计划字段多（原型 32 个字段，其中业务配置类 23 个），而实际业务中**同一套采购条件反复使用**的场景很常见：

- 同一品牌/品类/企业链路，按月或按季度滚动下单
- 已关闭的旧计划重新启用，只改日期和金额
- 两个计划只差一个企业或一个差价参数

现状下用户只能点「创建采购计划」从零手填 20+ 个字段，重复劳动且易出错。

**目标**：以一条已有计划为模板，一键带出全部业务配置，用户只调整差异项即可保存。

**非目标**：
- 不做批量复制（多选多条计划一次性复制）
- 不做跨页签复制（如把采购订单复制成计划）
- 不做「模板库」概念（本期复制对象就是计划本身）

---

## 二、交互方案选型

给出三种做法，推荐 **方案 B**。

### 方案 A：一键直复制（静默新建）

点击「复制」→ 系统原地生成一条新计划（新编码 + 源计划的业务配置 + 执行态归零）→ Toast 提示成功 → 用户再去列表里找到它点开编辑。

| 优点 | 缺点 |
|------|------|
| 交互最快，一步到位 | 日期必须原样复制，**必然撞唯一性校验**（见 §五）；若源计划日期已过，新计划刷新后被自动置为「执行中」 |
| 实现简单 | 用户看不到表单，改错要二次进入 |
| | 复制出来的是「脏数据」，还得手动清理 |

**结论：不推荐。** 唯一性与日期问题无解。

### 方案 B：复制并打开表单（预填）★ 推荐

点击「复制」→ 打开**创建表单弹窗**，标题显示「复制采购计划（源：PLxxxx）」，表单**预填源计划的全部业务配置**，编码已自动生成新值，执行态字段归零，日期清空 → 用户核对/调整 → 点「保存」才真正入库。

| 优点 | 缺点 |
|------|------|
| 与「创建」共用同一个表单与校验，**零新增校验逻辑** | 比 A 多一次点击 |
| 取消/关闭弹窗 = 不产生任何数据，无副作用 | |
| 日期由用户重填，天然规避唯一性冲突 | |
| 沿用现有 `editingPlanIndex = -1` 分支，`savePlan()` 几乎不用改 | |

### 方案 C：复制为弹窗内的一个按钮

在「编辑采购计划」弹窗底部加「另存为副本」。

**结论：不推荐。** 编辑弹窗只在「待执行」状态可用，而**已关闭/已完成的计划恰恰是最好的复制来源**，把它挡在门外等于砍掉主要使用场景。

## 四、日期策略（关键决策点）★

`f_startDate` / `f_endDate` 是本次唯一需要拍板的字段。

| 方案 | 做法 | 问题 |
|------|------|------|
| ① 原样复制 | 照搬源计划日期 | **双重踩坑**：<br>· 源计划若为「待执行/执行中」，唯一键含日期 → 保存时必被唯一性校验拒绝（PRD UC01 步骤 6）<br>· 源计划日期若已过，页面刷新时 `autoExecutePlans()`（原型 :1332）会把新计划**自动转成「执行中」**，用户还没反应过来计划就跑了 |
| ② 周期平移 | 起 = 今天+1，止 = 今天+1+原周期天数 | 用户友好，但同企业 + 同品牌品类 + 同日期段的计划若已存在，仍会撞唯一性，且用户不易察觉为什么被拒 |
| ③ **清空，强制重填** ★ 推荐 | 两个日期留空 | 用户必须主动选择日期 → 唯一性冲突由用户自己的选择触发，语义清晰；且与现有 `savePlan()` 的必填校验（`:1255-1256` 空日期直接报错）**完全对齐，零改造** |

**推荐 ③。** 理由：日期是复制场景中**最需要变、也最不该猜**的字段——用户复制一条计划，通常正是因为要换一个执行周期。让用户填 2 个日期，换来 20+ 个字段不用填，收益已经很大。

> 若后续觉得 ③ 太生硬，可在日期旁加一个「按原周期填充」的弱化按钮（点击后填 今天+1 ~ 今天+1+原周期天数），但**不作为默认行为**。本期不做。

## 五、唯一性校验的影响

PRD `采购计划管理-PRD.md:303-305` 与 `:351-356` 定义的唯一键：

```
二级采购：品牌 + 品类 + 采购企业1 + 采购企业2 + 预计开始日期 + 预计结束日期
三级采购：品牌 + 品类 + 采购企业1 + 采购企业2 + 采购企业3 + 预计开始日期 + 预计结束日期
```

有效范围（`PRD:563-569`）：

| 执行状态 | 计划状态 | 参与唯一性校验 |
|---------|---------|--------------|
| 待执行 | 启动 | ✅ |
| 执行中 | 启动 | ✅ |
| 已完成 | 关闭 | ❌ |
| 已关闭 | 关闭 | ❌ |
| 已删除 | 关闭（逻辑） | ❌ |

**对复制功能的两点结论**：

1. **复制不新增任何校验逻辑。** 复制出来的计划就是一条普通新计划，走 UC01 原有校验链路。日期由用户重填（§四方案 ③）后，是否冲突交由既有规则判定。
2. **原型 HTML 目前未实现唯一性校验**（检查 `savePlan()` :1237-1314，只有必填/大小关系校验，无唯一键比对）。因此：
   - **原型阶段**：复制保存永远成功，无需改动
   - **上线阶段**：需按 PRD 补唯一性校验，届时从「待执行/执行中」的计划复制且日期未改，会被拒绝并提示源计划编码——这是预期行为

## 六、原型实现方案（代码级）

### 6.1 抽取公共填表函数 `fillPlanForm(p)`

现状：`openEditPlanModal(index)`（:1195-1235）把「打开弹窗 + 填表」写在一起，其中填表逻辑约 35 行。复制功能需要同样的填表逻辑，**先抽取，避免两份重复代码**。

```js
// 新增：把源计划 p 的业务配置回填到表单（不含任何执行态字段）
function fillPlanForm(p) {
    document.getElementById('f_level').value    = p.level;
    document.getElementById('f_brand').value    = p.brand;
    document.getElementById('f_category').value = p.category;
    document.getElementById('f_totalAmount').value = p.totalAmount;
    document.getElementById('f_company1').value = p.company1;
    document.getElementById('f_company2').value = p.company2;
    document.getElementById('f_company3').value = p.company3;
    if (ss1) ss1.setValue(p.company1);
    if (ss2) ss2.setValue(p.company2);
    if (ss3) ss3.setValue(p.company3);
    document.getElementById('f_diff1Type').value = p.diff1Type;
    document.getElementById('f_diff1Pct').value  = p.diff1Pct;
    document.getElementById('f_diff1Amt').value  = p.diff1Amt || 0;
    document.getElementById('f_diff2Type').value = p.diff2Type;
    document.getElementById('f_diff2Pct').value  = p.diff2Pct;
    document.getElementById('f_diff2Amt').value  = p.diff2Amt || 0;
    document.getElementById('f_term1').value = p.term1;
    document.getElementById('f_term2').value = p.term2;
    onLevelChange();          // 必须先跑，按层级决定企业3/差价2/账期2 的显隐与清空
    onDiffTypeChange(1);
    onDiffTypeChange(2);
    document.getElementById('f_minPrice').value = p.minPrice;
    document.getElementById('f_maxPrice').value = p.maxPrice;
    document.getElementById('f_minQty').value   = p.minQty;
    document.getElementById('f_maxQty').value   = p.maxQty;
    document.getElementById('f_minTotal').value = p.minTotal;
    document.getElementById('f_invoiceRate').value  = p.invoiceRate;
    document.getElementById('f_coopTerm').value     = p.coopTerm;
    document.getElementById('f_tradeAmount').value  = p.tradeAmount;
}
```

> **顺序很重要**：`onLevelChange()` 必须在企业/差价/账期回填之后调用（它会按层级清空二级采购下的企业3、差价2、账期2），且要在日期回填之前——原 `openEditPlanModal` 就是这个顺序（:1219-1222），保持一致。

### 6.3 新增 `openCopyPlanModal(code)`

```js
let copyingFromCode = '';   // 仅用于保存后区分 Toast 文案

function openCopyPlanModal(code) {
    const src = plans.find(x => x.code === code);   // 按 code 查找，比下标稳
    if (!src) return;

    editingPlanIndex = -1;                  // 关键：-1 → savePlan 走「新建」分支
    copyingFromCode  = code;

    document.getElementById('modalTitle').textContent = '复制采购计划（源：' + code + '）';
    fillPlanForm(src);

    // —— 执行态归零 ——
    document.getElementById('f_code').value            = genPlanCode(plans.length + 1);
    document.getElementById('f_completionRate').value  = '0.00%';
    document.getElementById('f_execStatus').value      = '待执行';
    document.getElementById('f_planStatus').value      = '启动';
    // —— 日期清空，强制用户重填（§四 方案 ③）——
    document.getElementById('f_startDate').value = '';
    document.getElementById('f_endDate').value   = '';

    openModal('planModal');
}
```

**注意**：按 `code` 查找而非 `filteredPlansData` 下标——与 `executePlan` / `closePlan` / `deletePlan` / `openPlanDetail` 的现有写法一致，也避免分页筛选后下标错位。

现状（:1518-1523）操作列按钮为：执行 / 关闭 / 删除 / 判断详情。插入「复制」，**全状态可用**：

```html
<td>
```

按钮配色：复制用**紫色 `#722ed1`**（Ant Design 紫），与执行绿 / 关闭橙 / 删除红 / 详情蓝区分开。

### 6.5 `savePlan()` 的改动（最小）

`savePlan()` 通过 `editingPlanIndex >= 0` 判断编辑还是新建（:1301-1309）。复制时 `editingPlanIndex = -1`，**天然走新建分支，无需改动判断逻辑**。

仅建议两处小改（可选）：

1. Toast 文案区分来源：
   ```js
   showToast(copyingFromCode ? `已复制采购计划 ${planData.code}（源 ${copyingFromCode}）` : '采购计划已创建', 'success');
   ```
2. 编码兜底（防连点/边界）：新建分支入库前，若 `plans.some(p => p.code === planData.code)` 则重新生成一次。

保存成功后需清空 `copyingFromCode = ''`。
