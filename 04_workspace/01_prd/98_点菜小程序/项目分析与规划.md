## 二、菜谱数据深度分析

### 2.1 数据格式规范

每道菜以 Markdown 文件存储，目录组织为 `dishes/{category}/{dish_name}.md`，内容结构高度统一：

```
# {菜名}的做法

{一段描述：口味、营养、难度概括}

预估烹饪难度：★★~★★★★★

预估卡路里：{数字} 大卡

## 必备原料和工具

- {食材/工具清单}

## 计算

{按份数计算的原料用量公式}

## 操作

{分步骤的烹饪过程}

## 附加内容

{小贴士、变体做法、参考链接}

如果您遵循本指南的制作流程而发现有问题或可以改进的流程，请提出 Issue 或 Pull request 。
```

### 2.2 数据质量评估

| 维度 | 评价 |
| :--- | :--- |
| **完整性** | 每道菜均有完整做法步骤，90%+ 包含食材清单和用量计算 |
| **一致性** | 格式高度统一，便于程序化解析 |
| **难度标注** | 统一使用 ★ 星级标注（1~5星），可做筛选维度 |
| **热量标注** | 每道菜标注预估卡路里，可做健康筛选 |
| **图片关联** | 约 1/3 的菜配有成品图，但图片存储分散（同一菜肴的图片可能在子目录中） |
| **标签缺失** | 缺少"餐次"（早/中/晚）、"受众"（大人/小孩）、"口味"（辣/清淡）等业务标签 |

### 2.3 数据存储现状问题

| 问题 | 说明 |
| :--- | :--- |
| **双模存储** | 部分菜是 `dish.md` 单文件，部分菜是 `dish/` 目录（内含 .md + 图片），解析路径需兼容 |
| **图片分散** | 353 张图片分布于各子目录中，没有统一的图片资源管理 |
| **无元数据层** | 菜谱的"餐次"、"荤素"、"口味"、"烹饪时长"等业务分类均未显式标注，仅隐含在分类目录和描述文本中 |
| **跨类别模糊** | 如"西红柿炒鸡蛋"在素菜类，"西红柿土豆炖牛肉"在肉类，查询时难以做交叉筛选 |

## 三、业务需求与数据缺口分析

对照 [工具架构.md](04_workspace/01_prd/98_点菜小程序/工具架构.md) 的功能需求，分析数据层面的支撑情况：

### 3.1 功能覆盖矩阵

| 功能模块 | 需求详情 | 现有数据支撑 | 缺口 |
| :--- | :--- | :--- | :--- |
| **多维分类** | 按餐次、受众分类 | 仅有食材类别（肉/素/水产等），无餐次/受众标签 | 需为每道菜补充 `meal_type` 和 `target` 标签 |
| **做法详情** | 食材清单、步骤、图片 | 完整覆盖食材和步骤，353 张图片 | 图片需统一管理，部分菜无图片 |
| **智能点菜** | 随机推荐一荤一素一汤 | 荤素汤分类明确，可基于分类目录实现 | 需补充"荤素"标签来覆盖跨类别菜品 |
| **快捷组合** | 保存常用套餐 | 数据层无依赖，纯功能开发 |
| **饮食记录** | 日历看板、频率提醒 | 数据层无依赖，需新建 `meal_logs` 集合 |
| **最爱排行** | 统计"点赞" | 需新建交互数据和排行逻辑 |

### 3.2 关键数据字段映射

从现有 .md 文件可程序化提取的字段：

```yaml
name:        # 文件名或 h1 标题（可自动提取）
difficulty:  # ★ 星级（可用正则提取）
calories:    # 预估卡路里（可用正则提取）
ingredients: # 必备原料清单（可解析列表）
steps:       # 操作步骤（可提取为数组）
category:    # 所属分类目录（现成的）
images:      # 子目录中的图片（需扫描关联）
```

需要手动补充的业务字段：

```yaml
meal_type:   # ['早餐', '午餐', '晚餐', '下午茶']
target:      # ['大人', '小孩', '全家']
taste:       # ['清淡', '微辣', '重辣', '酸甜', ...]
cook_time:   # 烹饪时长（分钟）
is_meat:     # true/false（荤素标识）
tags:        # 自定义标签（'快手菜', '下饭菜', '减脂', ...）
```

### 5.2 数据清洗脚本逻辑

建议用 Node.js 编写的自动化脚本，功能包括：

1. **遍历 dishes/ 目录**，识别两类存储结构：
   - `{category}/{name}.md` → 单文件
   - `{category}/{name}/` → 子目录（内含 .md + 图片）
2. **解析 Markdown**，提取：
   - h1 标题 → 菜名
   - 难度星级 → difficulty
   - 卡路里 → calories
   - 原料列表 → ingredients
   - 步骤文本 → steps
3. **关联图片**：扫描子目录中的 jpg/png/webp 文件
4. **判断荤素**：根据 category 目录（meat_dish/aquatic → true, staple/soup/vegetable_dish 需进一步判断）
5. **输出为结构化 JSON**，供后续导入

### 5.3 标签补全策略

采用"AI 批量标注 + 人工审核"的方式：

- **AI 辅助标注**：根据菜名和食材描述，自动推断 meal_type、target、taste、cook_time
- **人工抽样审核**：对 AI 标注结果抽样 10% 检查修正
- **分批上线**：不需要等 364 道菜全部标完再开始开发，可以先导入 50 道核心菜验证功能

建议首批导入的"核心菜单"（约 50 道）：

| 素菜 | 西红柿炒鸡蛋、酸辣土豆丝、蒜蓉西兰花、蚝油生菜、红烧茄子 |
| 肉菜 | 红烧肉、可乐鸡翅、鱼香肉丝、糖醋排骨、宫保鸡丁 |
| 水产 | 清蒸鲈鱼、白灼虾、咖喱炒蟹 |

## 七、风险与注意事项

1. **数据标签质量**：364 道菜的标签补充是最大的工作量，建议采用"核心菜精标 + 长尾菜粗标"的分级策略
2. **小程序云开发限额**：免费版数据库 5GB、云存储 5GB、云函数 1000 次/天，前期够用，图片需要压缩后上传
3. **图片版权**：现有 353 张图片部分为实拍，需确认无版权风险
4. **家庭多人使用**：如果后续要做多人协同（投票、记录同步），需规划用户体系（微信 OpenID）
5. **菜谱扩展**：后续新增菜谱需建立流程规范（按模板写 .md → 运行脚本更新数据）

## 八、结论

**项目基础扎实，数据充足。** 364 道菜谱覆盖了日常家庭烹饪的绝大多数场景，配合 .md 的结构化格式，通过脚本批量处理后可以快速导入数据库。

最大的瓶颈不在技术开发，而在**数据标签的补充**（为每道菜标注餐次、受众、口味等业务属性）。建议先以 50 道核心菜验证完整链路，再逐步扩展到全部菜谱。
