## 0. 为什么单写一份

设计文档 §5.7 给的是这样两个函数：

```python
def calc_on_inbound(line, balance) -> CalcResult:   # 读余额 → 算新余额 → 返回
def calc_on_outbound(line, balance) -> CalcResult:
```

它把三件事揉在一个函数里：**计量**（算成本金额）、**记账**（改余额）、**校验**（assert 不许负库存）。加进货主分层后还要再塞进去二级分摊。这条路走下去会有四个问题：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **没定义过账顺序** | 移动平均的**结果依赖处理顺序**。同一批单据，先入后出与先出后入得到不同均价 → 不同存货金额 → 对账永远差一点，且差得没规律 |
| 2 | **读-改-写不幂等** | 引擎把余额当输入。余额已被改过再算一次，`old_qty` 变了、结果就变了。§2.2 原则 2「同一笔单据重复计算结果一致」在这个形态下**做不到** |
| 3 | **三个职责耦合** | 计量逻辑是二期唯一会重写的部分（MA → SI / FIFO），却和记账、校验缠在一起，换计价方法要动全链路 |
| 4 | **校验放在月末** | `Σ alloc_amount = 一级层金额` 这类硬约束靠对账事后发现。错数据已经落库，只能靠人找 |

这四处都不是"写代码时注意一下"能解决的，是**结构问题**。下面给出结构。

---

## 1. 定位与边界

**一句话**：核算引擎是把「库存事件序列」**确定性地**翻译成「余额 + 凭证」的**纯函数**，并且是账的**唯一写入者**（single writer）。

「确定性」和「唯一写入者」是这句话里两个不能删的词：前者保证可重放、可审计，后者保证没有第二个地方偷偷改余额。

**引擎不做什么**（边界清单，防止范围蔓延）

| 不做 | 归属 |
|---|---|
| 取价 | 事件层——价与 `price_source` 由单据**快照**进来（框架 4.6），引擎不查价目表 |
| 业务合法性判断 | 事件层——"这单该不该收"是接入适配层的事；引擎只做自身不变量 assert |
| 生成报表 | 投影层——余额、收发存、库龄都是投影 |
| 推消息 / 发通知 | 外部订阅事件表，引擎不知道谁在听 |
| 对账 | **独立的稽核程序**——必须用与引擎**不同的实现**（见 §10），否则是自己检查自己 |
| 结账锁账流程 | 结账是运维动作（打 `is_closed` 标志），引擎只**读取**这个标志并拒绝越界过账 |

---

## 2. 四层结构

```
① 事件层 Events   接入适配层产出。已含：货主、批次、数量、价、price_source、业务日期。
                  ↓  引擎的输入，只读，永不修改
② 计量层 Measure  策略化。MA（一期）/ SI / FIFO（二期）。
                  只回答"这笔业务的成本金额与损益是多少"，不碰余额、不碰凭证。
                  ↓
③ 记账层 Post     生成「余额变动 delta」+「凭证分录」；二级三组金额在此派生。
                  ↓
④ 投影层 Project  余额、报表、对账数据都是「事件 + 分录」的投影（物化视图，可重建）。
```

**关键点：② 是唯一会因二期换计价方法而重写的层。** 所以 ② 与 ③ 之间的接口要先冻结、且**只传金额语义、不传余额**。冻结了这个接口，二期上 SI / FIFO 就是加一个策略实现，其余三层不动。这是整份文档最重要的一条设计意图。

---

## 3. 核心改动：引擎返回 delta，不返回余额

这是与 §5.7 差别最大的一处，也是"幂等"能否成立的分水岭。

```
measure(event: InventoryEvent, ctx: PeriodContext) -> Posting
```

`Posting` 的内容：

| 字段 | 内容 | 说明 |
|---|---|---|
| `balance_deltas[]` | `{ (物料, 仓库, 一级货主, 批次), qty_delta, amount_delta, in_qty_delta, out_qty_delta }` | **变化量**，不是新余额 |
| `alloc_deltas[]` | `{ 二级维度, qty_delta, alloc_amount_delta, internal_amount_delta, internal_cost_price }` | 二级三组金额，见 §7 |
| `pnl[]` | `{ 损益类型, 金额, is_accounting }` | `is_accounting=1` 走会计损益；`=0` 走二级内部损益（R2） |
| `vouchers[]` | `{ 借/贷, 科目, 金额, 辅助核算 owner_code }` | 一级才出凭证（R1 / R2） |
| `rounding_diff` | 本笔舍入差异 | 累加进核算单元的 `rounding_diff_acc`（F3） |
| `trace` | 算式输入的完整快照 | 用了哪个价、来自哪个来源、`price_base` / `markup_rate`；写进 `t_calc_log` 的扩展字段 |
| `invariants` | 引擎自证 | 如 `Σ alloc_amount_delta == 一级层 amount_delta`，见 §7 |

**接口为什么这样定**

| 好处 | 展开 |
|---|---|
| 引擎**无状态** | 输入相同 → 输出逐位相同。这才是 §2.2 原则 2 要的"幂等" |
| 可重放 | 重放 = 忽略现有余额，从**期初快照**（D-01）按事件序列重跑，结果必须一致。这是终极对账手段 |
| 可并发 | 持久化退化为 `balance += delta`，按核算单元加乐观锁（version 列）即可 |
| 可单测 | F1–F15 每个公式都是纯函数，不需要造数据库 |

**余额的持久化**由仓储层做，且必须是**在核算单元行上加锁 + 乐观 version**：

```
UPDATE t_inventory_balance
   SET qty = qty + :qty_delta, amount = amount + :amount_delta,
       version = version + 1
 WHERE 维度键 = :key AND version = :expected_version
```

影响 0 行 → 说明该核算单元被并发改过 → **重试**（重查、重算、重写）。**不要用"读出来算好再写回去"**，那正是缺口 2。

## 4. 顺序与确定性（最致命的一节）

移动平均是**顺序依赖**的。同一业务日两张单，谁先过账决定当日均价。这不是实现细节，是**口径**，必须定义并被测试覆盖。

### 4.1 排序键

```
过账顺序 = (biz_date, seq_in_day)          # 不是 doc_no
```

- `doc_no` **不可用作排序键**：单号不单调（有补单、有外部系统单号、有前缀差异），且业务系统改了单号规则历史数据就乱。
- `seq_in_day` 由引擎在过账时分配的**当日序号**，落库在单据行上（`posting_seq`），全局单调递增，**不复用**。

### 4.2 同一业务日的内部规则（E-01）

同一 `biz_date` 内，`seq_in_day` 的分配规则（**E-01 已锁定：采用方案 B**）。三个候选与取舍理由保留如下，便于日后复盘：

| 方案 | 规则 | 优点 | 缺点 |
|---|---|---|---|
| **A. 业务时刻** | 用业务系统给的 timestamp 排序 | 最贴近事实 | 业务系统**给得出吗**？一期是 Excel 导入，多半没有时刻 |
| **B. 入库优先**（**★ 采用**） | 同日先过所有入库，再出库；同类型按单号 | 避免"当天补入的货被按旧均价出库"——这是业务最不能接受的差异；不依赖上游字段 | 与真实时刻不符（当天先出后入时） |
| **C. 单号序** | 全按 doc_no | 简单 | 单号带日期前缀时会退化，且业务上无意义 |

**采用 B（E-01）**，理由：一期数据来自 Excel / 业务系统推送，**时刻字段不可靠**；而"入库优先"的偏差方向是**业务可以理解的**（当天进的货当天出，按新均价结转是合理口径），比"按单号"这种无法解释的规则强。

> **二期若切 A 必须先决条件**：业务系统能给出**可信的业务时刻**，且切换**必须伴随历史重算**。不能一期 B、二期 A 混着用——两期数据会不可比，且同一批历史单据在两种规则下均价不同，对账会永远差一点。

### 4.3 迟到单据与结账（关联 D-05）

已结账期间来了新单据，两条路：

| 策略 | 做法 | 代价 |
|---|---|---|
| **(a) 禁止**（**★ 采用**） | 已结账期间拒绝入库新单据；确需补记的走"当期补录单"通道，**下在当期**，不动历史 | 历史不可改、可审计；代价是补记的金额落在当期，跨期损益不精确 |
| (b) 级联重算 | 接受迟到单据，级联重算该核算单元其后全部期间 | 已出的报表会被改写；重算窗口可能很长；审计上很难解释"上个月的数变了" |

**采用 (a)（E-04）**。理由：一期还没有"会计期间"概念（§5.6.5 说是二期的事），但**至少要有一个结账标志** `period.is_closed`（**E-03 已锁定：要引入**）——否则永远没有"已定稿"的时点，重放不收敛、审计无从谈起。结账标志是这套引擎**能否被审计**的前提，优先级高于"重算能力"。

**结账周期（E-07 已锁定）**：**月结锁账，日结只做校验、不锁账**。

| 动作 | 周期 | 做什么 |
|---|---|---|
| 日结校验 | 每日 | 跑硬校验与对账（`Σ alloc = 一级层`、数量守恒 F12、金额守恒 F13、批次行均价一致性 E-02），**发现问题当天报，但不锁账** |
| 月结锁账 | 每月 | 舍入差异结转（F3）、跌价计提（F6–F11）、数量金额对账、打 `is_closed` 标志 |

理由：日结锁账会让业务当天补单都做不到；但日结校验能在当天就抓到硬错误，不必等到月末。**"校验"与"锁账"分开，是这一条的全部要点。**

**跨期补录单（E-08 已锁定）**：新增独立单据类型 **`PERIOD_ADJUST`**，**必审**。

> 为什么值得单开一个类型而不是复用现有单据：审计时"哪些数是补记进来的"必须能一眼筛出来。混在普通入库里，事后只能靠人工比对业务日期与记账日期——那正是审计最不信任的做法。必审的理由同源：补录是唯一能绕开"历史不可改"的通道，通道必须有闸。

> **「必审」在一期具体是什么（与 O-19 对齐）**：一期**不建审批流引擎**，只在单据状态机里保留「待审 / 已审核」两个状态位，并保留一个**审核动作**——一个人看一眼、点确认，记 `approved_by` / `approved_at`。所谓"必审"就是**这一步动作不能跳过**，不是"必须跑一条可配置的审批流"。接口按框架文档 O-19 的方式预留：定义 `ApprovalGateway`（`submit` / `approve` / `reject` / `query`），一期给**单点直通实现**，二期接上真审批流时换实现、不动调用方。**通道的闸先划在接口上，闸门本身二期再装。**
>
> 同理，`PERIOD_ADJUST` 的"必审"与**反结账的"须批"（E-09）**是同一个闸的两种用法，不要各写一套。

**跨期补录单的量价口径（E-10 已锁定）**：**一律按当期口径**——补录出库按**当期均价**结转、建**当期成本层**；单据上仍保留原业务日期，但**仅用于追溯，不用于取价**。

> 理由不是"简单省事"，而是**按原期间口径根本算不准**：要知道"这一笔当时若在期内会排在第几位"，而 E-01 的排序键是按**当日序号**分配的（§4.2），跨期回填无法复原那个序号。硬做只能得到一个人为编造的顺序——**报得出来，但报的是假数**。宁可口径统一、口径写清。

**锁账之后的错误出口（E-09 已锁定）**：**允许反结账，但必须走审批并留痕**——记录"谁、何时、因何重开了哪个月"。

| 错误类型 | 走哪条路 | 为什么不能混用 |
|---|---|---|
| **结错了**（结账动作本身有误、计提/结转不对） | **反结账**，重开后重新结 | 语义是"上次的结账结果作废" |
| **漏了一笔**（业务单据迟到、当时没进来） | **当期补录单 `PERIOD_ADJUST`**，下在当期 | 语义是"这笔在原期间从未存在" |

> **两条路的语义不同，混用会让审计无法区分"错误"与"遗漏"**——而这两种情况的责任归属、是否需要追溯调整，恰恰是不同的。反结账是硬锁上的闸，补录单是绕过锁的通道，**闸与通道必须能分开数**。落地时两条路都经同一个 `ApprovalGateway`，但**单据类型、留痕字段、报表口径全部区分**。

> 三条一起说清楚：**一期用"当期补录单"换取"历史不可改"，用"反结账须批"换取"错误仍可修"。** 这是拿精度换可审计性、拿流程换修正通道，都是一期该做的取舍；跨期精确归集留给二期有会计期间之后。

### 4.4 确定性的可验证形式

| 测试 | 断言 |
|---|---|
| 重放一致性 | 同一事件序列过账两次（第二次清空余额重放）→ 余额、凭证、日志**逐位相同** |
| 顺序敏感性 | 同一天打乱输入顺序 → `seq_in_day` 按 §4.2 规则重排后，结果**与有序输入完全相同**；若不同说明排序键没生效 |
| 幂等 | 同一 `(doc_type, doc_no, version_no)` 过账两次 → 第二次**零 delta**（见 §6） |

## 5. 并发边界：核算单元

移动平均的**均价池**不是余额表的行，而是：

```
核算单元 = (物料, 仓库, 一级货主)        # 批次不进均价池
```

批次只影响**库龄**（F6 / F7），不影响均价。所以：

| 规则 | 说明 |
|---|---|
| **同一核算单元内严格串行** | 这是锁的最小单位，也是唯一需要的锁 |
| **不同核算单元可并行** | 整批导入时按核算单元分组 → 组内串行、组间并行 |
| **跨单元单据固定加锁顺序** | 调拨、货权转移同时动两个单元（from / to）。必须**按维度键排序后依次加锁**，否则并发下死锁 |
| **同批次多行的原子性** | 一张单据的全部行在同一事务内过账——不能出现"入库行过了、出库行没过的"半张单 |

**一处必须定的表结构问题（E-02）**：余额表现在以 `(物料, 仓库, 批次)` 为主键，加货主成四轴。但**均价属于核算单元**，不属于批次行。于是有两个选择：

| 方案 | 做法 | 代价 |
|---|---|---|
| **(a) 保留批次行，`unit_price` 作派生值**（**★ 采用**） | 余额表仍是四轴；`unit_price` 在**同一核算单元的所有批次行上必须一致**，由引擎保证 + 加一条一致性校验 | 冗余但改动小；F7 库龄分层直接可用 |
| (b) 拆表 | `均价表(核算单元)` + `批次数量表(四轴)` | 口径最干净，二期 SI / FIFO 更合适；但一期就要动余额表和全部报表 |

一期采用 **(a)（E-02）**，二期上 SI / FIFO 时随批次成本一起改 (b)。

**两个方案都成立的前提**——**"均价的所有者是核算单元"要写进表注释和代码**。写不清，实现就会退化成"每个批次行各自算各自的均价"，那已经不是移动平均了。方案 (a) 下多加一条一致性校验：同一核算单元内所有批次行的 `unit_price` 必须相等，日结时校验、不等即报错。

## 6. 幂等：三种幂等不是一回事

现有设计（§7.5）只覆盖了第一种，容易误以为幂等已经解决。

| # | 层次 | 做法 | 解决的问题 |
|---|---|---|---|
| 1 | **传输幂等** | `batch_id + doc_no + line_no` 去重 | 同一个文件导两次，不重复入库 |
| 2 | **事件幂等** | 幂等键 `(doc_type, doc_no, version_no)`；已过账的键再次提交 → **返回零 delta，不报错** | 重试、消息重投、手工重跑 |
| 3 | **结果幂等** | 引擎是纯函数 + 顺序确定 → 重放逐位相同 | 审计、灾难恢复、口径验证 |

**第 2 条要特别写清**：幂等不是"拒绝了重复请求"，而是"**重复请求返回与第一次相同的结果**"（这里是零变化）。返回错误会让上游以为失败而无限重试。

**改单不能用"删了重来"**：改单 = `version_no + 1` 产生**新事件**，旧版本作为历史保留。这样：
- 重放时序列唯一，结果确定
- `t_calc_log` 上能看到 v1 与 v2 各自的算式输入
- 与货权变更单的"已核算不可撤、只能反向"（框架 4.7）保持同一套语义

## 7. 三组数的派生与校验前移

货主分层后，**一次计量要输出三组数**（框架 4.5）。引擎必须同时产出，且**在出口做硬校验**：

| 输出 | 计算 | 校验 | 不过怎么办 |
|---|---|---|---|
| 一级层（会计口径） | MA 公式 F1 / F2 | 数量守恒 F12 | 整单回滚 |
| `alloc_amount`（二级会计分摊额） | 数量 × **一级均价** | **`Σ alloc_amount_delta == 一级层 amount_delta`（硬）** | **整单回滚**，不是记账后报警 |
| `internal_amount`（二级内部结算额） | 数量 × `internal_price`（快照值） | **不做等式校验** | 差额 = 内部未实现毛利，正常 |

三条要写进代码规范的话：

1. **硬校验放在引擎出口，不放月末对账。** 校验前移是这份设计的核心收益之一——错误数据根本不落库。月末对账是**第二道网**，不是第一道。
2. **`internal_amount` 的差额不许做成"校验告警"。** 它天然不等于一级层金额，做成告警会天天误报（框架 4.5 已写）。
3. **二级的钱只走管理口径。** 引擎输出里 `pnl.is_accounting` 与 `vouchers` 只对一级产生内容；二级产出 `alloc_deltas` 与 `is_accounting=0` 的损益。**凭证里绝不出现二级货主**（O-10）。

## 8. 重构后的伪代码

```python
# ── ② 计量层：纯函数，策略可换 ───────────────────────────────
class MeasureStrategy(Protocol):
    def measure(self, event: InventoryEvent, ctx: PeriodContext) -> Posting: ...

class MovingAverage(MeasureStrategy):
    def measure(self, event, ctx) -> Posting:
        # 1) 取该事件的核算单元快照（只读；不修改）
        for line in event.lines:
            key = CU(line.material, line.warehouse, line.owner_l1)   # 批次不进 key
            snap = ctx.snapshot(key)                                  # qty / amount / unit_price

            if line.is_in:
                # F1
                qty_delta    = line.qty
                amount_delta = line.inbound_amount
                new_qty      = snap.qty + qty_delta
                new_price    = round((snap.amount + amount_delta) / new_qty, 6)
            else:
                # F2 —— 出库不改变单价
                assert snap.qty >= line.qty, "库存不足"          # 引擎内不变量，非业务判断
                amount_delta = round(line.qty * snap.unit_price, 2)
                qty_delta    = -line.qty
                new_price    = snap.unit_price

            posting.balance_deltas.append(Delta(key, line.batch, qty_delta, amount_delta,
                                                unit_price_after=new_price))
            posting.rounding_diff += amount_delta - line.qty * new_price   # F3

        # 2) 二级派生（一次计量、三组输出）
        for line in event.lines:
            if line.owner_l2:
                alloc = round(line.qty * cu_price(line), 2)               # 按一级均价
                internal = round(line.qty * line.internal_price, 2)        # 快照价
                posting.alloc_deltas.append(AllocDelta(..., alloc, internal,
                                                       internal_cost_price=line.internal_price))
                if event.doc_type == 'OWNER_REASSIGN':
                    posting.pnl.append(Pnl('二级内部损益', internal - alloc, is_accounting=0, ...))

        # 3) 一级损益与凭证
        if event.doc_type == 'OWNER_TRANSFER':
            posting.pnl.append(Pnl('一级转移损益', transfer_price_amt - cost_amt, is_accounting=1, ...))
        posting.vouchers = build_vouchers(event, posting)                  # 辅助核算只带 owner_l1

        # 4) 出口硬校验（不过就抛，整单回滚）
        assert posting.invariants.alloc_equals_l1(), "Σ alloc_amount ≠ 一级层金额"
        return posting
```

```python
# ── ③ 记账层：加锁 + delta，绝不读-改-写 ─────────────────────
def post(event, strategy) -> None:
    if is_posted(event.idempotency_key):        # §6 第 2 层：返回零 delta
        return
    with unit_of_work():
        keys = sorted(lock_keys(event))          # §5：固定加锁顺序，防死锁
        ctx  = ctx.load(keys)                    # 只读快照
        p    = strategy.measure(event, ctx)
        for d in p.balance_deltas:
            apply_delta(d, expected_version=ctx.version(d.key))   # version 不匹配 → 重试
        apply_alloc_deltas(p.alloc_deltas)
        write_vouchers(p.vouchers)
        write_calc_log(event, p.trace)           # 含 price_source / price_base / markup_rate
        mark_posted(event.idempotency_key)
```

## 10. 可测试性（是设计的一部分，不是测试计划）

引擎的可靠性不能靠"上线后对账发现"，要靠**可重放的测试资产**：

| 资产 | 内容 |
|---|---|
| 公式单测 | F1–F15 各一个；边界包含 `old_qty=0`、出清 F4、舍入 F3、双轨孰高 F10 |
| **Golden case 回归** | 把《货主分层口径分析与表述框架》第 7 章的 7 组案例固化为测试：输入单据 → 期望余额、三组金额、凭证**逐字段**比对。案例 7.2（二级重分配）与 7.3（集团内转移）是必测 |
| 重放一致性 | 随机生成 N 笔单据 → 全量过账 → 清空余额 → 重放 → 逐位相同（§4.4） |
| 顺序敏感性 | 同日打乱 → 按排序键重排后结果必须一致（§4.4） |
| 并发正确性 | 同一核算单元并发过账 → 无丢更新、无死锁 |
| **独立对账实现** | 对账程序**不复用引擎代码**：用 SQL 直接聚合单据流水算"应有余额"，与余额表比对。复用引擎代码的对账只能证明"引擎和自己一致" |

最后一条容易被省掉，但它是唯一能发现"引擎整体性错误"的手段——**自洽的错误是最危险的错误**。

## 12. 一页速查

**一句话**：核算引擎 = 把库存事件序列**确定性**翻译成余额 + 凭证的**纯函数**，是账的唯一写入者。

**六个设计决定**

| # | 决定 |
|---|---|
| 1 | **返回 delta，不返回余额**（§3）——幂等、可重放、可并发的前提 |
| 2 | **四层**：事件 / 计量 / 记账 / 投影；只有**计量层**会因二期换计价方法而重写（§2） |
| 3 | **顺序必须定义**：`(biz_date, seq_in_day)`，同日入库优先；`doc_no` 不能当排序键（§4） |
| 4 | **锁的最小单位 = 核算单元 `(物料, 仓库, 一级货主)`**；跨单元按维度键顺序加锁防死锁（§5） |
| 5 | **校验前移**：`Σ alloc = 一级层` 在引擎出口硬校验、不过整单回滚，不等月末对账（§7） |
| 6 | **三种幂等分开**：传输 / 事件 / 结果；改单 = `version+1` 新事件，不是删了重来（§6） |

**两个最容易被省掉、但省掉就出事的东西**

- **结账标志**（E-03 已锁定要引入；周期见 E-07：月结锁账 + 日结只校验）——没有"已定稿"的时点，重放不收敛，历史随时能被改写。
- **独立对账实现**（§10）——复用引擎代码的对账只能证明引擎和自己一致。

**已锁定的十条（E-01 – E-10）**

| 编号 | 一句话 |
|---|---|
| E-01 | 同日**入库优先** + 同类型按单号；`doc_no` 不当排序键 |
| E-02 | 余额表**保留批次行**（四轴）；均价归核算单元，加日结一致性校验 |
| E-03 | **引入结账标志** `period.is_closed` |
| E-04 | 迟到单据**禁止**，走**当期补录单** |
| E-05 | **按核算单元串行、跨单元并行**；实时与批量走同一 `measure` |
| E-06 | **事件为真相源**，余额是投影；重放起点由 D-01 决定 |
| E-07 | **月结锁账 + 日结只校验**——"校验"与"锁账"分开 |
| E-08 | 跨期补录单独立类型 **`PERIOD_ADJUST`**，**必审**（一期 = 单点审核动作 + 留痕） |
| E-09 | **允许反结账，但须走审批并留痕**；反结账与补录单**两条路分开用**，不互相代替 |
| E-10 | 补录单一律**按当期口径**量价；原业务日期仅供追溯，不用于取价 |
