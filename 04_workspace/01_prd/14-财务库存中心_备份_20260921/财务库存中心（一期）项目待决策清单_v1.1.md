## 0. 怎么用这份清单

现有两份文档解决了"**正常流程怎么做**"（正向/逆向流程、公式、算例、接口契约、定义权归属），本清单专补另外四类**"非正常但必然发生"**的问题：**起点（开账）、例外（暂估/负库存/退货）、边界（金蝶/法人/权属）、工程（性能/切换/治理）**。

每个决策项结构统一：

```
为什么要问           →  不回答会导致什么后果
决策选项             →  A / B / C 各自的做法、优点、代价
建议默认值           →  若无人反对即可采用
🔒 v1.1 锁定结论      →  v1.1 新增：本条实际采用的结论（含被推翻的）
责任方               →  谁拍板、谁参与
最晚时点             →  超过这个时点再定就要返工
影响范围             →  会改动哪些设计文档章节
```

**v1.1 的读法变了**：原清单假设"每项都要开会逐条拍板"，所以给了「建议默认值」等会上确认。**v1.1 起 13 条已全部锁定**——每项标题下方都有一条 `🔒 v1.1 锁定结论`，**那是本条的正式结论**，「建议默认值」段保留只为**留推导依据**（被推翻时能找到要改哪几处）。

**优先级按"最晚回答时点"划分**（v1.1 后含义微调——**P0/P1 已全部锁定，优先级现在表示"若被推翻，返工代价有多大"**）：

| 优先级 | 时点 | 不定会怎样（现含义：推翻的代价） |
|---|---|---|
| **P0** | W1 内 | 需求与详细设计无法定稿，**后续开发必返工** |
| **P1** | W1–W2 设计评审 | 影响**数据模型与核算引擎结构**，改起来伤筋动骨 |
| **P2** | W6–W8 上线前 | 影响实施与运维，不冲击核心模型 |

## 2. P0 决策项（**已全部锁定** · 推翻代价最大）

### D-01 开账日与期初库存来源

> **🔒 v1.1 锁定结论：A + C**（按建议默认值）
> 以**金蝶存货余额倒推**为基准（开账日金蝶存货科目余额 ÷ 库存数量 = 期初单价）；对金蝶余额异常（负库存、无单价、金额与数量不匹配）的物料，**由财务指定评估价**。期初数据做成一张《期初库存导入表》一次性导入，**双人复核后锁定**。
> **设计侧已落地**：`t_initial_balance`（设计 `4.3.5`）。
> **唯一前提**：**开账日必须与业务库存中心的库存快照时点完全一致**，否则第一天账实就对不上。

**为什么要问**

移动平均是**从开账日起累积**的算法：`新均价 = (期初金额 + 本次入库金额) ÷ (期初数量 + 本次入库数量)`。期初若没有单价，开账后第一笔出库**无成本可结转**，整个成本链从第一天就失真。

另一个隐藏前提：**开账日必须与业务库存中心的库存快照时点完全一致**，否则第一天账实就对不上。

**决策选项**

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A | **金蝶存货余额倒推**：开账日金蝶存货科目余额 ÷ 库存数量 = 期初单价 | 与总账天然一致，审计友好 | 金蝶历史数据若不干净（负库存、串料、暂估未冲回）会带病进入新系统 |
| B | **最近采购价** | 最快、业务好理解 | 历史采购价缺失或已过时，偏差大 |
| C | **手工评估 + 财务确认** | 最可控，可留评估依据 | 工作量大，SKU 多时不可行 |

**建议默认值**

**A 为主 + C 兜底**：以金蝶余额倒推为基准；对金蝶余额异常（负库存、无单价、金额与数量不匹配）的物料，由财务指定评估价。期初数据做成一张《期初库存导入表》一次性导入，**双人复核**后锁定。

**责任方**：财务部（主）· 业务团队（提供数量）· IT（提供金蝶导出）
**最晚回答**：W1 第 2 天
**影响范围**：设计文档 4.3 库存余额表（是否加"期初"来源标记）、5.3 入库场景、3.7 算例基线；契约文档 2.4 快照

### D-02 与金蝶系统的边界（唯一成本源）

> **🔒 v1.1 锁定结论：A**（按建议默认值）
> **本系统为唯一成本源**：金蝶关闭存货核算，存货/成本凭证由本系统生成凭证清单 + **Excel 导出**（**不直推金蝶**）。
> **设计侧已落地**：设计 `8` 凭证生成、`13.1` 科目映射。
> **与契约 v1.2 的一致性**：金额对账的对手是**金蝶总账**（契约 §2.4b / F04）——不是矛盾，而是同一件事的两面：本系统是**成本源**（唯一算出值的），金蝶总账是**过账结果**（本系统凭证导入后的落点）。对账即核"我们生成的凭证有没有被正确过账"。

**为什么要问**

如果金蝶的**存货核算模块同时启用**，会出现两套存货科目余额——本系统算一套、金蝶算一套。年终审计时两个数字打架，谁都说不清哪个对。**必须指定唯一成本源**，这是整个项目最大的组织风险。

**决策选项**

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A | **本系统为唯一成本源**：金蝶关闭存货核算，存货/成本凭证由本系统生成 Excel 导入 | 口径统一，能做精细成本 | 依赖本系统稳定性 |
| B | **金蝶为唯一成本源**：本系统只做分析与对账，不产凭证 | 风险最低 | 本系统"核算模块"定位名不副实，无法做精细成本 |
| C | **双轨并行**：两边都算，月末对账 | 看似稳妥 | 差异解释成本极高，**不推荐** |

**建议默认值**

**A**——与一期既定方案"生成凭证清单 + Excel 导出、不直推金蝶"完全一致。

**责任方**：财务部（主）· IT · 金蝶实施方
**最晚回答**：W1
**影响范围**：设计文档 8 凭证生成、13.1 默认科目映射、10.3 可扩展性

### D-03 核算主体（法人/账套）与跨主体调拨

> **🔒 v1.1 锁定结论：C —— 多主体 + 调拨视同销售 + 内部抵消报表**
>
> **⚠️ 本条采用的不是原「建议默认值」，因为原默认已被推翻。**
>
> | | 内容 |
> |---|---|
> | **原建议默认** | "若一期为单主体，数据模型仍预留 `legal_entity` 字段（默认主体），**但不开多主体功能**" |
> | **为什么失效** | 货主分层引入后，**一级货主 = 法人主体**，且一期**已确认做跨法人转移**（视同销售、必出凭证、必确认会计损益、需合并抵消）。原默认的三个前提（单主体 / 调拨不视同销售 / 无抵消）**全部不成立** |
> | **现锁定** | **C**：加 `legal_entity` 维度 + 内部交易标识 + 抵消报表 |
>
> **设计侧已落地**：`legal_entity` 进四轴（设计 `6.1`）、`t_owner_transfer` 一级货权转移单（`4.2.3`）、**集团内未实现损益抵消**（凭证模板 `8.1.10`）、`voucher_source` 与账套（`4.4.1`）。相关规则见框架 **R1 / R4** 与 **O-12**（"集团内未实现损益抵消"由"单法人可不做"改为**一期即需做**）。
>
> **尚未闭环的一项**：**金蝶侧的账套能否承载多法人**——需 D-02 的金蝶实施方确认。这是本条的**外部依赖**，不是设计问题。
>
> **对另外两个子问题的回答**（原清单要求回答的三个问题）：
> 1. 一期涉及几个会计主体？→ **多个**（具体几个由财务部给出法人清单）
> 2. 跨法人调拨是否视同销售？→ **是**（R1）
> 3. 是否需要内部交易抵消报表？→ **需要**（O-12，一期即做）

**为什么要问**

这决定数据模型**是否需要在物料/仓库/单据/余额上增加"法人（账套）"维度**。**现在加是加字段，开发后再加是重构**——这是全清单里最贵的一条。

**要回答的三个问题**

1. 一期涉及**几个会计主体**（法人 / 账套）？
2. **跨法人调拨是否视同销售**（需开票、产生内部交易）？
3. 是否需要**内部交易抵消**报表？

**决策选项**

| 选项 | 模型改动 | 适用场景 |
|---|---|---|
| A | **单主体**：不加法人与抵消逻辑 | 一期只覆盖一个法人 |
| B | **多主体 + 调拨不视同销售**：加 `legal_entity` 字段与主体间调拨标识，只做库存转移 | 同集团内部调拨 |
| C | **多主体 + 调拨视同销售**：加字段 + 内部交易标识 + 抵消报表 | 独立法人间的真实交易 |

**建议默认值**

先确认主体数量。若一期为单主体，**数据模型仍预留 `legal_entity` 字段（默认主体），但不开多主体功能**——为二期留路，成本极低。

**责任方**：财务部（主）· 项目组
**最晚回答**：W1（直接涉及建表）
**影响范围**：设计文档 4.1 主数据、4.2 单据流水、4.3 库存余额、9 对账维度；契约文档 3 一致性矩阵（仓库归属公司）

### D-04 暂估入库与发票冲回

> **🔒 v1.1 锁定结论：A**（按建议默认值）——**只调当期余额，不做追溯重算**
> 一期用 **A**（匹配"常规接口、快速上线"目标）；同时要求业务侧**提供"暂估入库"与"发票到达"两个独立事件**；二期视差异金额大小评估是否升级为 B。
> **设计侧已落地**：设计 `5.6.6`（新增，F19）——`t_document_line.settle_status`（`ESTIMATED`/`SETTLED`/`ADJUSTED`）+ `estimate_ref_doc`；发票到达时**追加反向事件 + 据实事件**，**各出一张凭证**。
> **⚠️ 落地形式与选项 A 的字面描述有一处不同、需说明**：A 原文是"冲回只调整当前库存金额"——听起来像一次 UPDATE；**设计实际做成"反向事件 + 据实事件"两笔追加**（理由：E-06 事件为真相源，事件只增不删）。**语义等价**（都不追溯、都只影响当期），但**实现是追加不是修改**。这也顺带满足 A 原本的"差额挂待处理成本差异"——差额落在两张凭证的价差科目上（`8.2` 价差三分类）。
> **二期升级路径**：若确认升级为 B（全量重算），**不推翻现架构**——`t_calc_log` 已有 `posting_seq` 与快照，重放能力是引擎自带的（PF8 反结账同一套机制）。

**为什么要问**

货到票未到是贸易/电商的**高频日常**。标准做法是：暂估价入库 → 发票到达 → 冲回暂估、按实际价重入。

难点在移动平均下：**若冲回时该物料期间已发生过出库，冲回会牵动后续所有出库的成本**。这是**架构级选择**，不是细节。

**决策选项**

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A | **只调余额（不追溯）**：冲回只调整当前库存金额，差额挂"待处理成本差异" | 实现简单，快速上线 | 账面成本有尾差，需专门科目归集 |

### D-05 负库存与时间倒挂

> **🔒 v1.1 锁定结论：A 为默认（硬禁止）＋ C 的容差逻辑预留但阈值 = 0（一期关掉）**（按建议默认值）
> 由**业务系统保证不产生负库存**，财务侧收到即拦截；对调拨在途、平台仓回传场景**预留 C 的容差逻辑**，但**阈值可配且默认 0**——即**一期实际等价于纯 A**。
> **设计侧已落地**：设计 `5.4` 出库场景、`5.6` 特殊场景、`3.4` 逆向流程图。
> **⚠️ 与迟到单据口径的联动**（契约 v1.2 / C-03）：**已锁账期间禁止迟到单据入账**，漏记走当期补录单 `PERIOD_ADJUST`。负库存拦截与锁账拦截是**两道独立的闸门**，任一不过即拒绝，**不要合并成一道**。

**为什么要问**

设计文档写的是"禁止负库存"，但现实必然出现：**先卖后到货、跨仓调拨在途、平台仓数据回传延迟**。财务侧拿到一张出库单时账上无货，**移动平均没有单价可用**。

**决策选项**

| 选项 | 做法 | 适用 |
|---|---|---|
| A | **硬禁止**：业务系统保证不产生负库存，财务侧收到即拦截 | 对业务系统要求高，最干净 |
| B | **待成本挂账**：允许单据进入，成本暂挂"待成本"科目，后续入库补齐单价后自动补算 | 贴合现实，工程量大 |
| C | **临时容差**：在途/跨仓场景短时允许负库存，按最近有效单价暂估，入库后自动修正 | 折中，阈值可配 |

**建议默认值**：**A 为默认**；对调拨在途、平台仓回传场景**预留 C 的容差逻辑**（阈值可配，默认 0，即一期先关掉）。

**责任方**：业务团队（主，保证单据顺序）· 财务部（口径）
**最晚回答**：W2
