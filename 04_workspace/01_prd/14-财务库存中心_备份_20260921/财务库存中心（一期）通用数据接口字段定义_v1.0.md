# 财务库存中心（一期）通用数据接口字段定义

> 版本：v1.0（**接口协议未定型下的通用字段层**）
> 用途：一期数据来源确定为**直接 API 对接**，但接口协议与字段清单**尚未与业务侧确定**。本文先把**协议无关的字段层**定下来，作为前端、后端、测试三方的共同基线；协议定型后**只补映射，不改字段**。
> 读者：后端（适配层与落库）、前端（接入页与错误清单）、测试（用例与断言）、业务库存中心团队（W1 接口评审会）
> 关联文档：设计 v0.4 `§7`（数据接入与接口字段表）/ `§7.6`（适配层接口预留）· 契约 v1.2（业务侧义务）· PRD v1.1（FR-12 – FR-16）· 引擎 v1.3（三种幂等）
>
> 编号约定：字段描述用**表内行**，不引新编号；错误码用 **`E-xxx`**（本文首次系统化，与 F-xx / C-xx / D-xx / O-xx / E-01–E-10 / V-xx 均不重叠——`E-01`–`E-10` 是引擎决策项，`E-XXX-YYY` 是报文错误码，**形式不同、不冲突**）。

---

## 0. 先把三件事拆开

「接口未定」**不是阻塞项**，因为这套架构本来就把边界划在**接口**上而不是划在**功能**上（设计 `7.6`，同一套路见 O-19 的 `ApprovalGateway`）。所以现在能定的、不能定的，分得很清楚：

| # | 事项 | 状态 | 本文做什么 |
|---|---|---|---|
| 1 | **字段定义**（字段名 / 类型 / 精度 / 必填 / 枚举 / 幂等键 / 错误回执） | **本文定下来** | 全文 |
| 2 | **传输协议**（REST / MQ / 文件，URL、鉴权、分页、重试） | **待定** | `§9` 留映射位 + 给示例，不改字段 |
| 3 | **部署与运维**（网络、证书、调度、责任人） | **待定**（D-12） | `§10` 列待回填项 |

> **一句话**：**字段先冻结，协议后面套。** 无论最后是 REST 还是消息队列，都是把同一套字段换个壳子装——**换壳不改字段**。
>
> **保留的导入入口是同一套字段的另一种绑定**：Excel/CSV 导入不是"另一条技术路线"，它就是通用字段集的一个**文件绑定**（`§9.3`）。所以两条入口**共用一套校验、一套幂等、一套错误回执**——这正是"先保留导入"不会造成两套逻辑的原因。

## 1. 三层边界：谁定什么

| 层 | 内容 | 谁定 | 现状 |
|---|---|---|---|
| **业务事实层** | 11 类单据流水、主数据、数量快照 | **业务库存中心**（① 业务权威 / A 级主数据须双方一致） | 契约 v1.2 已列义务 |
| **通用字段层** | 字段名、类型、精度、必填、枚举、幂等键、错误回执 | **双方共同**（本文） | **v1.0 已定**，W1 会确认 |
| **传输协议层** | REST / MQ / 文件、鉴权、调度、重试 | **双方 + IT** | **待定**（`§10`） |
| **价值回传层** | 库存金额 / 库龄 / 跌价 / 两个金额口径 | **财务库存中心**（④ 财务定义并回传） | 契约 v1.2 `§4.2` + 本文 `§7` |

> **跨象限只读引用，不改变定义权归属。** 业务侧推过来的字段，定义权在业务侧；财务回传的字段，定义权在财务侧。**双方都不许"顺手改一下对方的口径"**。

## 2. 通用约定

### 2.1 报文信封

所有报文**共用同一个信封**，`object` 决定 `records` 里装什么。信封字段与业务字段**分开放**，便于协议层做路由、限流、审计。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `batch_id` | string(32) | Y | **传输批号**，由**推送方**生成（财务侧也接受服务端补生成）；同一批重推**必须复用同一个 `batch_id`**，否则传输幂等失效 |
| `source_system` | string(32) | Y | 来源系统标识（如 `BIZ_INV`），用于多来源隔离 |
| `schema_version` | string(16) | Y | 字段定义版本，本期固定 `v1.0`；**不匹配即拒绝**，防"字段悄悄改了不说" |
| `object` | enum | Y | `master_data` / `document` / `doc_action` / `snapshot` |
| `push_time` | datetime(带时区) | Y | 推送时刻，`YYYY-MM-DDTHH:mm:ss±HH:mm` |
| `record_count` | int | Y | 声明条数；与实际 `records` 长度**不符即整批拒绝**（防截断） |
| `records` | array | Y | 记录数组，元素结构见 `§3`–`§6` |

> **不加 `legal_entity` 到信封**：法人是**行级**属性（同一批里可以混法人），放信封会把"一批一法人"这个错误约束写死。

### 2.2 数据类型与精度规范

| 逻辑类型 | 精度 | 适用字段 | 约定 |
|---|---|---|---|
| **数量** | `decimal(18,4)` | `qty` `base_qty` `book_qty` `actual_qty` | **核算一律用 `base_qty`（基本单位）**；业务单位数量只作展示 |
| **金额** | `decimal(18,2)` | `amount_ex_tax` `tax_amount` `allocated_cost` `alloc_amount` `internal_amount` | 入账基数**不含税**；含税金额只用于核对 |
| **单价** | `decimal(18,6)` | `transfer_price` `internal_price` `price_base` `price_value` `unit_price` | **6 位**——移动平均单价按 6 位舍入 |
| **加成率** | `decimal(10,7)` | `markup_rate` | **7 位**——与设计 `4.2.4` 一致 |
| **税率** | `decimal(10,6)` | `tax_rate` | 默认 `0.13` |
| **日期** | `YYYY-MM-DD` | `biz_date` `effective_from` | **业务日期，非推送日**（填错 + 已锁账 = 直接拒绝） |
| **布尔** | `0` / `1` | `is_in` `is_internal` `is_related_party` `batch_managed` | **不用 `true/false`、不用 `是/否`**——文件绑定侧负责把"是/否"翻译成 `0/1` |
| **编码** | string | `material_code` `warehouse_code` `owner_l1` `doc_no` | 见 `§2.3` |

> **数量一律传 `base_qty`**（基本单位），这是核算唯一口径。业务单位 `qty` + `unit` 一并传，系统用 `convert_rate` 验算 `base_qty`——**对不上就拒绝，不做 1:1 兜底**（兜底会让数量对账永远差一笔）。

### 2.3 编码规则

| 对象 | 规则 | 备注 |
|---|---|---|
| 物料 / 仓库 / 货主编码 | 大写字母 + 数字 + 连字符，≤ 32 位 | **一级货主为 A 级主数据，须双方一致** |
| 单据号 `doc_no` | ≤ 64 位，**同一 `doc_type` 内唯一** | **不可作排序键**（`§2.6`） |
| 行号 `line_no` | 整数，**同一 `doc_no` 内从 1 递增** | 调拨展开后两行 `line_no` 连续 |
| 批次号 `batch_no` | ≤ 64 位；**允许为空** | 空 = 不按批次管理，落库为 `NULL` |
| 二级货主 `owner_l2` | **必须以 `owner_l1` 为上级** | 一级缺失时二级一律拒绝 |

### 2.4 空值与缺省

| 情况 | 约定 |
|---|---|
| 无值 | 传 `null`，**不传空字符串**（`""` 与"未维护"无法区分） |
| 未维护的换算率 | **必须报错拒绝**，不得缺省为 1 |
| `tax_rate` 缺失 | 缺省 `0.13`，**这是唯一的缺省值** |
| 未管理的维度 | `batch_no` / `owner_l2` 传 `null`，**不传占位符**（`"N/A"` `"-"` 一律视为非法值） |

### 2.5 一致性等级（沿用契约的四级标注）

| 级别 | 含义 | 冲突处理 |
|---|---|---|
| **A 级** | 双方必须一致 | 不一致**拒绝入账**并回执（如一级货主清单） |
| **B 级** | 允许一方滞后，但须可追溯 | 记录差异并预警 |
| **① 业务权威** | 业务侧说了算 | 财务**只取价 / 只采信**，不覆盖 |
| **④ 财务权威** | 财务侧定义并回传 | 业务侧只读使用 |

### 2.6 幂等键（**三层，不是一件事**）

| 层 | 键 | 防什么 | 重复时的行为 |
|---|---|---|---|
| **传输幂等** | `batch_id + doc_no + line_no` | 同一批推两次 | **自动跳过**，计入"去重"而非"失败" |
| **事件幂等** | `(doc_type, doc_no, version_no)` | 同一事件重放两次 | **返回零 delta 且不报错**（不是抛异常） |
| **结果幂等** | 纯函数 `(event, ctx) → Posting` | 重放结果不可复现 | 同一输入必得同一结果 |

> **只做传输层去重不够**——**重放（反结账）也会重复触达事件层**。测的时候要专门断言"重复事件返回零 delta 且 HTTP 200 / 业务码成功"，不是断言"报错"。
>
> **排序键是 `(biz_date, seq_in_day)`，`doc_no` 不可作排序键**：乱序推同一批单据，结果必须与顺序推**一致**（FR-24 的验收断言）。

### 2.7 错误回执

**整批拒绝用信封级**，**行级错误用记录级**——一次回执里两者可同时出现。

```json
{
  "batch_id": "BATCH-20260122-03",
  "schema_version": "v1.0",
  "result": "PARTIAL",
  "accepted": 49,
  "rejected": 1,
  "deduplicated": 0,
  "errors": [
    {
      "row_no": 37,
      "field": "owner_l1",
      "error_code": "E-CROSS-LEGAL-ENTITY",
      "raw_value": "调出仓 WH01(ENT_A) → 调入仓 WH02(ENT_B)",
      "suggestion": "跨法人转移须改推 OWNER_TRANSFER，系统不做自动升级"
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `result` | `SUCCESS` / `PARTIAL` / `REJECTED`（整批拒绝）/ `DEDUPLICATED`（全部命中幂等） |
| `row_no` | **报文内序号**，必须能定位回原文；文件绑定时即 Excel 行号 |
| `field` | 出错的字段名（**用本文的字段名**，不是中文列名） |
| `raw_value` | **原文**——用于导出错误清单时不丢上下文 |
| `suggestion` | 给出可执行建议，**不是"数据有误"这种废话** |

**错误码全集**：

| 错误码 | 触发条件 | 处理 |
|---|---|---|
| `E-HEADER-INVALID` | 报文字段名/顺序/`record_count` 不符 | **整批拒绝**，返回模板说明 |
| `E-SCHEMA-VERSION` | `schema_version` 不匹配 | 整批拒绝 |
| `E-MASTER-MISSING` | 物料 / 仓库 / 货主 主数据不存在 | 行级拒绝 |
| `E-OWNER-L1-MISSING` | `owner_l1` 缺失或非 A 级编码 | **行级拒绝**（四轴缺一轴不可入账） |
| `E-OWNER-L2-ORPHAN` | 二级货主无有效上级 | 行级拒绝 |
| `E-ENUM-INVALID` | 枚举值不在字典内 | 行级拒绝 |
| `E-UNIT-CONV-MISSING` | 换算率未维护 | **行级拒绝，不做 1:1 兜底** |
| `E-QTY-MISMATCH` | `qty × convert_rate ≠ base_qty` | 行级拒绝 |
| `E-CROSS-LEGAL-ENTITY` | 跨法人推 `TRANSFER` | **行级拒绝 + 回执原因**，要求改推 `OWNER_TRANSFER` |
| `E-PRICE-MISSING` | 一级转移缺 `transfer_price`，或二级缺 `internal_price` | 行级拒绝 |
| `E-PERIOD-CLOSED` | `biz_date` 落在**已锁账期间** | **行级拒绝**；漏记只能开当期补录单 |
| `E-NEGATIVE-QTY` | 出库导致负库存且超出容差 | 行级拒绝或预警（按 `t_depreciation_rule` 同级的容差配置） |
| `E-SRC-DOC-MISSING` | 退货单的 `orig_doc` 无法定位 | 行级拒绝 |

> **回执是业务侧唯一能看到"为什么被拒"的地方**，所以 `suggestion` 必须写清楚**怎么改**。这直接决定 W1 之后两边的沟通成本。

## 3. 主数据字段字典（`object = master_data`）

> 主数据**先于单据**接入。四轴的任何一轴缺失，单据一律拒绝入账。
> **注意**：设计 `7.2` 的字段表是 **Excel 中文列名**视角；本节是**规范字段名**视角。两者一一对应，文件绑定负责翻译（`§9.3`）。

### 3.1 物料 `record_type = material`

| 字段 | 类型 | 必填 | 一致性 | 说明 |
|---|---|---|---|---|
| `material_code` | string | Y | A 级 | **唯一键** |
| `material_name` | string | Y | — | |
| `material_category` | enum | N | — | 物料类别，决定跌价规则 |
| `unit` | string | Y | — | 基本单位（核算用） |
| `spec` | string | N | — | 规格 |
| `batch_managed` | bool | N | — | 是否批次管理 |
| **`launch_date`** | date | **Y** | **① 业务权威** | **3C 上市周期法的唯一输入；缺失则该物料算不出跌价** |
| `enabled` | bool | Y | — | 启用标志 |

### 3.2 仓库 `record_type = warehouse`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `warehouse_code` | string | Y | 唯一键 |
| `warehouse_name` | string | Y | |
| `warehouse_type` | enum | Y | `SELF` / `PLATFORM` / `OVERSEA` / `IN_TRANSIT` / `VIRTUAL`——**无"原料库/在制品库"**（业务画像是纯贸易，无生产环节） |
| **`legal_entity`** | string | **Y** | **所属法人**——权属判定的输入之一 |
| `cost_enabled` | bool | Y | 是否参与库存核算 |

> **权属不由仓库类型决定**（D-06 已更正）：**由一级货主的 `is_internal` 决定**。仓库类型只影响库龄与在途处理。

### 3.3 货主 `record_type = cargo_owner`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `owner_code` | string | Y | 唯一键 |
| `owner_name` | string | Y | |
| `owner_level` | int | Y | `1` = 一级货主（法人）/ `2` = 二级货主（管理维度） |
| `parent_code` | string | 条件 | 二级**必填**指向其一级 |
| `is_legal_entity` | bool | Y | 是否法人 |
| `ledger_set` | string | 条件 | **一级必填**（金蝶账套标识） |
| **`is_internal`** | bool | Y | **决定是否进存货总额、是否计提跌价**——这是全系统最关键的一个布尔 |
| `related_party` | bool | N | 关联方标识（决定合并抵消） |
| `effective_from` | date | Y | 生效起 |
| `effective_to` | date | N | 生效止，空 = 长期 |

> **一级货主是 A 级主数据**：两边清单不一致时，**单据拒绝入账**，不是"先收了后面再对"。因为一级货主是四轴之一，错了整个存货总额就是错的。
>
> **O-07 仍是唯一外部依赖**：业务侧**是否也建货主维度**未定。一期财务侧按物理层 `(物料, 仓库, 批次)` 对账，不预设业务侧有货主轴。

## 4. 单据字段字典（`object = document`）

### 4.1 单据头（所有单据类型共用）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `doc_no` | string | Y | **同一 `doc_type` 内唯一** |
| `doc_type` | enum | Y | 11 类之一，见 `§4.3` |
| **`biz_date`** | date | **Y** | **业务日期（A 级）**。**必须是真实业务发生日，不能填推送日** |
| `biz_status` | enum | N | `DRAFT` / `SUBMITTED` / `APPROVED` / `EFFECTIVE` / `VOID`；缺省 `EFFECTIVE` |
| `legal_entity` | string | Y | 法人（行级可不同法人，故也允许行级覆盖） |
| `counterparty_code` | string | 条件 | 供应商 / 客户 / 往来单位编码 |
| `approved_by` / `approved_at` | string / datetime | 条件 | **「必审」= 单点审核动作 + 留痕**（O-19，不建审批流引擎） |
| `remark` | string | N | |

### 4.2 单据行（所有单据类型共用）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `line_no` | int | Y | `doc_no` 内从 1 递增 |
| `material_code` | string | Y | |
| `warehouse_code` | string | Y | |
| **`is_in`** | bool | Y | `0` = 出 / `1` = 入。**调拨两行靠它与 `warehouse_code` 区分** |
| `owner_l1` | string | Y | **四轴之一，缺失拒绝入账** |
| `owner_l2` | string | N | 内部管理维度，不进余额表主键、不进存货总额 |
| `batch_no` | string | N | 空 = 不按批次管理 |
| `qty` | decimal(18,4) | Y | 业务单位数量（展示用） |
| `unit` | string | Y | 业务单位 |
| `base_qty` | decimal(18,4) | Y | **基本单位数量，核算唯一口径** |
| `amount_ex_tax` | decimal(18,2) | Y | **入账基数**（不含税） |
| `tax_rate` | decimal(10,6) | N | 缺省 `0.13` |
| `tax_amount` | decimal(18,2) | N | |
| `allocated_cost` | decimal(18,2) | N | 分摊的运费 / 关税 / 其他费用（按 `t_cost_allocation_rule` 分摊） |
| `settle_status` | enum | N | **`ESTIMATED` / `SETTLED` / `ADJUSTED`**——暂估冲回的入口 |
| `estimate_ref_doc` | string | 条件 | 暂估引用单号 |
| `is_related_party` | bool | N | 决定合并抵消 |

> **两个最容易错的字段**：
> - **`base_qty` 才是核算口径**，`qty × unit` 只作展示。填反了数量对账永远差一笔。
> - **`amount_ex_tax` 才是入账基数**，含税金额绝不入成本——含税入成本会**同时虚增存货、少计进项税**（两个错一起犯）。

### 4.3 11 类单据的差异化字段

| `doc_type` | 中文名 | 方向 | 作价 | 出凭证 | 差异化必填字段 |
|---|---|---|---|---|---|
| `PO_IN` | 采购入库 | 入 | — | 是 | `supplier_code` `settle_status` |
| `PO_RET` | 采购退货 | 出 | — | 是 | **`orig_po_doc`**（必须可追溯原单） |
| `SO_OUT` | 销售出库 | 出 | — | 是 | `customer_code`；**出库成本由系统算，不采信传入成本** |
| `SO_RET` | 销售退货 | 入 | — | 是 | **`orig_so_doc`**（按原出库成本回冲，不重算） |
| `TRANSFER` | 调拨 | 双边 | — | 是 | `out_warehouse_code` `in_warehouse_code`；**调出调入必须同一 `owner_l1`** |
| `STOCKTAKE` | 盘点 | 双边 | — | 是 | `book_qty` `actual_qty`；差异**自动生盘盈/盘亏单** |
| `OTHER_IN` | 其他入库 | 入 | — | 是 | `reason` |
| `OTHER_OUT` | 其他出库 | 出 | — | 是 | `reason` |
| **`OWNER_TRANSFER`** | **一级货权转移** | 双边 | **必作价** | **是**（+ 抵消） | **`from_owner_l1` `to_owner_l1` `transfer_price` `price_source`** |
| `OWNER_REASSIGN` | 二级重分配 | 双边 | **必作价** | **否**（R2） | **`from_owner_l2` `to_owner_l2` `internal_price` `price_type`** |
| `PERIOD_ADJUST` | 期间补录 | 双边 | 按原类型 | 是 | `adjust_reason`；**一律按当期口径量价**；**必审** |

> **`doc_type` 数的是一张单据从哪来、是干什么的，不是数它动了几行。** 所以调拨**不设** `TRANSFER_OUT` / `TRANSFER_IN`——一张单两个 `doc_type` 值会让幂等键和作废逻辑全部失效。

### 4.4 调拨的落库展开规则（**必须实现，不是可选**）

业务侧推 **1 张单、2 个仓**；适配层展开为 **2 行**：

```
doc_no = TR-202601-0001
  line 1: warehouse_code=WH01(调出), is_in=0, line_no=1
  line 2: warehouse_code=WH03(调入), is_in=1, line_no=2
两行 doc_type 都是 TRANSFER，共用同一个 doc_no
```

**为什么不能拆成两张单**：① `doc_no` 唯一性会被破坏；② 传输幂等键 `batch_id + doc_no + line_no` 对不上，**重推即重复入账**。

**跨法人判定（在展开之前做）**：若调出仓与调入仓**不属于同一一级货主** → **拒绝并回执 `E-CROSS-LEGAL-ENTITY`**，要求改推 `OWNER_TRANSFER`。

> **不做「自动升级」**：自动升级等于**财务替业务定价**，而一级作价的权威源是交易数据。这条必须在 W1 会上与业务团队讲死。

### 4.5 作价字段（一级与二级的差别在这）

| 字段 | 一级 `OWNER_TRANSFER` | 二级 `OWNER_REASSIGN` |
|---|---|---|
| `transfer_price` | **必填**——**交易数据，不配置**，来自销售单/合同 | — |
| `internal_price` | — | **必填**——**政策数据**，取 `t_internal_price` 价目表 |
| `price_type` | — | `FIXED` / `MARKUP`，**行属性、不进主键** |
| `price_source` | Y | Y |
| `price_base` | N | **MARKUP 时必填** = 当时**该一级货主层**均价 |
| `markup_rate` | N | **MARKUP 时必填** |
| `price_value` | Y | Y——**实际取到的价（快照）** |

**取价三条铁律**：按**业务日期**取价 → 取到即**快照** → 调价**不追溯**。

**「一个价、三个数」**：`MARKUP` 时三个字段**都要落库**。只存 `price_value` 是不够的——日后无法回答"这个价怎么来的"。

```
MARKUP: price_base = 12.000000 · markup_rate = 0.1000000 · price_value = 13.200000
FIXED : price_base = null       · markup_rate = null       · price_value = 13.200000
```

**层级别取错**：`price_base` 取的是**一级货主层**均价。取到二级层，全错。

### 4.6 二级层的回传结构（**一个数量、两个金额**）

二级重分配回传时**两个金额必须成对出现**，且**口径标注不可省**：

| 字段 | 算法 | 能否加总回一级层 | 校验 |
|---|---|---|---|
| `alloc_amount` | `qty × 一级均价` | **能** | **硬校验**：`Σ alloc_amount = 一级层金额`，不平**整单回滚 + 告警** |
| `internal_amount` | 按 `internal_price` 累计 | **不能** | **不做等式校验** |
| `internal_pl` | `Σ internal_amount − Σ alloc_amount` | — | = 内部未实现毛利，**管理口径、非会计** |

> **对 `internal_amount` 做等式校验，是把管理口径当会计口径用——这是红线复发的一种形态。**
>
> **二级层金额绝不可加进存货总额**；业务侧展示「库存金额」**只能用存货口径那一行**。

## 5. 动作报文（`object = doc_action`）

改单与作废**不是单据模板**，是**动作**。两者都与单据共用同一套字段与幂等键。

| 动作 | `action` | 关键字段 | 处理规则 |
|---|---|---|---|
| **改单** | `CHANGE` | `doc_no` `line_no` `version_no` + 变更后的行字段 | 未核算 → 直接替换；**已核算 → 追加反向事件 + 新正向事件（`version_no + 1`）**；已锁账 → 拒绝 |
| **作废** | `VOID` | `doc_no` `void_reason` | `cost_status = PENDING` → 直接置 `VOID`，**不产生事件**；`CALCULATED` → **追加反向事件 + 红字凭证**；已锁账 → 拒绝 |

| `action` | 结果 |
|---|---|
| `CHANGE` | **原事件保留不删**；余额走 `balance += Σdelta`——**不是「删行重推」** |
| `VOID` | **原凭证不改**，新增 `is_red = 1` 的红字凭证；`red_flag = 1`、`red_ref_doc` 记录原单号 |

> **作废闸门 = `cost_status`，不是「有无下游引用」。** 这是最容易被实现成"看有没有被引用过"的一条——**那样会漏放**。
>
> **已核算的一律不可撤**，只能反向单 + 红字凭证。改单与作废**都不物理删除**任何历史事件。

## 7. 价值回传字段（财务 → 业务侧，`object = value_feedback`）

> 回传是**反向**的：财务库存中心是发送方，业务库存中心是接收方。目的是根治"双方各算一套成本"（红线三）。

| 指标 | 字段 | 口径标注 | 备注 |
|---|---|---|---|
| 库存金额（**存货口径**） | `inventory_amount_l1` | 一级货主层 · `is_internal = 1` | **对外唯一权威值** |
| 库存数量（权属口径） | `inventory_qty_l1` | 一级货主层 | 按法人归集的权属数量 |
| 库存数量（在库口径） | `inventory_qty_physical` | 物理层（仓库, 批次） | 与数量对账基准一致 |
| 成本单价 | `unit_cost` | 核算单元 `(物料, 仓库, 一级货主)` | 移动平均单价 |
| 库龄 | `stock_age_days` | `(物料, 仓库, 批次, 一级货主)` | 天数 |
| 跌价准备 | `provision_amount` | 一级货主层 · `is_internal = 1` | 仅内部货主计提 |
| 周转天数 | `turnover_days` | 一级货主层 | 管理指标 |
| **内部结算金额** | `internal_amount_l2` | **管理口径 · 非会计** | **必须与 `inventory_amount_l1` 成对出现** |
| **内部结算损益** | `internal_pl_l2` | **管理口径 · 非会计损益** | 同上 |

**强制约束（契约 v1.2 `§4.2` 象限② + `§6` 红线三）**：

- `internal_amount_l2` **必须与 `inventory_amount_l1` 同一条报文、同一个批次**出现，**禁止单独使用**
- 业务侧展示「库存金额」**只能用 `inventory_amount_l1`**
- **若不区分口径**，业务侧必然挑一个当"库存金额"——**红线三以新形式复发**，而且这次是"契约里写了、实现里没区分"

## 8. 适配层接口签名（**一期即实现，不是二期才留口**）

设计 `7.6` 预留的三个方法，**一期就落地**——API 对接是本期方式，不是未来方式。

```python
class InventoryDataAdapter(ABC):
    """协议无关边界：REST / MQ / 文件 三种绑定都实现它。"""

    @abstractmethod
    def pull_materials(self, since: datetime) -> list[Material]: ...

    @abstractmethod
    def pull_documents(self, since: datetime, doc_types: list[str]) -> list[Document]: ...

    @abstractmethod
    def pull_inventory_snapshot(self, as_of: date) -> list[InventorySnapshot]: ...

    @abstractmethod
    def receive(self, envelope: Envelope) -> Receipt:   # 推模式入口
        """接收报文信封，返回 §2.7 的错误回执。"""


# 一期实现 A：API 对接（主）
class BusinessApiAdapter(InventoryDataAdapter):
    """从业务库存中心 API 拉取 / 接收推送。协议待定，字段用本文。"""

# 一期实现 B：文件导入（保留的过渡与补录入口）
class FileAdapter(InventoryDataAdapter):
    """Excel/CSV。校验 / 幂等 / 错误回执与 A 共用同一套实现。"""
```

> **边界划在接口上，不划在功能上**（O-19 同一套路：审批流保留 `ApprovalGateway` + 一期单点直通实现）。
>
> **关键收益**：`FileAdapter` 与 `BusinessApiAdapter` **共用同一套校验、幂等、错误回执**。所以"先保留导入入口"**不会产生两套逻辑**，也不会在切换时出现口径漂移。
