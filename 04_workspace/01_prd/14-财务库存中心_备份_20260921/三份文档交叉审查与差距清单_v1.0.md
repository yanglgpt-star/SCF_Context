## 0. 怎么用这份清单

本清单回答的问题是：**这三份文档现在能不能作为开发基线？不能的话，差在哪、改成什么、谁来改、什么时候改完。**

每条发现的格式统一：

```
编号 → 严重度 → 类型 → 涉及文档与章节 → 问题（含证据）→ 修订建议 → 责任方 → 最晚时点
```

严重度按"不修就返工"划分，与《待决策清单》的优先级口径保持一致：

| 严重度 | 含义 | 时点 |
|---|---|---|
| **P0** | 直接决定算出来的数对不对 / 范围错、多干或少干 | W1 内闭环 |
| **P1** | 影响数据模型与核算引擎结构，改起来伤筋动骨 | 设计评审前（W1–W2） |
| **P2** | 影响实施、运维、可追溯性，不冲击核心模型 | 上线前 |

类型标签：`口径`（算法/会计口径矛盾）、`范围`（一期范围与正文不同步）、`模型`（数据模型缺字段/缺表）、`缺口`（应有而无的设计）、`治理`（职责与流程）、`文档`（文字与版本）。

**总体结论**：三份文档的架构决策是对的（适配层、核算引擎幂等、`t_calc_log` 的 before/after 快照），**没有一条修订需要动架构**；但存在 **9 条 P0**，其中 4 条会直接导致算错账或对不上账。范围表（`0.2`）与契约要求（v1.1）两条线都已领先于设计正文，需要一次性回灌。

## 2. P0 发现详述

### F01 · 入库金额含税/不含税两处公式矛盾

**严重度**：P0 ｜ **类型**：口径 ｜ **主责方**：财务部 ｜ **最晚**：W1

**证据**

- `详细设计文档 5.2` 入库公式写为：`new_amount = old_amount + in_amount + tax_amount`（税额计入存货成本）
- `详细设计文档 3.6.2 F5` 写为：`入库入账金额（库存科目）= 不含税金额`
- `详细设计文档 5.3` 入库场景表：采购入库"含税时单独记录税额"

三处对"入库进成本的到底是哪一笔钱"给出了两种答案。

**问题**：这是全系统最上游的一个数。入库金额错了，移动平均单价、出库成本、库存金额、跌价基数、凭证金额全部跟着错，且错误会沿时间轴累积。含税进成本还会虚增存货、少计进项税。

**修订建议**

1. 统一口径为：`入库入账金额 = 不含税金额 + 可计入存货成本的采购附加费用分摊额`（附加费用见 F09）。
2. 删除 `5.2` 公式中的 `+ tax_amount`；同步修正 `5.7` 伪代码。
3. 在 `3.6.2` 增加 F5b 明确：税额只进"应交税费—应交增值税(进项税额)"科目，不进入 `new_amount`。
4. 在 `5.3` 表内增加"入账金额口径"列，逐单据类型写明入账金额来源（采购=不含税+费用分摊；调拨=调出仓成本；其他入库=财务估价）。

**影响章节**：设计 5.2 / 5.3 / 5.7 / 3.6.2；凭证模板 8.1.1

### F02 · 舍入差异是否在入库发生

**严重度**：P0 ｜ **类型**：口径 ｜ **主责方**：财务部 ｜ **最晚**：W1

**证据**

- `3.6.2 F3` 与 `5.5` 均定义：舍入差异由**出库**结转产生（`out_amount - out_qty × current_price`），累计到 `rounding_diff_acc`，月末结转。
- 但 `5.7` 伪代码 `calc_on_inbound` 在入库时也计算 `rounding_diff`，并据此**回改库存金额**：

```
rounding_diff = round(new_amount - new_qty * new_unit_price, 2)
if rounding_diff != 0:
    new_amount = new_amount - rounding_diff   # 校正金额
```

**问题**：入库只做"单价舍入到 6 位"，不回改金额（金额本身是确定的入账数）；出库才产生"金额 2 位 vs 单价 6 位"的尾差。伪代码把两者混在一起，会凭空调整入库金额，破坏 F13 金额守恒。开发若照伪代码实现，月末核对必然对不上。

**修订建议**

1. 明确规则：**入库不改金额，只舍入单价；舍入差异仅在出库产生**。
2. 删除 `5.7` 伪代码中 `calc_on_inbound` 的 `rounding_diff` 校正分支（第 1098–1101 行），如需留痕则改为写 `t_calc_log` 的信息性记录，且**不回改 `new_amount`**。
3. 在 `3.6.2` 补一句边界说明：入库金额由业务价格与费用确定，属于"输入"，不允许被系统舍入改写。

**影响章节**：设计 5.5 / 5.7 / 3.6.2

### F03 · 采购入库凭证的贷方口径未定义

**严重度**：P0 ｜ **类型**：口径 ｜ **主责方**：财务部 ｜ **最晚**：W1

**证据**：`8.1.1` 采购入库凭证模板：

```
借：库存商品 / 原材料          [calc_amount]
借：应交税费 - 应交增值税(进项)  [tax_amount]
    贷：应付账款 / 预付账款 - 供应商    [inbound_amount]
```

`inbound_amount` 在 `3.6.2 F1`、`5.2`、`5.3`、`7.3` 中含义不一致（有时指含税、有时指不含税、有时是可配），凭证模板未定义它取哪个口径。

**问题**：若 `inbound_amount` 实为不含税，则借方合计（不含税 + 税）大于贷方，**凭证直接不平衡**，`3.5.4` 的平衡校验会中断导出。

**修订建议**

1. 凭证模板改为显式口径，消除歧义：

```
借：库存商品 / 原材料              [calc_amount]         （不含税 + 费用分摊）
借：应交税费 - 应交增值税(进项)      [tax_amount]
    贷：应付账款 / 预付账款 - 供应商  [calc_amount + tax_amount]
```

2. 在 `8.1` 章首增加一句总则：**所有凭证模板的金额口径以"借方合计 = 贷方合计"为唯一校验标准**，模板中不允许出现未定义口径的占位符。
3. 全章排查其余模板（8.1.2–8.1.7）是否存在同类占位符。

**影响章节**：设计 8.1.1；3.5.4 平衡校验

### F04 · 金额对账缺比对基准，且对账频次与契约冲突

**严重度**：P0 ｜ **类型**：口径 ｜ **主责方**：双方 ｜ **最晚**：W1

**证据**

- `契约 2.4`：库存数量快照"**是否给金额：建议不给**"，理由是业务侧金额口径与财务移动平均必然不同。
- `详细设计文档 3.5.5` 对账流程：`获取业务系统库存快照（数量 + 金额）`；`9.2` 设"金额对账"。
- `详细设计文档 3.2` 主流程 K 节点：`日常对账：数量/金额 vs 业务系统快照`。
- `契约 5` 节奏约定：`对账频次：数量：日清；金额：月结`。

若照契约执行（业务不给金额），设计的金额对账就没有 `biz_value` 可填，`t_reconcile_result` 的 `AMOUNT` 类型记录全部无法生成。

**问题**：这是契约原则与设计实现之间的正面冲突，必须两选一，不能默认。

**修订建议**

**推荐方案**：金额对账**不比对业务系统**，改为比对总账。

| 对账维度 | 比对对象 | 频次 | 基准 |
|---|---|---|---|
| 数量 | 业务库存中心快照 | 日清 | 业务快照（契约 2.4） |
| 金额 | 金蝶总账存货类科目余额 | 月结 | 财务账面 vs 总账 |

理由：`待决策清单 D-02` 已建议"本系统为唯一成本源、金蝶关闭存货核算"，金蝶总账仍是最终对外报表的依据，本系统库存科目余额必须与总账勾稽；业务侧并不持有可比的金额口径，用它做基准只会制造假差异。

配套修订：

1. `3.5.5` 流程拆分两条支路：数量对账（vs 业务快照）、金额对账（vs 金蝶总账）。
2. `3.2` 主流程 K 节点改为"数量日清 / 金额月结"，与契约 5 对齐。
3. `9.2` 明确"金额 = 数量 × 单位成本"是**系统内部核对口径**，不是对账基准。
4. `4.5.1 t_reconcile_result` 增加 `basis`（基准来源：`BIZ_SNAPSHOT` / `GL_BALANCE`）字段。

**影响章节**：设计 3.2 / 3.5.5 / 9.1 / 9.2 / 4.5.1；契约 2.4 / 5

### F06 · 一期范围表过期（跌价口径）

### F07 · 8 类单据未落地 + 凭证模板缺退货

**严重度**：P0 ｜ **类型**：范围 ｜ **主责方**：双方 ｜ **最晚**：W1

**证据**

- `契约 2.2` 明确业务必推 **8 类**单据，含 `PO_RET`（采购退货出库）、`SO_RET`（销售退货入库）。

2. `4.2.1` `doc_type` 枚举补齐 `PO_RET` / `SO_RET`。

8.1.8 采购退货出库（按当前移动平均价结转）
  借：应付账款 / 预付账款 - 供应商   [calc_amount + tax_amount]

### F09 · 采购附加费用无字段、无规则、无模板列

**严重度**：P0 ｜ **类型**：模型 ｜ **主责方**：双方 ｜ **最晚**：W1

**证据**

- `契约 2.3`：采购附加费用（运费、关税、报关费）"**最容易被漏掉的一项，直接决定入库成本**"，并建议"W1 就把'运费、关税是否计入存货成本、怎么分摊'谈死"。
- `契约 9.1` 采购入库字段表含"运费/关税 + 分摊方式"。
- `契约 4.2③` 将"采购附加费用的分摊规则"列为**共同定义**项。

| tariff_amount | DECIMAL(18,2) | 本行分摊的关税 |
| other_cost_amount | DECIMAL(18,2) | 其他可计入存货成本的费用 |
| allocated_cost | DECIMAL(18,2) | 分摊后计入本行入库成本的合计 |

### F05 · 库存余额粒度未定

**严重度**：P1 ｜ **类型**：模型 ｜ **主责方**：项目组 ｜ **最晚**：W2

**证据**

- `4.3.1 t_inventory_balance` 联合主键为 `(material_code, warehouse_code, batch_no)`，`batch_no` 为"为空表示非批次"。
- `5.1` 计价方法配置：每个 `(material_code, warehouse_code)` 组合对应一种计价方法；`0.2` 明确"移动平均（**按物料 + 仓库粒度配置**）"。
- `t_calc_log` 的 before/after 快照也是 `(qty, amount, unit_price)` 三元组，没有批次维度。

**问题**：单价按"物料+仓库"算，主键却含批次——那一个批次的余额金额怎么拆？两种可能都自相矛盾：

- 若每批次单独一行、共用同一单价 → 拆金额时必然产生多余舍入差异；
- 若每批次单独一行、各自有单价 → 那就是"批次个别计价"，与 `0.2` 的移动平均口径冲突，也与 `0.3`"个别计价是二期"的规划冲突。

**修订建议**（三选一，推荐 A）

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | 一期余额主键改为 `(material_code, warehouse_code)`；批次维度下沉到**入库分层表**（见 F17），只服务库龄与跌价 | 与 0.2/5.1/F1–F3 公式完全一致；批次成本留到二期 | 一期无法按批次结转成本（但 0.3 本就把个别计价列为二期） |
| B | 余额保留批次主键，每批次独立移动平均 | 批次成本一期就有 | 一期范围扩大，`t_batch` 必须启用，5.1/5.2/算例全部改粒度 |
| C | 按物料配置粒度（`is_batch_managed` 决定） | 最灵活 | 引擎复杂度 ×2，8 周内风险高 |

选 A 时需注意：`4.3.1` 移除 `batch_no` 主键后，`6.1` 库龄"按 (物料, 仓库, 批次) 计算"改为"按分层记录计算"，`F7` 从"无批次物料的估算方法"升级为**统一方法**（这反而简化了 §6）。

**影响章节**：设计 4.3.1 / 5.1 / 5.2 / 6.1 / 3.6.2；`t_calc_log` 不涉及

### F12 · 单据状态字段语义冲突

### F15 · `as_of` 日切时点未定义到单据与余额

**严重度**：P1 ｜ **类型**：口径 ｜ **主责方**：双方 ｜ **最晚**：W2

**证据**

- `契约 3`："日切时点 / 快照口径（as_of） | **B** | 双方约定 | 同一时点，不能各取各的 | 对账永远差一点"
- `契约 4.2③`："日切时点 `as_of` / 快照口径"为共同定义项。
- `契约 5`："日切时点 | 统一 T 日 23:59:59"。
- `详细设计文档 4.3.1` 有 `as_of_date` 字段（DATE 型），但**未定义它与业务日期、单据推送时间的关系**；`4.2.1` 的 `doc_date` 也未见与日切的换算或边界规则。

**问题**：同一天的边界单据（例如 23:59 与 00:01 各一笔）归入哪一天，直接决定日清对账是否能对上。B 级要求不是"知道就行"，而是要在表里能定位。

**修订建议**

1. 明确三时间的关系并在表中落地：

| 字段 | 含义 | 来源 |
|---|---|---|
| 业务日期 `doc_date` | 业务事实发生日，决定成本计算顺序与入账期间 | 业务（A 级） |
| 推送时间 `pushed_at` | 数据到达本系统的时间 | 适配层 |
| 日切 `as_of` | 对账与快照的统一时点，T 日 23:59:59 | 双方约定（B 级） |

2. `4.2.1` 增加 `pushed_at`；`4.3.1` 的 `as_of_date` 语义写清为"该余额记录对应的日切时点"。
3. `3.5.1` 导入流程中明确：推送时间晚于日切但业务日期在当日的，属**迟到单据**，按 `5` 契约的迟到规则插入重算，不计入当日快照。
4. `9.1` 数量对账明确基准 = 同一 `as_of` 的业务快照 vs 财务侧 `as_of_date` 余额。

**影响章节**：设计 4.2.1 / 4.3.1 / 3.5.1 / 9.1；契约 3 / 4.2③ / 5

### F19 · 暂估入库与发票冲回未建模

### F22 · 一期无会计期间锁账，月结"定稿"缺机制说明

**严重度**：P1 ｜ **类型**：治理 ｜ **主责方**：财务部 ｜ **最晚**：W2

**证据**

- `详细设计文档 5.6.5`：跨月单据处理中写"二期增加'会计期间'概念，按期间锁账"。
- `3.4.3` 注："一期未启用'会计期间锁账'，月结后仍允许反结账重算（PF8）；二期引入期间概念后……"
- `3.5.6` 月末结账流程末步为"月结报表定稿 + 归档 + 快照备份"。
- `待决策清单 D-10`：建议"上线日 = 开账日"；`D-01` 也依赖开账日与期间。

**问题**：一期有"月结定稿"这个动作，却没有期间边界。定稿之后若再插一张上月单据并触发重算（PF8 允许），"定稿"的报表就失效了——是重新定稿、还是留一份不一致的存档？文档没有回答。这不是要上一期锁账，而是**必须说明一期"定稿"的确切含义**，否则月结报表的法律效力与审计口径都悬空。

**修订建议**（推荐 A）

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 一期引入**轻量期间标记**：`t_document_line` 增加 `period`（`YYYY-MM`，由 `doc_date` 推导）；月结产出 `t_balance_snapshot` 按 period 落库；反结账重算时**强制冲销并重新出具该 period 快照**，快照保留历史版本（`snapshot_version`） |
| B | 一期不使用"定稿"表述，改为"月结报表（第 N 版）"，明示可重出，审计以最终版为准 |

两者都需在 `3.5.6` 补一句明确说明，并同步 `5.6.5` 的措辞（避免"一期没有期间概念"与"按期间出快照"打架）。

**影响章节**：设计 3.5.6 / 5.6.5 / 3.4.3 / 4.2.2；清单 D-01 / D-10
