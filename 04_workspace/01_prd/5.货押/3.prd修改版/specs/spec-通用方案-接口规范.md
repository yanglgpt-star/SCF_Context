# Spec：通用方案——接口规范

> **涉及端**：🔄 跨端（ERP/WMS/银行）


> **对应PRD**：PRD_通用方案_待确认事项补充.md（章节一、四、五）  
> **适用范围**：供应链金融平台全部模块

---

## 1. Goal（目标）

平台技术团队通过统一接口协议、标准化请求/响应格式和错误码体系，实现与核心企业ERP（8个接口）、银行核心系统（6个接口）、WMS仓储系统（6个接口）的标准化对接，确保全平台外部系统集成的一致性和可维护性。

---

## 2. Scope（边界）

### 本次包含
- ERP接口协议、8个接口定义、请求/响应格式、错误码体系、降级方案
- 银行核心系统对接模式、6个接口定义、放款指令格式、异常处理
- WMS系统对接模式、6个接口定义、入库数据格式

### 本次不包含
- 具体的数据库表结构设计
- 接口的性能压测指标和容量规划
- 各接口对应的UI页面和前端交互逻辑
- 银行端和ERP端内部系统的改造

---

## 3. I/O（输入输出）

### 3.1 ERP接口

#### 3.1.1 通用请求头

| 字段名 | 类型 | 长度 | 必填 | 校验规则 | 所属端 |
|--------|------|------|------|----------||--------|------|------|------|----------|--------|
| Authorization | string | ≤512 | 是 | Bearer {jwt_token}格式 | | ⚙️ 系统 |
| Content-Type | string | ≤64 | 是 | 固定值`application/json` | | ⚙️ 系统 |
| X-Request-ID | string | 36 | 是 | UUID格式 | | ⚙️ 系统 |
| X-Idempotency-Key | string | 36 | 是 | UUID格式，写入接口必填 | | ⚙️ 系统 |
| X-Timestamp | string | 10 | 是 | Unix时间戳，与服务器时间差≤300秒 | | ⚙️ 系统 |

#### 3.1.2 通用响应体

**成功响应**：
| 字段名 | 类型 | 长度 | 必填 | 说明 | 所属端 |
|--------|------|------|------|------||--------|------|------|------|------|--------|
| code | int | - | 是 | 200 | | ⚙️ 系统 |
| message | string | ≤128 | 是 | "success" | | ⚙️ 系统 |
| data | object | - | 否 | 业务数据 | | ⚙️ 系统 |
| request_id | string | 36 | 是 | 与请求头X-Request-ID一致 | | ⚙️ 系统 |

**错误响应**：
| 字段名 | 类型 | 长度 | 必填 | 说明 | 所属端 |
|--------|------|------|------|------||--------|------|------|------|------|--------|
| code | int | - | 是 | 错误码，如40001 | | ⚙️ 系统 |
| message | string | ≤256 | 是 | 错误描述 | | ⚙️ 系统 |
| data | null | - | 是 | 固定null | | ⚙️ 系统 |
| request_id | string | 36 | 是 | 与请求一致 | | ⚙️ 系统 |

#### 3.1.3 接口清单（8个）

| 接口名称 | 方法 | 路径 | 调用方向 | 幂等 |
|----------|------|------|----------|------|
| 推荐码验证 | GET | `/api/v1/dealer/verify` | 平台→ERP | 否 |
| 经销商数据查询 | GET | `/api/v1/dealer/{credit_code}` | 平台→ERP | 否 |
| 风险预警推送 | POST | `/api/v1/risk/alert` | ERP→平台 | 是 |
| 数据变更通知 | POST | `/api/v1/data/change` | ERP→平台 | 是 |
| 协同催收响应 | POST | `/api/v1/collection/response` | ERP→平台 | 是 |
| 回购邀请响应 | POST | `/api/v1/repurchase/response` | ERP→平台 | 是 |
| 分润明细查询 | GET | `/api/v1/settlement/detail` | ERP→平台 | 否 |
| 分润确认 | POST | `/api/v1/settlement/confirm` | ERP→平台 | 是 |

#### 3.1.4 错误码定义

| 错误码 | 含义 | 处理策略 |
|--------|------|----------|
| 200 | 成功 | - |
| 40001 | 推荐码无效 | 提示经销商联系核心企业获取新推荐码 |
| 40002 | 经销商不存在 | 驳回申请，提示核实企业信息 |
| 40003 | 请求参数错误 | 记录日志，提示技术排查 |
| 40101 | Token过期 | 自动刷新Token后重试 |
| 40102 | 签名验证失败 | 记录日志，触发告警，人工排查 |
| 40301 | 无权限访问 | 记录日志，联系核心企业确认权限配置 |
| 42901 | 请求频率超限 | 等待后重试 |
| 50001 | 核心企业系统内部错误 | 标记"待人工确认"，通知核心企业技术 |
| 50301 | 核心企业系统维护中 | 提示"系统维护"，降级为人工处理 |

### 3.3 银行接口

| 模式 | 适用场景 | 时效 | 优先级 |
|------|----------|------|--------|
| 银企直联API | 放款申请、还款通知、出库授权 | 实时 | 首选 |

#### 3.3.2 接口清单（6个）

| 接口名称 | 方向 | 用途 | 时效 |
|----------|------|------|------|

| 出库授权 | 银行→平台 | 确认还款后发送允许出库授权 | 实时 |

| dealer_bank | string | ≤256 | 是 | 开户行全称 | | 🏪 企业端-融资企业 / 🏦 银行端 |
| amount | decimal | (18,2) | 是 | >0 | | ⚙️ 系统 |
| currency | string | 3 | 是 | 固定值`CNY` | | ⚙️ 系统 |

| callback_url | string | ≤512 | 是 | HTTPS URL | | ⚙️ 系统 |

#### 3.3.4 异常响应

| 异常场景 | 银行返回标识 | 平台处理 |
|----------|-------------|----------|
| 放款失败（账户异常） | `ACCOUNT_INVALID` | 通知客户经理联系客户核实，可重新发起 |
| 放款失败（余额不足） | `BALANCE_INSUFFICIENT` | 通知财务调拨资金，重新发起 |
| 银行系统维护 | `SYSTEM_MAINTENANCE` | 排队等待，维护结束后自动重试 |
| 重复放款（幂等失败） | `ALREADY_PROCESSED` | 查询确认状态，不重复扣款 |

### 3.4 状态覆盖矩阵

| 场景 | 成功 | 失败 | 网络异常 | 空状态 |
|------|------|------|----------|--------|
| ERP推荐码验证 | code=200+data | code=40001/40002 | 重试3次后标记"待人工确认" | data=null |
| WMS入库推送 | HTTP 200 | HTTP 4xx/5xx+记录告警 | 重试3次后入死信队列 | goods=[]时拒收 |
| 银行放款申请 | 银行返回成功 | 按异常类型分发处理 | 标记"放款中"，定时查询 | 金额≤0时前置拦截 |

## 4. Constraints（约束）

### 技术约束
- 所有接口必须使用HTTPS，禁用HTTP
- ERP接口签名算法固定为HMAC-SHA256，密钥双向预置
- WMS接口路径必须以`/api/wms/`为前缀，不可混用ERP路径前缀
- 所有写入接口必须携带幂等键，服务端需实现幂等校验
- Token有效期2小时，需实现自动刷新机制
- 连接超时5秒，读取超时10秒

### 安全约束
- JWT Token需包含scope权限声明，最小权限原则
- 银行接口涉及资金操作，必须通过专线VPN或双向证书认证
- 请求头X-Timestamp与服务器时间差超过300秒视为重放攻击，直接拒绝
- 敏感字段（账号、证件号）在日志中必须脱敏

### 设计约束
- 错误码体系全平台统一，不允许各模块自定义冲突码段
- 响应格式必须包含request_id，便于全链路追踪
- 网络异常必须实现指数退避重试（2s/4s/8s），避免雪崩

## 5. Acceptance Criteria（验收标准）

1. **打开Postman，调用ERP推荐码验证接口`GET /api/v1/dealer/verify`**：携带有效JWT和X-Idempotency-Key，返回code=200且data包含dealer信息；携带过期Token，返回code=40101且自动刷新后重试成功。
2. **调用WMS入库推送接口`POST /api/wms/inbound`**：发送符合格式的入库数据，平台返回HTTP 200且库存数据在5秒内更新；发送重复inbound_no，平台返回"已处理"不重复入库。
3. **调用银行放款申请接口**：发送合规放款指令，银行返回成功，平台融资单状态变为"放款成功"；发送金额为0的指令，平台前置拦截返回参数错误，不向银行发送。
4. **断开ERP网络连接后调用经销商数据查询**：平台自动重试3次（间隔2s/4s/8s），最终标记"数据过期"并使用7天内缓存数据，运营端显示"数据过期"标识。
5. **使用错误X-Timestamp（偏差600秒）调用任意接口**：平台返回403/签名验证失败，且触发告警通知管理员，不执行业务逻辑。
6. **调用WMS出库指令下发`POST /api/wms/release`**：企业处于"冻结"状态时，平台拦截返回"企业状态异常，禁止出库"，不下发指令至WMS。

## 6. Non-Goals（非目标）

- ❌ 不实现ERP/WMS/银行接口的Mock服务器（由测试团队另行搭建）
- ❌ 不实现接口级别的限流熔断框架（复用公司统一网关能力）
- ❌ 不实现接口文档的自动生成和在线调试页面
- ❌ 不实现银行端UAT环境的搭建和维护
- ❌ 不实现WMS厂商的定制开发（仅提供标准接口规范，由仓储方适配）
