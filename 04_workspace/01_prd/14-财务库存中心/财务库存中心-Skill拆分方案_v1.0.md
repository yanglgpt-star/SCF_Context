# 财务库存中心 · Skill 拆分方案 v1.0

> **本文是什么**：把财务库存中心这条线上**反复发生**的工作流，拆成 Claude Code Skill 的方案。**只做分析、不落地**——确认后按 §七 顺序执行。
>
> **一句话结论**：**5 个专属 Skill + 1 份常驻约束底座（不是 Skill）+ 1 个可选通用 Skill**；分层为「底座 → 只读核对 → 授权改写 → 交付产出」。

---

## 一、为什么现在值得拆

这条线上已经有 **32 份 md**（需求文档原文 / 通俗版 / 计算逻辑分册 / 计算示例 / 两份整体 PRD / 详细设计 / 原型说明 / 方案文档 / 各类核对清单…）、**1 份 632 KB 的 16 页原型 HTML**、**3 个生成/校验脚本**，而且**口径已经走到第二代**（二级层「一个数量、三个金额」）。

与此同时，全部这些约定**只活在项目记忆里**（716 行），不在仓库的任何一份 CLAUDE.md 里（`find` 结果：全仓只有 `01_agents/`、`96-磁力贴搭建/pc/` 下 4 份，与本项目无关）。

**这正是该做 skill 的信号**：知识已经沉淀成型，但载体是对话记忆，换一个会话、换一个人就丢。

## 二、判断依据：拆 skill 的三条判据

一个新 skill 值得建，要同时满足：

| 判据 | 说明 |
|---|---|
| **频次高** | 反复发生，不是一次性交付 |
| **非显然约定多** | 不看就会做错，且**错法不直观**（不是"忘了格式化"那种一眼能看出的错） |
| **有明确触发词** | 能靠 `description` 命中，否则永远不被调起 |

拿这三条量这张表——**项目记忆里绝大部分内容是约束、权威层级、先例和「已报未改」清单**，说明这个领域的贵处不在「怎么写」，而在**「什么能动、谁先谁后、什么绝不能碰」**：

| 工作流 | 频次 | 非显然约定 | 风险 | 结论 |
|---|---|---|---|---|
| 多文档一致性核对 / 差距清单 | 高 | 高（权威层级、易分歧点） | **低**（只读） | ★★★ 建 |
| 跨文档口径传播 | 中 | 高（授权门禁、不动清单） | **高**（批量改文件） | ★★★ 建 |
| 原型 HTML 精改 | 高 | 高（浮层层次 / 抽屉 / `td` 禁令 / 令牌源） | 中 | ★★★ 建 |
| 核算口径与算例 | 中 | 极高（三金额、对平、池化差异） | 中 | ★★★ 建 |
| 文档本地化 / 术语与维度名统一 | 中 | 高（**范围界定**本身易错） | 低 | ★★ 建（可并入上者） |
| 阅读版生成（md → HTML） | 中 | 低（已有母本脚本） | 无 | ★★ 通用 skill |

## 三、底座：`14-财务库存中心/CLAUDE.md`（**不是** skill）

**为什么不做成 skill**：skill 是**按 `description` 触发**的，可能不进上下文；而门禁规则必须**无条件常驻**——「字段层冻结」「跨文档传播要单独授权」这类规则，恰恰在模型最想顺手改东西的那一刻最不能被漏掉。

底座要装的内容（10 条）：

1. **权威层级**：`财务库存中心（一期）需求文档 1.0（原型页面与核算引擎）.md` 是**唯一权威规格与原型管线源**；口径冲突**一律以它为准**。
2. **字段层默认冻结**；解冻需**单独授权**。
3. **跨文档传播需单独授权**——先报告、停下、等授权，再动手。
4. **命名禁令**：正文不写裸 `MA` / `SI` / `FIFO`（一律中文全称）；原型 HTML 的 `tbody td` **不许出现英文码**（码只进 `title`）；「二级货主」是**已废弃称谓**（但既有对象名如 `t_owner_allocation` 不改）。
5. **交付文档里英文字段 / 枚举 / 错误码都要带中文说明**，每个出现处都加，不必等用户提。
6. **界面定死一态**，不做系统主题跟随。
7. **维度名全页统一**：一级 = 「一级货主」、二级 = 「二级产权人」。
8. **不动清单**：详细设计文档的 changelog、方案文档的历史决策表、markdownlint 的 `MD038`/`MD037` 等告警——**故意不修**。
9. **不提交 commit**。
10. **方案类交付物写成仓库内 md 文件**，不只在对话里输出。

## 四、5 个专属 skill

### S1 `fin-consistency-audit` — 多文档一致性核对（**只读**）

- **触发**：「核对」「一致性」「交叉审查」「差距清单」「反向核对」「有没有冲突」「对不上」
- **做什么**：读 N 份文档 → 按权威层级逐项比 → 输出**分歧清单**（`文件:行` + 现值 + 应然值 + 依据）→ **只报告，不改任何文件**
- **references**：权威层级图、文档清单与各自角色（哪份是源、哪份是派生、哪份是历史版）、**易分歧点清单**（金额口径 / 小数位 / 单据号前缀 / 维度名 / 页签列数 / 字段层级）
- **为什么值**：频次最高、零风险可随时跑；而「谁是权威」这件事每次都要重新推一遍

### S2 `fin-cross-doc-sync` — 授权后的跨文档口径同步（**写·高风险**）

- **触发**：「同步到全部文档」「传播」「统一改成」「按 PRD 改原型」「批量改」
- **做什么**：**先出变更清单 → 停下等用户单独授权 → 备份 → 逐份改 → 校验零外溢 → 报告**
- **关键约束**：授权是**一次性的、不继承**；遵守 §三 第 8 条不动清单；改完必须 `git status` 确认零外溢
- **为什么与 S1 分开**：**两者风险相反**。S1 可以随便跑，S2 必须停下。合成一个，模型会从「报告」滑向「顺手改」——而这正是本项目最贵的一类事故

### S3 `fin-prototype-edit` — 原型 HTML 精改（**写**）

- **触发**：「改原型」「P01–P16」「原型页面」「规格抽屉」「浮层」「加列」「加字段」
- **做什么**：**手工精改**（`/tmp/reqdoc/` 的 Python 管线**已丢失**，不能再指望脚本重跑）→ 改完跑 `build_proto_doc.py` 重出阅读版
- **references**：16 页清单 + 6 组侧栏、**四层浮层** `dw`/`pw`/`mw`/`fw`、`tbl--spec` 规格抽屉与文档逐列对齐、HTML 令牌源**只认** `PC端界面.html`、`tbody td` 禁令

### S4 `fin-calc-example` — 核算口径与算例（**写**）

- **触发**：「算例」「计算示例」「逐笔推导」「三金额」「对平验算」「池化差异」
- **做什么**：三金额口径（`alloc_amount` 二级分摊金额**参与对平** / `internal_amount` 二级内部结算金额**不参与对平** / `own_amount` 二级自有结存金额**绝不加总进存货**）、统一表格模板、逐笔推导、对平 `V1`/`V2`/`V3`/`M1`/`M2`/`M3`/`E-11`/`E-12`/`E-13`、池化差异 `D` **按起点实算、不预设 0**
- **references**：三种计价方法（移动加权平均 / 个别计价 / 先入先出法）、**内部结算价只给转入方定价**（否则 `internal_amount` 恒等于 `alloc_amount`）、池化差异 `D` 的唯一样例指针

### S5 `fin-doc-localize` — 交付文档本地化与术语统一（**写·低风险**）

- **触发**：「中文化」「表与字段中文版」「去掉英文」「术语统一」「维度名统一」
- **做什么**：**先界定范围**（换什么、留什么）→ 首现括注原码 → 词典来源与权威顺序 → 废弃称谓处理
- **为什么单列**：**「范围界定」本身就是最容易做错的一步**——本项目刚发生过一次返工（先做「全中文版」，用户随即收窄为「只是表和表的字段用中文替代」）
- ⚠️ **这是五个里最弱的一个**：若你要的是 4 个而不是 5 个，**S5 并入 S2**（两者都是「授权后批量改文档」），代价是丢一个很准的触发词

## 六、为什么不这样拆

| 不这么做 | 原因 |
|---|---|
| ❌ 按**文档类型**拆（需求文档 skill / 详细设计 skill / 通俗版 skill…） | 会拆出 8–10 个高度相似、`description` **互相抢触发**的 skill |
| ❌ 做一个「财务库存大全」skill | `description` 太宽，**永远命中不准** |
| ❌ 给已有的**需求分析 / PRD 撰写 / SQL 检查 / PC Demo** 再包一层 | 这 4 个通用 skill 已存在，本项目只是消费者，再包一层会**双触发** |
| ❌ 把 **S1 / S2 合并** | 见 §四 S2 条 |

## 七、落地顺序

1. **底座 `CLAUDE.md`** —— 零风险，立刻生效，且是其余 5 个的前提
2. **S1 一致性核对** —— 只读、零风险，当天可用
3. **S3 原型精改 + S4 算例与口径** —— 高频写操作，收益最大
4. **S2 跨文档同步 + S5 本地化** —— 低频写操作，风险最高，放最后
5. 可选：**`doc-reader-build`**

## 八、要你拍板的 4 件事

1. **单一真源**：`01_agents/.claude/skills/` 与 `01_agents/pm_agent/.claude/skills/` 里**各有一份**现有 4 个 skill 的副本。新 skill 放哪一份？还是先把这三处**收敛成一份**？（不收敛，将来必然三处漂移）
2. **放哪个位置**：`.claude/skills/`（仓库内、随 git 走）还是 `~/.claude/skills`（个人级、跨项目）？—— 建议**通用放用户级、专属放仓库级**（`settings.json` 的 `chat.agentSkillsLocations` 两处都已收录）
3. **底座形态**：我建议 `CLAUDE.md`（无条件常驻）；若你希望它也走触发式，可改成一个 `fin-guardrails` skill——**但我不推荐**。
4. **是否真的落地**：本方案只分析不落地。确认后我按 §七 顺序做，**每做完一个给你验一个**。
