# 计价方式优先级判断规则 · 口径核对清单 v1.0

> **本文是什么**：把一份 **12 级「计价方式优先级判断规则」** 表逐条对到原文与 P01 计价模型配置的现有口径上，指出哪里一致、哪里是扩维、哪里是冲突、哪里是表自身的空洞。
>
> **权威关系**：以原文 `财务库存中心（一期）需求文档 1.0（原型页面与核算引擎）.md`（下称「原文」）为准；详细设计文档是 schema 权威来源之一。**本文只核对、不改任何文件**，所有改动建议集中在 §七，**须单独授权**（`CLAUDE.md` §2.2）。
>
> **一句话结论**：这份 12 级表在原文里**没有对应物**——原文只有一句 5 级散文链、**不含货主维度**；表本身还**漏掉了原文明确存在的「仓库」一级**；并且它把「业务类型」抬成路由维度，与原文「核算单元 = 商品 × 仓库 × 一级货主」**结构性冲突**。

## 二、逐级对照

「原文 5 级链」= 原文 `:619` 那一句：

> 路由匹配优先级：**特定 SKU → 仓库 + 品类 → 商品品类 → 仓库 → 全局默认（移动加权平均）**

| 级 | 用户表组合 | 原文链里有吗 | 判定 |
|---|---|---|---|
| 1 | 货主 + 仓库 + 业务类型 + SKU（品类不参与） | 部分——只有「特定 SKU」一级，**无货主、无业务类型** | 🟡 扩维（同轮违反 §3.1） |
| 2 | 货主 + 仓库 + 业务类型 + 品类 | 部分——对应「仓库 + 品类」，**无货主、无业务类型** | 🟡 扩维 |
| 3 | 货主 + 仓库 + SKU（业务类型空、品类空） | 部分——对应「特定 SKU」 | 🟡 扩维 |
| 4 | 货主 + 仓库 + 品类 | ✅ 对应「仓库 + 品类」，加了货主 | 🟡 加维 |
| 5 | 货主 + 业务类型 + SKU | ❌ 原文无业务类型维度 | 🆕 纯新增 |
| 6 | 货主 + 业务类型 + 品类 | ❌ 同上 | 🆕 纯新增 |
| 7 | 货主 + SKU | 部分——对应「特定 SKU」 | 🟡 扩维 |
| 8 | 货主 + 品类 | ✅ 对应「商品品类」，加了货主 | 🟡 加维 |
| 9 | 货主兜底（其余全空） | ❌ 原文链里没有货主维度 | 🆕 纯新增 |
| — | **货主 + 仓库（其余全空）** | ✅ 原文**明确有「仓库」这一级** | 🔴 **用户表漏了** |
| 10 | 全局 SKU（货主空） | 部分——「特定 SKU」本身就可货主为空 | 🟡 但是被降级（见 §3.4） |
| 11 | 全局品类（货主空） | 部分——「商品品类」可货主为空 | 🟡 但被降级 |
| 12 | 全局兜底（全空） | ✅ 完全一致 | ✅ |

**覆盖率**：原文 5 级链中，用户表覆盖了 **4 级**（特定 SKU / 仓库+品类 / 商品品类 / 全局默认），**漏了「仓库」**；另新增 8 个原文没有的层级。

## 三、🔴 真分歧

### 3.1 业务类型无法切分核算单元（结构性，最严重）

| | 内容 |
|---|---|
| **用户表** | 第 1/2/5/6 级把 `biz_type`（业务类型：自营 / 代销 / 代采 / 寄售）作为**计价方法的路由维度** |
| **原文** | 核算单元 = `(商品, 仓库, 一级货主)`（`:50`、`:67`、`:343`）；详细设计 `4.1.6` 与 `5.1` 更明确：**均值池、余额、凭证、跌价基数全部建在核算单元上**。`biz_type` 只是 P01 规则的**适用范围字段**，原文 `:626` 写「本规则适用的业务类型，非必填……空代表全部」，**从未说它能切分核算单元** |
| **冲突点** | 同一 SKU 放在同一仓库、归属同一货主，同时发生自营入库与代销入库 → 两张单据落在**同一个均价池**里。按用户表，自营行走第 1 级、代销行走第 1 级，若两条规则配了不同方法，**同一个均价池就要挂两种方法**——无解 |
| **补充** | 项目记忆里也记着 `biz_type`「进了搜索条件 + 列表列 + 两个表单抽屉、**未进路由**」——用户表正是把它推进了路由 |
| **两条出路** | ① **不动字段层**：把 `biz_type` 从路由维度降回「规则适用范围」（只用于筛选与展示），12 级表缩成不带业务类型的版本；② **解冻字段层**：把业务类型加进核算单元键 → 等于把核算单元改成四轴，**牵动均值池、余额表主键、凭证、跌价基数、全部报表**（`CLAUDE.md` §2.1，须单独授权） |

### 3.2 「仓库」级被漏掉

原文 `:619` 的 5 级链里，**「仓库」是独立一级**（第 4 级，比「商品品类」更粗、比「全局默认」更细）。用户表从第 8 级「货主 + 品类」直接跳到第 9 级「货主兜底」，**中间没有「货主 + 仓库」**。

后果：财务想配一条「仅限某货主在某仓库统一用某方法、不区分品类与 SKU」的规则时，**12 级表里没有任何一级能接住它**。这条规则在原文是合法的，在用户表里无处安放。

### 3.3 `货主 + 仓库 + 业务类型` 是孤儿组合

逐级验证：

- 第 1 级要 SKU，第 2 级要品类 → 不匹配；
- 第 3 级要求业务类型为空 → 不匹配；
- 第 4 级要求业务类型为空 → 不匹配；
- 第 5/6 级要求仓库为空 → 不匹配；
- 第 9 级要求「其余全部为空」→ 仓库与业务类型都不空 → 不匹配。

**结论：`货主 + 仓库 + 业务类型`（不指定 SKU、不指定品类）无级可落。** 这和第 3.2 条是同一类问题——表的组合展开不完整。

### 3.4 「特定 SKU 优先级最高」被反转

| 位置 | 现文 |
|---|---|
| 原文 `:619` | 路由链**以「特定 SKU」打头** |
| 原型说明 `:125` | 「填了就只对该 SKU 生效，**优先级最高**」 |
| 用户表 | 「特定 SKU」因货主是否为空被拆成两级——第 7 级（货主 + SKU）与第 10 级（全局 SKU）；**第 9 级「货主兜底」压在第 10 级之上** |

后果：一条「只填了 `sku_code`、没填货主」的规则，在原文里是**最高优先级**，在用户表里**输给一条只填了货主的兜底规则**。这不是细节差异，是同一份配置在两种口径下选出**不同方法**。

> 若要保留用户表，就必须同步改掉原文与原型说明里「特定 SKU 优先级最高」这句——不能两句话同时成立。

### 3.5 `priority` 的语义：固定阶梯 vs 人工拖拽

| 依据 | 说的是什么 |
|---|---|
| 原文 `:607` / `:612` | `priority`（优先级）支持**鼠标拖拽**、`[上移/下移]`、`[保存优先级重排]`——是**财务可自由调整的顺序** |
| 原文 `:373` | `priority` 是**路由排序键**，数值越小越优先 |
| 原文 `:619` | 同时又写着一条**固定的** 5 级颗粒度链 |

**原文自身已经互斥**：如果顺序可随意拖，那「颗粒度决定优先级」就不成立；如果颗粒度决定优先级，那拖拽就只剩「同级别内部排序」的作用。

用户表把顺序**完全固定为 12 级阶梯**，实际上选择了「颗粒度决定优先级」这一侧。那么原文 `:607` / `:612` 的拖拽交互、`:373` 的「不留断号」规则都要重写——**这是 12 级表落地的前置条件，不是可选项**。

### 3.6 原文内部有两套计价配置模型

| | **模型 A · 核算单元配置表** | **模型 B · 规则表** |
|---|---|---|
| 表名 | `t_price_method_config`（计价方法配置表） | `cfg_inventory_pricing_rule`（计价模型配置表） |
| 键 | 联合主键 `(物料, 仓库, 一级货主)` | `rule_code`（规则编码）+ `priority`（优先级） |
| 维度 | 只有三轴，**无品类、无业务类型、无 SKU 规则** | 五个可选范围列：货主 / 仓库 / 品类 / SKU / 业务类型 |
| 选方法的方式 | **直接按核算单元查一行**，查不到 → 全局默认移动加权平均 + 告警 | **按优先级匹配规则** |
| 出处 | 原文 `:67`、`:343`、`:1579`；详细设计 `4.1.6`、`5.1`；skill `fin-valuation` | 原文 P01 `:619-630`；原型说明 P01；通俗版；两份 PRD |

**用户这份 12 级表只能落在模型 B 上**——模型 A 的键里根本没有品类、SKU、业务类型。

而 `财务库存中心（一期）菜单取数分析_v1.0.md` `:76` 又给了**第三种读法**：`t_price_method_config` 是权威取价来源，`cfg_inventory_pricing_rule` **只在核算单元无配置时兜底**。同一件事三种说法，必须择一写死。

> 另：该文件 `:256` / `:321` 已记录 `cfg_inventory_pricing_rule` **在详细设计里没有表结构**——12 级表若要落地，第一件事是补这张表的 schema。

### 3.7 「同类存货方法须一致」与单品级规则冲突

原文 `:345` 与 `:2207`：

> 同类存货的计价方法**须一致**，变更须披露；切换**只对新商品类别自开账日启用，不对存量品类中途切换**。

用户表第 1 级「极特殊单品」（货主 + 仓库 + 业务类型 + SKU）与第 7 级「货主 + SKU」，都允许**同一品类下的不同 SKU 落到不同方法**。这与「同类存货一致」字面冲突。

> 原文这两条本身也有张力：配置粒度是 SKU 级，一致性要求却是品类级——原文**没有定义「同类」的边界**（是品类？是物料类别？）。12 级表要落地，得先把这个词定死。

## 五、用户表新增、原文缺失且有价值的部分

这几条**建议吸收进原文**（属 §七 授权范围）：

1. **把散文链展开成组合矩阵**。原文只有一句「A → B → C」的散文链，**从未定义多列同时非空时怎么比**；12 级表给出了逐组合的空/非空语义。
2. **明确「SKU 出现时品类不参与匹配」**。原文没有这句——`category_name` 与 `sku_code` 同时填值时的行为是空白。
3. **显式排除若干组合**。`仓库 + 业务类型`、`品类 + 业务类型`、`仓库 + 品类 + 业务类型` 都不设级——原文没有说明为何不设。
4. **全局 SKU 的禁用条件**：「只要有一个货主此 SKU 计价不同，则禁止使用」——原文无此约束，这是一条**实质性的治理规则**。
5. **把定制段（1–9）与全局段（10–12）分开**。原文的 5 级链把「特定 SKU」与「全局默认」混在一条链上，没有分层语义。
