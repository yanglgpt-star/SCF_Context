# 财务库存中心 · 企业级 Skill 拆分方案 v1.0

> **本文是什么**：假设财务库存中心**本身变成一个 AI 项目**——上线后的日常与月结工作**由 skill 承载**，人（和 agent）照着 skill 干活。本文是**拆 skill 的方案，只分析、不落地**。
>
> **一句话结论**：**4 层**（底座 → 编排 → 岗位 → 能力），落地为 **2 条编排 + 3 个岗位 skill**（合起来 **5 个新 skill**）；**已有 10 个 `fin-*` skill 全部留用**——其中 5 个规则 skill **正是现成的「能力层」**，不用重做，只需重新定位。

**与另两份方案的分野**（三个轴，别混）：

| 方案 | 拆的是 | 受众 | 判据 |
|---|---|---|---|
| `财务库存中心-工作流Skill拆分方案_v1.0.md`（五十五） | **改文档**的工作流 | 文档工程师 | 频次 / 非显然约定 / 触发词 |
| `财务库存中心-功能Skill拆分方案_v1.0.md`（五十六） | **产品有什么规则** | 写文档 / 写代码的人 | 规则密度 |
| **本文** | **上线后谁在什么时候做什么、做完怎么算对** | 财务 / 运维 / agent | **时点 × 岗位 × 闭环 × 可自证** |

## 一、轴变了：前两轮交付「知识」，这一轮交付「班次」

前两轮的产物是**给人读的知识**——「计价方法是这么回事」「负库存是这么闭环的」。换个人、换个会话，读完就懂了。

**企业级不一样**：一个会计系统上线后，真正的痛点不是「不懂规则」，而是**「这个月的账谁来结、什么时候结、结错了怎么退、结对了拿什么证明」**。规则早就写在原文里了，缺的是**班次表**。

所以拆分的轴必须换：

| 维度 | 文档 skill（前两轮） | 企业级 skill（本轮） |
|---|---|---|
| 触发 | 关键词命中（用户说「算例」） | **日历 / 事件**（今天是月末、挂账表有 `OPEN` 记录） |
| 主体 | 谁问都一样 | **绑定岗位**（核算会计 / 财务主管 / 系统管理员） |
| 前置 | 无 | **闸门**（期间未锁账？上月日清过了吗？数据接齐了吗？） |
| 产物 | 一份 md | **报表 / 凭证 / 挂账状态 / 审计日志** |
| 结束条件 | 写完 | **自证通过**（守恒式平了）才算完 |
| 出错 | 改文件 | **有例外路径**（回滚 / 补单 / 上报），且**必须留痕** |

**一句话：文档 skill 的产出是「理解」，企业级 skill 的产出是「一次可审计的执行」。**

## 二、一条关键判断：能被代码强制的，不要写进 skill

这是本方案最重要的一条，先说。

原文里已经有一整套**硬不变量**——它们不是"建议"，是"不平就是错"：

| 不变量 | 含义 | 在哪 |
|---|---|---|
| **F12** | 数量守恒：期末数量 = 期初 + 入库 − 出库 | 原文 `§二` |
| **F13** | 金额守恒：期末金额 = 期初 + 入库 − 出库 + 成本调整 | 原文 `§二` |
| **V1 / V2 / V3** | 三个维度的数量 / 一级层金额 / 二级分摊金额对平 | 原文 `§一.5.2` |
| **M1 / M3** | 管理口径：`Σ own_amount + D = 一级层金额` | 原文 `§一.5.2` |
| **E-11 / E-12 / E-13** | 引擎出口硬校验 | 详细设计 `9.3` / `9.4` |

⚠️ **这些绝不能做成 skill 里的一句「请检查是否平」**。企业级最大的伪落地，就是**把内控寄托在 LLM 的自觉上**——模型今天心情好就查、token 不够就跳过，而账错了是不可逆的。

**正确的分工**：

| 性质 | 载体 | 例子 |
|---|---|---|
| **硬不变量**（平不平、守恒不守恒） | **系统**（数据库约束 / 服务端断言 / 引擎出口校验） | F12 / F13 / V1–V3 / `E-NEGATIVE-QTY`（负库存错误码） |
| **判断**（规则有分支、要看法条） | **skill** | 这笔算「漏了」还是「结错了」；跌价该不该下钻到一级货主 |
| **编排**（先做什么后做什么、什么能并行） | **skill** | 月结 8 步的顺序与审批点 |
| **例外处置**（校验不过怎么办） | **skill** | 对账不平的分诊树、挂账逾期怎么催 |

**判据**：**一个规则如果能用一行 SQL 表达，它就不该是 skill 的一部分。** skill 只承载 SQL 表达不了的东西。

> 这条直接决定了后面所有 skill 都会变小——因为一半内容被推回系统了。**这是好事**。

> ⚠️ **过渡期例外（2026-10-13 定）**：仓外实现审计发现**两边都没有可运行的核算引擎**（16 项能力已实现 0 项，见 §十）。所以一期**不等待系统**——硬不变量**先放进 skill 的检查步骤**。但必须**显式标注为过渡性技术债**，并写清**下沉条件**。**否则临时措施会变成永久措施**——那才是真正的风险。

## 三、四层结构（不是一个平面清单）

「工作流程都根据 skill 来做」这句话，字面意思就是**要有编排**。所以不能像前两轮那样列一个平铺清单，得分层：

```
L0  底座          CLAUDE.md（常驻）       口径 · 权限矩阵 · 闸门定义 · 禁令
     │
L1  编排层        2 条 runbook            按日历触发，串起下面所有能力
     │  ├─ fin-daily-ops    日清（每日）
     │  └─ fin-month-close  月结（每月）
     │
L2  岗位层        3 个动作闭环            按事件触发，一个闭环一件事
     │  ├─ fin-negative-ops   负库存处置（异常）
     │  ├─ fin-period-adjust  跨期处置（异常·必审）
     │  └─ fin-config-ops     配置变更（低频·高权限）
     │
L3  能力层        现有 5 个规则 skill     被上面引用，**不直接触发**
        fin-valuation / fin-owner-pricing / fin-negative-stock
        fin-provision / fin-period-close
```

**为什么 L1 与 L2 要分开**：月结**不是一件事**，是 8 件事串起来的流水线，中间夹着两个人工审批点。把它写成"月结 skill"会变成一个巨物；把它拆成 8 个 skill 又会失去顺序和闸门。**编排层就是那个"顺序 + 闸门"的载体**。

**为什么 L3 不直接触发**：没人会"主动想跑一次 fin-valuation"。它只在**日清发现异常**或**月结算跌价**时被引用。直接暴露给用户只会造成误触发。

## 四、L1 编排层：两条 runbook

### 4.1 `fin-daily-ops` 日清岗（每日）

| 项 | 内容 |
|---|---|
| **时点** | 每日（建议业务日次日晨） |
| **谁** | 数据运维 / 核算会计 |
| **前置闸门** | 昨日日清已完成；本月未锁账 |
| **动作** | ① **接入巡查**——到位率 / 失败单据重试过账 ② **日清数量对账**（F12 日粒度）③ **异常池分诊**——负库存挂账 / 对账不平 / 成本波动超阈值 |
| **产物** | 日清报告 + **异常工单**（分诊到人） |
| **自证** | F12 数量守恒（日粒度）；**不平即分诊，不硬改** |
| **失败处置** | 不平 → 分诊到 L2 对应岗位，**不在日清里就地改数** |

> ⚠️ **日清只校验、不锁账**（原文 `§一.3` `:70`）——日清通过≠当期已定稿。别把日清当成小月结。

### 4.2 `fin-month-close` 月结编排（每月）★ 核心

```
1  前置闸门   期间未锁账 + 本月日清全过 + 接入无积压        [agent 自检]
2  日清补齐   未过的日清逐日补跑                            [agent]
3  跌价计提   库龄推导 → 双轨取孰高 → 出计提建议            [agent 试算] → ★人审
4  金额对账   F13 金额守恒（法人层 / 合并层两段）           [agent]
5  出报表     P12 库存表 / P13 进销存周期表 / P16 余额管理报表  [agent]
6  凭证       按法人分别出 + 回传                           [agent]     → ★人复核
7  归档快照   余额表 / 收发存 / 跌价表 / 对账报告             [agent]
8  锁账       is_closed（是否已锁账）= 1                     [★财务主管批]
──────────────────────────────────────────────────────────────
★ = 必须人工审批，agent 不得自批
```

**编排层独有的三条约束**：

1. **任一步自证不过 → 整条停，不跳步**。跳到第 8 步锁账而第 4 步不平，是最严重的事故形态。
2. **两个审批点是硬点**——跌价计提建议（第 3 步）与凭证（第 6 步）**必须人看**，因为这两处直接进损益。
3. **锁账不可由 agent 触发**——第 8 步只有财务主管能做（权限矩阵强制，**不靠 skill 自觉**）。

## 五、L2 岗位层：三个动作闭环

| # | skill | 时点 | 谁 | 前置闸门 | 动作 | 产物 | 自证 |
|---|---|---|---|---|---|---|---|
| **O3** | `fin-negative-ops` 负库存处置岗 | 异常 | 核算会计 | 挂账表有 `OPEN`（未平）记录 | 催票 → 采购到货**冲平** → 出成本调整单 | 挂账置 `RESOLVED`（已平）；单据 `cost_status`（核算状态）转 `CALCULATED`（已核算） | 挂账清零；逾期超 `max_pending_days`（最长挂账天数）→ 阻断出库 |
| **O4** | `fin-period-adjust` 跨期处置岗 | 异常·**高权限** | 财务主管（**必审**） | 期间**已锁账** | 判「**漏了**」还是「**结错了**」→ 走当期补录单 `PERIOD_ADJUST` 或**反结账** | 补录单或反结账记录 | 一律**按当期口径量价**；原业务日期仅供追溯；留痕 |
| **O5** | `fin-config-ops` 配置变更岗 | 低频·**高权限** | 财务主管 + 系统管理员 | 该核算单元当期**开账前** | 计价方法配置 / 负库存策略（`cfg_negative_stock_rule`）/ 期初启用 | 配置生效记录 | **方法一经选定即锁定**——变更须走审批 |

**三处最容易做错、必须写进 skill 的分界**：

- **O3**：挂账的两阶段（暂估价 `P_est` 锁定 → 冲平 → 剩余入池）**是两步不是一步**；且「补单 / 排序键复核 / 调容差」三条路**不可互换**。
- **O4**：**改单 / 反结账 / 当期补录三条路不可互换**——混用会让审计**无法区分「错误」与「遗漏」**。这是内控问题，不是技术问题。
- **O5**：计价方法**一经选定即锁定**；负库存策略选「严格禁止」时**缺口上限 / 最长挂账天数 / 暂估单价来源三项隐藏**（条件行联动）。

> 规则细节不在这里重复——**全部在 L3 能力层**（`fin-negative-stock` / `fin-period-close` / `fin-valuation`），本层只声明**闸门与产物**。

## 六、L3 能力层：现有 5 个规则 skill **原样留用**

这是本轮一个省事的结果：**五十七建的 5 个规则 skill，正好就是企业级体系要的能力层**。

| 现有 skill | 在体系里的角色 | 被谁引用 |
|---|---|---|
| `fin-valuation` 计价方法 | 三法定义 / 判据树 / 方法锁定 | O5 配置、月结第 3 步 |
| `fin-owner-pricing` 货主分层与两级作价 | R1–R5 / 三金额 / 对平 | 日清对账、月结对账 |
| `fin-negative-stock` 负库存 | 两阶段闭环 / 容差 / 三条路 | **O3** |
| `fin-provision` 跌价准备 | 双轨取孰高 / 库龄 | 月结第 3 步 |
| `fin-period-close` 期间与锁账 | 日结只校验月结锁账 / F12 F13 | **O4**、月结第 8 步 |

**唯一要补的东西**：每个能力 skill 头部加一节 **「我能被谁调用 / 我需要什么前置数据」**——因为企业级下它不再是"给人看的摘要"，而是**被编排器调用的接口**。

> ⚠️ **但它们的写法不用改**——仍然是「规则摘要 + 原文指针 + 易错点」。**规则永远是规则，变的只是谁在调它。**

## 七、已有的 10 个 skill 怎么归位：两条生产线并列

企业级之后，这个项目会同时跑**两条生产线**，别混：

| 生产线 | skill | 干什么 | 何时用 |
|---|---|---|---|
| **规格线**（本文之前就有） | `fin-consistency-audit` / `fin-cross-doc-sync` / `fin-prototype-edit` / `fin-calc-example` / `fin-doc-localize` | **立法 / 修法**——改文档、改原型、核口径 | 需求变更时 |
| **运营线**（本文新增） | `fin-daily-ops` / `fin-month-close` / `fin-negative-ops` / `fin-period-adjust` / `fin-config-ops` | **执法**——按班次执行 | 每日 / 每月 / 异常 |

### ⚠️ 权威关系**反转**（必读）

| | 文档时代（今天） | AI 项目时代 |
|---|---|---|
| **唯一权威** | 原文（`…需求文档 1.0（原型页面与核算引擎）.md`） | **skill**——它是**可执行规格** |
| **原文的地位** | 法条本体 | **立法理由**（解释"为什么这么定"） |
| **冲突时** | 以原文为准 | **以 skill 为准**；但 skill 与原文**不一致本身就是一个缺陷**，要修 |

**这个反转是渐进的、不是今天生效的**——今天 skill 仍是索引。但只要有人（或 agent）**照着 skill 去执行**，skill 事实上就成了执行依据。**所以 skill 的改动从此需要治理**（见 §八）。

## 八、治理：skill 即内控

一旦 skill 成为执行依据，**改 skill 就等于改流程、等于改内控**。企业级必须补上三样今天没有的东西：

1. **版本号 + 发布记录**——skill 的每次改动记「谁 / 何时 / 因何 / 影响哪些岗位」，与会计系统本身同版本发布。
2. **评审**——改 `fin-month-close`（月结编排）或 `fin-period-adjust`（跨期处置）必须过财务主管，这两个直接动账。
3. **三样东西与 skill 同版本**：**口径 / 权限矩阵 / 系统能力清单**。任一样改了而 skill 没同步，skill 就是在教人做错事。

> 落地形态：这本身就是**一条规格线工作流**——可以复用 `fin-cross-doc-sync` 的「先出变更清单 → 停下等授权 → 再动手」骨架，加一层版本记录。

## 九、触发机制：`description` 关键词**不够**

前两轮全部 skill 都靠 `description` 里的关键词命中。**企业级工作流不能靠这个**——没人会在聊天框里打「日清」，日清是**日历触发的**。

| 触发方式 | 适用 | 在本项目怎么落 |
|---|---|---|
| **关键词命中**（现有） | 规格线 skill | 不变 |
| **显式命令** | 运营线 skill | 包装成 slash command（如 `/月结` `/日结` `/挂账处置`） |
| **日历 / 定时** | 日清、月结的**提醒与启动** | 定时任务起手 → 再进 skill |
| **事件钩子** | 负库存挂账产生、对账不平 | 系统事件 → 唤起对应岗位 skill |

⚠️ **`description` 仍然要写好**——它是兜底（用户直接问「这个月怎么结」时能命中），但**不能是唯一入口**。

## 十、首期建议（别一次全做）

### 10.0 系统实现现状（2026-10-13 审计结论）

一期原本的前置是「系统能力清单」。只读审计仓外代码 `~/Documents/Codex/财务库存中心/`（140 文件）后，结论是**这张清单要倒过来读**：

- **16 项能力已实现 0 项**——两个仓**都没有可运行的核算引擎**。
- 仓外那份「一期可运行原型」是**名义上的**：`db/` 空；`server.js` 仅 59 行（`/api/dashboard` 返回**硬编码假 KPI**，`/api/actions` 只校验动作串后返回**罐头响应**）；`public/index.html` 加载的 `/app.js` **不存在**。
- schema 只是 `docs/04-数据设计/ddl/` 下的**未执行 SQL 文本**（43 表）+ 一份自述「待 DBA 评审，未执行验证」的 722 行迁移；**无一条 CHECK 约束涉及守恒**——`inv_period_balance.equation_passed`（是否守恒）列**没有任何代码计算它**。
- ⚠️ **仓外仓的规格与本仓是两套**（凭证 / 先入先出法 / 合并抵消 / 表名 / 错误码 / 锁账字段全不一致）。**已拍板：以本仓四份文档为准**，仓外仓视为**旁支**。
- **可复用的副产品**：`server.js` 的 7 个动作串（`approve` / `reject` / `retry` / `close-period` / `reopen-period` / `review` / `save-rule`）是一份现成的**动作契约骨架**，与本文 skill 一一对得上。

### 10.1 分期

| 期 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **一期** | **L0 底座补权限矩阵** + **O3 `fin-negative-ops`** + **L1 `fin-daily-ops`**；硬不变量**先放 skill 检查**（标注过渡性技术债） | 频次最高、最痛、风险可控；且**不等系统** |
| **二期** | **O4 `fin-period-adjust`** + **O5 `fin-config-ops`** | 高权限、低频，但**闸门最硬**，要先把权限矩阵立住 |
| **三期** | **L1 `fin-month-close`** | 跨模块最广、依赖系统接口最多 |
| **贯穿** | **下沉**——系统侧每实现一条硬不变量，就**从 skill 里移除**对应检查 | 技术债必须还，否则过渡期变永久 |

**下沉条件（写进每个 skill 的头部）**：当系统侧出现对应的 DB 约束 / 服务端断言 / 引擎出口校验时，**skill 里的该条检查立即降级为「仅提示」或删除**。每条过渡检查都要标 `⚠️ 过渡期` 并写明它等的是哪一条系统能力。

## 十一、已拍板（2026-10-13）

| # | 问题 | 决定 |
|---|---|---|
