## 2. 硬冲突（P0）：照旧文档开工就会做错

### C-01 · 反结账的「回滚 / 删行重推」与引擎的「事件只增不删」正面相反

**证据**

- `设计 3.4.3`（PF8）步骤 D：「**回滚**：从错误单据开始逆向撤销（利用 `calc_log` 的 before/after 快照）」；步骤 E：「修正错误单据（改单 / **补单 / 删行重推**）」
- `设计 5.6.3` 改单处理：「按原单据相反方向做一次成本计算（**相当于"撤销"**）」
- `设计 3.4.2`（PF7）：「库存余额**反向调整**」
- 对立面：`引擎 §3`「引擎返回 **delta**，不返回余额」、`§6`「改单 = `version+1` **新事件**，不是删了重来」、`框架 4.7`「已核算的一律不可撤，只能反向单 + 红字凭证」

**问题**：这是两种根本不同的机制。「回滚」意味着把余额改回去、把日志删掉重算；引擎的做法是**只追加反向事件、余额由 delta 累加**。照 `设计 3.4.3` 实现，`t_calc_log` 的 before/after 快照就成了"可被改写的中间态"——**引擎的三种幂等、重放一致性、可审计性会一起失效**，而这正是 `设计 2.2 原则 2`（核算引擎幂等）想要的东西。

**一个更细的缝**：`设计 3.4.2` 的作废闸门是「单据是否有下游引用（凭证 / 对账已引用）」，而框架的闸门是「**已核算**」。一张已核算但尚未生成凭证的单据，设计允许撤、框架不允许。

**修订建议**

1. PF8 改写成「**定位 → 追加反向事件（红字）→ 追加修正后的事件（`version+1`）→ 重放校验**」，删掉"回滚""删行重推"两处措辞。
2. `5.6.3` 的"相当于撤销"改为"追加两笔反向与正向事件"。
3. 作废闸门统一为**核算状态**（已核算即不可撤），下游引用只作为提示。
4. 明确 `t_calc_log` 的定位：**审计留痕与投影，不是回滚依据**（`引擎 §9` 已要求给它加 `posting_seq` / `idempotency_key`）。

**影响章节**：设计 3.4.1 / 3.4.2 / 3.4.3 / 5.6.3 / 7.4；引擎 §3 §6

### C-02 · 「一期不锁账」与「月结锁账」方向相反

**证据**

| 出处 | 原话 |
|---|---|
| `设计 3.4.3` 注 | 「一期**未启用"会计期间锁账"**，月结后仍允许反结账重算（PF8）；二期引入期间概念后…」 |
| `设计 5.6.5` | 「二期增加"会计期间"概念，按期间锁账」 |
| `设计 13.2` | 「会计期间：财务结账的最小时间单位（**一期未启用**，二期规划）」 |
| `引擎 E-03` | 「**要引入** `period.is_closed`。这是重放能收敛、历史可审计的前提」（已锁定） |
| `引擎 E-07` | 「**月结锁账** + 日结只做校验」（已锁定） |
| `引擎 E-09` | 「**允许反结账，但必须走审批并留痕**」（已锁定） |

**问题**：不是措辞问题，是**方向相反**。设计文档三处都在告诉开发"一期不做期间"，而引擎的三条已锁定决策都以"一期必须有结账标志"为前提。照设计做，E-03/E-07/E-09 全部落空，`t_balance_snapshot`（`差距 F22` 要求）也没有落库依据。

**修订建议**：`设计` 三处统一改为——**一期引入 `period` 与 `is_closed`；日结只跑校验不锁账；月结打锁；反结账须走审批并留痕**。`5.6.5` 的"二期再引入期间"改为"二期把它升级为完整会计期间（含期间损益结转）"。`13.2` 术语条同步。

**影响章节**：设计 3.4.3 / 3.5.6 / 5.6.5 / 13.2；引擎 E-03 / E-07 / E-09

### C-03 · 契约里「迟到单据允许」是接口契约里最该改的一句话

**证据**

`契约 5` 时序与节奏约定：

> 「迟到单据 | **允许**，但必须带真实业务日期，财务按业务日期插入重算」
> 「**迟到单据为什么不用怕**：财务侧的核算引擎按"业务日期 + 单据号"顺序重排计算（见设计文档 PF8），迟到单据会自动插到正确位置并触发该维度重算。前提是业务日期必须真实，不能填推送日。」

对立面：`引擎 E-04`（已锁定）「已结账期间的迟到单据：**禁止** + 当期补录单通道」。

**问题**：这句话不只是描述错误，它在**教对方"随便迟到没关系"**。契约是双方签字文件，写着"允许"而系统实际禁止，责任会在第一次跨期补单时扯不清。而且它给的理由（自动插到正确位置）依赖的是 C-04 里那个错误的排序键。

**修订建议**

1. 契约 5 该行改为：「**已结账期间禁止迟到**；未结账期间可接受，按业务日期插入；跨期确需补记的走**当期补录单**（`PERIOD_ADJUST`，必审）」。
2. 删掉"迟到单据为什么不用怕"整段，替换为"**迟到单据为什么必须有闸**"——补录是唯一能绕开"历史不可改"的通道，通道必须有闸。
3. 契约 2.5 的"数据补推"行补一句：补推若落在已结账期间，一律转当期补录单，**不重算历史**。

**影响章节**：契约 2.5 / 5；引擎 E-04 / E-05 / §4.3

### C-04 · 排序键写成 `(业务日期, 单据号)`

**证据**（四处同源）

- `设计 3.2` 主流程：「移动平均核算引擎 | 按（业务日期, 单据号）顺序逐单计算」
- `设计 3.5.2`（PF10）：「按（业务日期, 单据号）取出待算单据」
- `设计 3.4.3`（PF8）：「按业务日期顺序正向重放该维度全部单据」
- `契约 5`：「按"业务日期 + 单据号"顺序重排计算」

对立面：`引擎 §4.1`「过账顺序 = `(biz_date, seq_in_day)`」＋「**`doc_no` 不可用作排序键**：单号不单调（有补单、有外部系统单号、有前缀差异），且业务系统改了单号规则历史数据就乱」。

**问题**：只写了 `doc_no` 这一半的错——正确规则还有 `E-01` 的「同日**入库优先** + 同类型按单号」。按 `doc_no` 排，同一天内"先出后入"会与"先入后出"算出不同的均价，而算例 3.7.1 恰恰依赖"入库优先"。

**修订建议**：四处统一改为 `(业务日期, 当日序号)`，并写明同日规则 = **入库优先，同类型按单号**；`doc_no` 明确标注"不可作排序键"。

**影响章节**：设计 3.2 / 3.4.3 / 3.5.2 / 契约 5；引擎 §4.1 §4.2

**证据**

- `清单 D-03` 建议默认：「先确认主体数量。**若一期为单主体**，数据模型仍预留 `legal_entity` 字段（默认主体），但**不开多主体功能**——为二期留路，成本极低。」选项 A/B/C 分别对应单主体、多主体不视同销售、多主体视同销售。

**修订建议**

1. D-03 三个选项按新结论重写：**结论落在 C 的变体**（多主体 + 跨法人转移视同交易 + 一期即需抵消报表）。
2. 把"一期几个主体"从待答问题改为**待确认清单（列名单）**——主体数量仍是事实问题，但"要不要多主体"已经定了。
3. `清单` 第 1 章总览表的 D-03 一行、第 5 章决策记录表同步。

### C-07 · 调拨与一级货权转移的判定规则缺失

**证据**

- `设计 3.3.4`（PF4）调拨：「读取调出仓（物料, 调出仓库）当前余额与单价 → 按调出仓做调拨出库 → 按同一金额做调拨入库」→ 凭证 `借 库存商品-调入仓 / 贷 库存商品-调出仓`。**全额同额，不产生损益。**
- `设计 4.2.1` `doc_type` 有 `TRANSFER_IN` / `TRANSFER_OUT`，无跨法人分支。
- `框架 §4.7` / `§8.3`：一级货权转移 = `OWNER_TRANSFER`，**必作价、必出凭证、必有损益**（R1）；`框架 §9` 只说"单据类型从 8 类增至 10 类"。
- `框架` 第 45 行把「集团内跨法人调拨」归入**一级货主 = 我方法人（含集团内其他法人）**维度。

**问题**：四轴引入后必然出现一个判定缝——**一张 `TRANSFER` 单，调出仓与调入仓若分属不同法人，它到底是"内部调拨"（无损益、借贷同科目）还是"一级货权转移"（作价、确认损益、需要抵消）？** 现在没有任何文档回答。框架把它归到了一级货主维度（等于承认它是转移），但没写成规则；设计侧的调拨逻辑完全没有跨法人分支。开发遇到这张单只能自己猜，**而猜错的后果是凭证方向错、损益不确认、合并抵消漏做**。

**修订建议**

1. 明确判定规则并写进 `设计 3.3.4` 与 `4.2.1`：

   | 条件 | 单据类型 | 作价 | 凭证 | 损益 |
   |---|---|---|---|---|
   | 调出仓与调入仓**同一一级货主** | `TRANSFER` | 按调出仓成本，同额 | 借调入仓 / 贷调出仓 | **无** |
   | 调出仓与调入仓**不同一级货主** | `OWNER_TRANSFER` | 按 `transfer_price`（交易数据） | 视同销售 + 成本结转 | **有**，且需抵消 |

2. 明确适配层责任：业务侧推出的 `TRANSFER` 若跨法人，**适配层拒绝并回执原因**，要求改推 `OWNER_TRANSFER`——不做"自动升级"（自动升级等于财务替业务定价）。
3. `差距 F08`（调拨行展开规则）的修订范围随之扩大：跨法人时展开的不只是两行，还有 `is_accounting_event`。

**影响章节**：设计 3.3.4 / 4.2.1 / 7.3 / 8.1.3；框架 §9；差距 F08

   - 业务不建：`(物料, 仓库, 批次)`，**且必须在对账报告的脚注里写明"数量对账口径为物理层，不区分货主"**（框架原话：**不能默默降级**）
2. 契约 3 矩阵新增：一级货主编码 = **A 级**；二级货主 = B 级或不参与。
3. 契约 2.2 字段最小集加 `owner_l1`（可由仓库归属公司推导）/ `owner_l2`（**必须业务给**，不能推导）。
4. 把这条作为**契约变更**正式提给业务团队，写进 W1 Checklist。

**影响章节**：契约 2.2 / 2.4 / 3 / 8 / 10；框架 O-07 / §9

### C-19 · 金额对账改对总账后，维度须按法人分

**证据**：`差距 F04` 建议金额对账改为比对**金蝶总账存货类科目余额**，并给 `t_reconcile_result` 加 `basis`（`BIZ_SNAPSHOT` / `GL_BALANCE`）字段；对账维度仍是 `(material_code, warehouse_code)`。

**问题**：金蝶总账是**按法人账套**的，而 F04 的维度里没有法人。多法人下，正确做法是**逐法人分别对总账，合并层再对一次存货总额**（R4：存货总额 = Σ 一级层 `is_internal=1`）。少这一维，对出来的"一致"是假的。

**修订建议**：金额对账维度改为 `(legal_entity, 物料, 仓库)`，并明确两级：
- **法人层**：各法人账面 vs 该法人金蝶账套存货科目余额（月结）
- **合并层**：Σ 一级层 `is_internal=1` vs 合并报表存货（月结，且需扣除内部未实现损益）

**影响章节**：差距 F04；设计 9.1 / 9.2 / 4.5.1；框架 R4 / O-12

### C-20 · 「凭证日期取系统当前日期」会让跨期补录的凭证落错期间

**证据**：`设计 5.6.5` 跨月单据：「单据日期用于库存余额计算；**凭证日期取系统当前日期**（或业务系统推送的会计期间）」。

**问题**：有了 E-07 的月结锁账与 E-10 的当期口径，"取系统当前日期"就变成隐患——跨期补录单的业务日期是历史日，若凭证日期取"当前日期"（= 当期），两者恰好错位一期；而若取业务日期，又会落进已锁账的期间。**规则必须显式写清，不能让"或"字留在文档里。**

**修订建议**：改为「**凭证日期 = 记账期间首日**（跨期补录单即当期首日，原业务日期仅进摘要与追溯字段）；库存余额计算按 `(业务日期, 当日序号)` 排序」。删掉"或业务系统推送的会计期间"这个含糊选项。

**影响章节**：设计 5.6.5；引擎 §4.1 / E-07 / E-10

## 5. 新文档内部的小缝

### C-21 · 事件幂等键按单据，部分行重推会被静默漏掉

**证据**

- `引擎 §6` 事件幂等键 = `(doc_type, doc_no, version_no)`，已过账的键再次提交 → **返回零 delta，不报错**。
- `引擎 §6` 传输幂等键 = `batch_id + doc_no + line_no`。
- `契约 2.5` 变更与异常通知：「**数据补推** | 历史区间补推（含明确区间与原因）| 及时」。

**问题**：两种幂等的**粒度不同**——传输按行、事件按单据。若业务侧补推一张单据、**且行数与原单不同**（多了一行或换了一行）而**没有升 `version_no`**（补推不等于改单，业务方不会主动升版本），事件幂等会整单判为"已过账 → 零 delta"，**新增的那些行被静默丢弃**。而"零 delta 不报错"的设计恰好让它连日志都不留。

**修订建议**：三选一，写进 `引擎 §6`：
1. 事件幂等键加上**行集合指纹**（行数 + 各行 `line_no` + 数量哈希），指纹不同即视为新事件；
2. 或在适配层强制约定：**行集合变化的补推必须升 `version_no`**，并写进契约 2.5；
3. 或对"键命中但行集合不同"的情况**返回冲突错误**而不是零 delta（宁可打断，不可静默）。

推荐 3（最保守，且与"零 delta 不报错"只对**行集合完全相同**的情形）。

**影响章节**：引擎 §6；契约 2.5

### C-23 · 货主列的命名在框架内部是两套

**证据**：`框架 8.3` 给 `t_document_line` 建议 `owner_l1` / `owner_l2`；`框架 4.7` 的货权变更单要素用 `from_owner_code` / `to_owner_code` / `from_owner_l2` / `to_owner_l2`。

**问题**：两处语义不同（一个是存量归属，一个是转移前后），本身合理；但 `l1` 与 `owner_code` 两个词根指同一概念（一级货主），落到建表时会分叉成两种列名。

**修订建议**：统一为 `owner_l1` / `owner_l2`，转移单用 `from_owner_l1` / `to_owner_l1` / `from_owner_l2` / `to_owner_l2`。

**影响章节**：框架 4.7 / 8.3
