## 一、先说清楚现在这张表混了三种东西

### 1.1 一台设备的一生，事件是多次的

一台 SN 从进来到出去，可能要经过：

| 事件 | 单据类型 | 发生次数 |
|---|---|---|
| 建档案 | 采购入库 | 1 次（一般） |
| 换仓 | 调拨出库 + 调拨入库（同一张单两腿） | 0…n 次 |
| 换法人 / 换产权人 | 一级货权转移出库 + 入库（同一张单两腿） | 0…n 次 |
| 卖出 | 销售出库 | 0…n 次（可卖出、退回、再卖出） |
| 退回 | 销退入库 | 0…n 次 |
| 返修 / 借出 / 归还 | 其他出库 / 其他入库 | 0…n 次 |
| 报废 | 其他出库（报损） | 0…1 次 |
| 退回供应商 | 采退出库 | 0…1 次 |

### 1.2 而列表的每一列只能放一个值

现状 P08 列表 **19 列**（18 个字段 + 操作），其中：

| 类别 | 列 | 问题 |
|---|---|---|
| **身份**（一生不变） | SN / 商品 SKU / 商品名称 / 成色等级 | 无问题 |
| **状态**（同一时刻只有一个值） | 当前状态 / 一级货主 / 二级产权人 / 所在仓库 | 无问题 |
| **事件**（有发生时间、可能发生多次） | 采购入账成本、入库单据号、入库单据类型、入库时间、销售出库成本、出库单据号、出库单据类型、出库时间、销售额（不含税）、单机毛利额 | **语义未定义** —— 一台机器卖过两次，`销售出库成本` 该放哪一次？ |

现在的实现是**隐式**取「首次入库 + 最近一次出库」，但页面上没有任何地方写明。

### 1.3 原型自己的 8 行样例已经不自洽

这是最有说服力的一条证据（`data-tab="8"`，8 行样例）：

- **第 1 行 `SN868120000000`「当前状态 = 在库」，却填了出库时间 `2026-09-25 10:20:00`** —— 在库的机器不可能已经出库；
- **第 5 行 `SN868120030868` 入库时间 `2026-09-28 21:15:28`、出库时间 `2026-09-25 11:00:00`** —— 出库早于入库；
- 8 行里 4 行的当前状态是「在途」「已冻结」，**这两个取值原文里根本没有**（原文只有 `IN_STOCK` 在库 / `SOLD` 已售 / `RETURNED` 已退供 / `SCRAPPED` 已报损，`:1122` `/` `:1147`）。本轮拍板把状态收成 **在库 / 出库 / 在途** 三值（§六.1），「已冻结」废弃，「在途」转正。

根因不是数据编错，是**列的含义没定义** —— 编样例的人只能凭感觉填。

### 1.4 结论

这不是「加个按钮」的事。**必须先定死每个字段取哪个时刻的值**，定不下来的，全部下沉到流水明细。

## 二、两种切法

| | **方案 A（推荐）** | 方案 B（保守） |
|---|---|---|
| 状态层列数 | 15 列（14 字段 + 操作） | 18 列（基本不动） |
| 状态层语义 | 每列显式标注「当前值 / 首次值 / 最近一次值」 | 列不动，只补语义说明 |
| 流水层 | 新建抽屉 `data-dw="8b"`，12 列 | 新建同样抽屉 |
| 改动量 | 列表重写 + 新抽屉 + 样例重造 | 只加抽屉 |
| 能否消除 1.3 的不自洽 | ✅ | ⚠️ 只消除一半（在库行的出库时间仍然留着） |
| 与原文的偏离 | 6 列下移 | 小（原文 14 字段全保留） |

**推荐 A。** 理由：用户要「分成两层」，如果状态层还是把 18 列原样摊着，等于只是多了一个入口，列的歧义照旧；而**歧义恰恰是这张表现在最难用的地方**。

> 如果评审更看重「少动原文」，选 B 也能落地 —— 流水层、取数、抽屉设计两案完全相同，只是状态层不瘦身。

## 三、方案 A 的具体形态

### 3.1 状态层（列表，15 列）

判据一句话：**同一时刻只有一个值的留在状态层；有一个时间戳、且可能发生多次的，进流水层。**

| # | 列 | 取值口径 | 数据来源 |
|---|---|---|---|
| 1 | SN / IMEI / 车架号 | 身份 | SN 资产档案（见 §四.1） |
| 2 | 商品 SKU | 身份 | 商品主数据 |
| 3 | 商品名称 | 身份 | 商品主数据 |
| 4 | 成色等级 | 身份（返修可能变，取当前） | SN 资产档案 |
| 5 | 当前状态 | **当前值**，三值：在库 / 出库 / 在途（§六.1） | SN 资产档案 |
| 6 | 一级货主 | **当前值**（货权转移会变） | SN 资产档案 |
| 7 | 二级产权人 | **当前值** | SN 资产档案 |
| 8 | 所在仓库 | **当前值**；在库 → 实际所在仓，在途 → 在途仓，出库 → `—` | SN 资产档案 |
| 9 | 当前账面成本 | **当前值** = 该件当前成本层金额（个别计价下 `batch_no` = SN，见 §四.2）；**在库 / 在途有值，出库为 `—`**（货已不在账上） | `t_inventory_layer` |
| 10 | 首次入库时间 | **首值** | 首条状态迁移为「→在库」的事件 |
| 11 | 最近一次销售：销售额（不含税） | **末值**，取最近一次**有效**销售出库（已被销退入库冲销的不算） | 单据行 |
| 12 | 最近一次销售：出库成本 | **末值**，与第 11 列同一次销售 | 单据行 / `t_inventory_layer` |
| 13 | 单机毛利额 | 派生 = 11 − 12；无有效销售时为 `—` | 派生 |
| 14 | 最近变动时间 | **末值**（任意事件的最后一次） | 事件流水 |
| 15 | 操作 | `[流水]` `[查看]` | — |

**之所以保留「首次入库时间」与「最近变动时间」两个时间戳**：它们让列表能按「放了多久」「最近有没有动过」排序，而这两个问题用不到具体是哪张单。

### 3.2 被移出状态层的 6 列 → 落到流水层

| 原列 | 新位置 | 理由 |
|---|---|---|
| `in_bill_no`（入库单据号） | 流水层第 1 条事件 | 一台机器可能入过多次库（采购 / 调拨 / 退货 / 货权转移） |
| `in_bill_type`（入库单据类型） | 同上 | 同上 |
| `out_bill_no`（出库单据号） | 流水层最近一条出库事件 | 可能卖过多次 |
| `out_bill_type`（出库单据类型） | 同上 | 同上 |
| `out_time`（出库时间） | 同上 | 同上 |
| `initial_cost`（采购入账成本） | 由第 9 列「当前账面成本」承接；采购原值在第 1 条事件里可见 | 经一级货权转移后，**该件的成本基准会按转移价重置**，原值 ≠ 现值；单列一个「原值」会让人拿它当现值用 |

> ⚠️ 这条**与整体 PRD 的「逐台展示的核心列」冲突**（PRD 把 `采购入账成本` / `销售出库成本` / `单机毛利额` 列为核心列）——见 §七 第 3 条。

### 3.3 流水层（抽屉，12 列）

**行粒度**：一行 = **一张单据对该 SN 的一次作用**。

| # | 列 | 说明 |
|---|---|---|
| 1 | 发生时间 | `YYYY-MM-DD HH:mm:ss`，按时间**倒序**（最近的在最上） |
| 2 | 单据类型 | 10 类（采购入库 / 销退入库 / 调拨入库 / 其他入库 / 货权转移入库 / 销售出库 / 采退出库 / 调拨出库 / 其他出库 / 货权转移出库） |

**顶部摘要条**（不是字段，派生展示）：SN / 商品 / 成色 / 当前状态 / 当前货主 / 当前仓库 / 当前账面成本 / 事件笔数 / 全周期毛利。

**为什么不做单独的时间轴图**：一台机器的事件通常 3–8 笔，表格按时间倒序本身就是时间轴，再加一条竖线时间轴是重复表达。若要视觉化，可在顶部摘要条下加一条极简节点条（入库 → 调拨 → 销售），列为二期。

#### 3.3.1 状态迁移表（本层的语义基线）

| 单据类型 | 方向 | 状态迁移 | 代价 |
|---|---|---|---|
| 采购入库 | 入 | — → 在库 | 形成该件成本层（`initial_cost`） |
| 调拨出库 | 出 | 在库 → 在途 | 转出仓出清；转出方按自己账面口径扣 |
| 调拨入库 | 入 | 在途 → 在库 | 转入仓形成成本层（同单两腿同号） |
| 货权转移出库 | 出 | 在库 → 在途 | 转出方成本层出清（同单两腿同号） |
| 货权转移入库 | 入 | 在途 → 在库 | **入账基准按转移价重置** |
| 销售出库 | 出 | 在库 → 出库 | 结转成本，产生销售额与毛利 |
| 采退出库 | 出 | 在库 → 出库 | 按原采购成本退回供应商 |
| 其他出库 | 出 | 在库 → 出库 | 报损 / 借出 / 返修送修，按 `reason` 区分 |
| 销退入库 | 入 | 出库 → 在库 | 按原出库成本回冲，该笔销售不再计入毛利 |
| 其他入库 | 入 | 出库 → 在库 | 借出归还、返修回来 |

> **三种状态的性格不一样**：**在库**是活跃态；**在途**是**过路态**，必由一对腿包夹（出腿进、入腿出），单腿停在在途经超阈值应作为异常监控；**出库**是终态，但可被销退入库 / 其他入库拉回在库 —— 于是同一台会有两次销售、两次出库，只有**未被冲销的那一次**计入「最近一次销售」与毛利。
>
> 双边单据（调拨 / 一级货权转移）**按腿各出一行**（§六.3），所以一次换仓在读感上是「出库 → 在途」再「在途 → 在库」两行；两行单据号相同、时间可能同秒，靠**方向 + 状态迁移**区分先后。这也是「在途」这个状态存在的唯一理由 —— 它让两条腿之间的中间态可被观察。

#### 3.3.2 双边单据要不要合并成一行

调拨与一级货权转移都是**一张单两条腿**（第一腿出库、第二腿入库），记账上确实是两条事件。

**已拍板：按腿两条**（§六.3）。抽屉里一次换仓占两行：

| 发生时间 | 单据类型 | 单据号 | 方向 | 状态（前→后） | 仓库（前→后） |
|---|---|---|---|---|---|
| 09-09 09:50 | 调拨出库 | TR-…0022 | 出 | 在库 → 在途 | WH01 → WH04 |
| 09-09 11:20 | 调拨入库 | TR-…0022 | 入 | 在途 → 在库 | WH04 → WH02 |

代价与规避：

- **读感上像「出去又进来」** —— 靠「状态（前→后）」列自证：中间那行是 `在途`，不是凭空少了一台；两行**单据号相同**，一眼能看出是一次调拨。
- **行数变多** —— 一台设备 6–8 行很常见。抽屉按时间**倒序**排，最近的在最上，不影响找人。
- **收益是无需在展示层做合并逻辑**：合并方案要让一条行承载「两个 `journal_no`、两个仓、两个成本动作」，字段说明里还得额外解释「这一行其实是两条账」——那才是真正的语义债。按腿两条与记账粒度 1:1，`t_calc_log` 一行对得上界面一行，对账时不用心算。

## 四、数据从哪来（这是本方案最硬的约束）

### 4.1 「SN 资产档案」在全项目没有 schema

原文在 P08 里 9 次把数据来源写成「**SN 资产档案**」（`:1143` 起），但：

- 详细设计文档里**没有任何 SN 资产表**（`t_sn_asset` / `sn_asset` 零命中）；
- 原文 `§四` 的数据模型章节也没有这张表。

也就是说 **状态层的"来源"是一个只有名字、没有字段的对象**。这不影响本方案，但落库前必须补 —— 见 §七 第 1 条。

### 4.2 三张现有表能拼出 SN 级流水

| 需要的东西 | 从哪来 | 关键点 |
|---|---|---|
| 该 SN 发生过哪些单据事件 | `t_document_line` 的 SN（一行可能带 N 个 SN） | 按 `sn` 反查单据行 |
| 每次事件的金额 / 数量 | `t_calc_log`（`doc_no` + `line_no` + `version_no`） | **`t_calc_log` 没有 `sn_code` / `batch_no` 列**，粒度是「单据行」不是「台」 |
| 该件每次的成本 | `t_inventory_layer` | 个别计价下 **`batch_no` 直接承载 SN**（一个 SN = 一条批次记录），按 `batch_no = sn` 取 |
| 该件当前在哪 / 归谁 / 什么状态 | SN 资产档案（待定义） | 或者由最后一条事件推导 |

### 4.3 粒度坑：一行多台机器，会共享同一个记账流水号

一张采购入库单的一行带 100 台机器时：

- 单据层：**1 行**；
- `t_calc_log`：**1 行**（按单据行记账）；
- `t_inventory_layer`：**100 条**（个别计价，一个 SN 一层）。

所以抽屉里 100 台机器点开，**第 11 列「记账流水号」会是同一个号**。这不是取数错误，是粒度差异 —— 必须在字段说明里写明，否则评审和测试都会当成 bug 报。

**若要真正的「一台一行日志」**，只能：`t_calc_log` 增 `sn_code`（等于把记账粒度改成按台），或新建 SN 轨迹表 —— 两者都动字段层，需单独授权。

### 4.4 三个取数选项

| 选项 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **(a) 展示层派生**（推荐一期） | 按 §4.2 现查现拼，不落新表 | 查询略重；`journal_no` 会重复（§4.3） | **推荐** |
| (b) `t_calc_log` 增 `sn_code` | 记账按台写 | 字段层 + 记账粒度 + 全部下游 | 不建议（一期） |
| (c) 新建 SN 轨迹表 | `t_sn_track`，事件落表 | 字段层；且与事件流形成**双真相源**，容易不一致 | 不建议 |

**(c) 特别要警惕**：`t_calc_log` 已经是"只增不删的真相源"，再建一张轨迹表就是第二个真相源，重放 / 红冲时两边必然漂移。

## 六、拍板结果（2026-10-23）

| # | 待定 | **拍板结果** | 落地形态 |
|---|---|---|---|
| 1 | **当前状态枚举** | **在库 / 出库 / 在途**（3 值） | 状态层只出这 3 个 tag；原「已售 / 已退供 / 已报损」合并为「**出库**」，原「已冻结」**废弃**，「在途」保留并转正为过路态（§3.3.1） |
| 2 | **成本列** | **只留「当前账面成本」** | 状态层第 9 列；`采购入账成本` 不再出列，采购原值在第 1 条流水事件里可见。在库 / 在途有值，出库 `—` |
| 3 | **流水层行粒度** | **按腿两条** | 调拨、一级货权转移各出两行，单据号相同、方向相反、状态 `在库→在途` / `在途→在库`（§3.3.2）。**与记账粒度 1:1**，不做展示层合并 |
| 4 | **按钮名** | **`[流水]`** | 行内 `[流水]` + `[查看]` 两个链接；抽屉标题「序列号流水明细」。原文的 `[全生命周期轨迹]` 由它承接 |

**拍板 1 的两个连带结论**：

- 「**出库**」是一个**合并态**，不区分卖出 / 退供 / 报损 —— 这三种结果在账上都是「货离开了、成本结转了」，差异由流水层最后一条事件的**单据类型**表达（销售出库 / 采退出库 / 其他出库）。状态层因此不为这层差异付列宽。
- 「**在途**」是**唯一由单据腿结构性产生**的状态：任何一台在途设备，必然有一条 `在库→在途` 的出腿事件在它下面。这让「在途」可以被机械校验（有在途无出腿 = 数据错误），而不是一个靠人填的自由值。
