## 一、前提变了什么

### 1.1 旧前提（现行全部文档的写作基础）

| 维度 | 旧口径 | 代表出处 |
|---|---|---|
| 系统边界 | **两个系统**、两个团队各自建设、**并行搭建** | 详细设计 `:142`「业务库存中心由另一团队负责搭建，财务库存中心作为独立模块同步建设」；通俗版 `:20`、原型版 `:40` |

| 对外依赖 | `O-07`（业务库存中心是否也建货主维度）＝「本契约唯一的外部依赖项」 | 契约 `:700–715`；字段定义 `:252` |

### 1.2 新前提

业务库存中心与财务库存中心**同属一套系统、共用同一个数据库**。由此：

- 没有「系统间」——只有**同一进程内的模块**，或**同一个库里的两组表**；
- 没有「推送 / 拉取」——数据**本来就都在库里**，不需要搬运；
- 没有「接口就绪的过渡期」——不存在「对面还没上线」这件事；
- 没有「两个团队签字」的契约对象——衔接问题是**内部设计问题**。

### 1.3 一个关键判断：变的是「边界」，不是「职责」

**职责分离（业务管实物/数量、财务管价值/金额）不因同库而消失**——同一个库里的两组表仍然分属两个关注点，数量的权威和价值的权威仍是两回事。**变的是这些职责之间靠什么衔接**：以前靠**接口报文**，现在靠**同一份数据**。

这条判断决定了后文的分类结果：**凡是「因为数据要跨系统搬运」才存在的规则，失效；凡是「因为业务语义本身」才存在的规则，留下，而且因为少了一层搬运，往往变得更强（同一事务、同一把锁、同一份主数据）。**

## 二、八道检查逐条结论

> 八道检查的权威出处：需求文档 `:1778`「入参完整性、主数据存在性、期间闸门、负库存闸门、四轴必填、二级货主必填、幂等校验、出口硬校验」。
> 分类口径：**失效**（前提不存在了，规则没有对象）/ **降格**（只在文件通道保留）/ **改造**（语义保留、形式与落点变）/ **加强**（语义不变，但由代码判定升级为数据库强制）/ **不变**（会计不变量）。

### 2.1 为什么「表头校验」整类降格

三个子项都不是业务规则，是**装载格式**规则：

- **列名 / 列顺序**：详细设计 `:2209` 写得很直白——「列名与顺序即**表头校验的判据**」。这个判据的存在前提是「数据以文件形式进来」。同库后数据本来就是表里的行，没有「列名对不对」这回事。
- **必填列**：等价于列上的 NOT NULL，属于 1c，不单列。
- **`record_count`**：字段定义 `:46–60` 把它定义在**报文信封**里（`batch_id / source_system / schema_version / push_time / record_count / records`）。这是「一次搬运声明搬了几条、实际搬了几条」的对账，同库没有搬运。

**结论**：整类**降格**——只在 Excel/CSV 通道保留。这不是把它们删掉，而是**把它们的适用范围从「主通道」缩到「批量导入工具」**。

### 2.2 为什么「行级校验」是加强而不是保留

现行写法是「判定 → 拒绝 → 回执」（需求文档 `:1782`「表头不合法整批拒绝，行列校验不过整单拒收」）。同库后这些判定可以由 **数据库约束**直接承担：

| 现行检查 | 同库后的强制手段 |
|---|---|
| 编码存在性 | 外键 |
| 必填 | NOT NULL |
| 类型 | 列类型 |
| 枚举合法 | ENUM / CHECK / 字典表外键 |
| 四轴必填 | NOT NULL 组合 |
| `owner_l2` 必填 | NOT NULL |
| `owner_l2` 有上级 | 自引用外键 |
| `qty × convert_rate = base_qty` | 生成列 + CHECK，或过账前校验 |
| 占位符 `"N/A"` / `"-"` 非法 | CHECK |
| 主数据存在 | 外键 |

**这不是「规则变少了」，而是「规则的位置从应用层移到了数据库层」**——错误数据不是「被拒绝」，而是**根本写不进去**。可用性上更强，但**对文件通道不适用**（文件里的错行仍然需要应用层判定 + 回执），所以文件通道的那一套**不能删**。

### 2.3 顺带消灭的一个历史顽疾：两级主数据清单

现行有一条：一级货主须在 `t_cargo_owner` 且为 **A 级**，**两级清单不一致时单据拒绝入账**（需求文档 `:1783`）。「两级清单」正是两个系统各存一份主数据的产物。

同库后**只有一份 `t_cargo_owner`**，「两级清单对不上」这个失败模式**从根上消失**。这是本次前提变化里最干净的一处收益，值得单独记一笔：**A-级判定保留（业务规则），但「清单比对」这个概念可以整体删除。**

### 2.4 期间闸门：语义不变，但落点必须前移（⚠️ 新增待定义项）

期间闸门本身**不需要改**——`t_period.is_closed` 仍是唯一开关，反结账 / 当期补录单（`PERIOD_ADJUST`）两条出口、三条路不能互换，全部照旧。

**但它会引出一个新问题**：旧架构下，业务单据**只在推送那一刻**才触达财务侧，所以「业务日期落在已锁账期间 → 拒收」是一个**单一入口的判定**，拒了就没有下文。

同库后，业务模块可能**先把单据写进业务表**——此时财务侧还没过账。如果期间检查仍只放在财务侧入口，就会出现：

> **业务单据已落库、财务过不了账** 的悬挂态。

这是旧架构下不存在、新架构下必然出现的状态。**必须新增定义一条**：期间检查是前置到**业务侧提交时**（业务侧就不能往已锁账期间写），还是允许悬挂、由财务侧挂账 + 告警。三种可选口径：

| 口径 | 做法 | 代价 |
|---|---|---|
| **A 前置到业务侧** | 业务模块提交单据时即校验 `t_period`，锁账期间直接不允许新增 | 业务侧要依赖期间表；跨期补录单的入口要单独开口 |
| **B 悬挂 + 挂账** | 业务侧照写，财务侧过账失败时挂账 + 告警 | 需要一张「待过账挂账表」，与 P15 负库存挂账表的关系要理清 |
| **C 保持现状语义** | 把「拒收」理解为「财务侧拒绝过账」，业务侧单据保持「未核算」态 | 最省事，但「悬挂」是设计出来的还是漏出来的必须写明 |

**这一条是本次复核里唯一需要新增设计的地方，需要拍板。**

### 2.5 幂等：三层要拆开看

| 层 | 现行键 | 结论 |
|---|---|---|
| 传输幂等 | `batch_id + doc_no + line_no` | **失效**（主通道）/ **降格**（文件通道保留，作为导入批次去重键） |
| 事件幂等 | `doc_type, doc_no, version_no` | **不变**——防的是**重放**（反结账重算会重复触达），与数据怎么来的无关 |
| 结果幂等 | 引擎纯函数 + 确定顺序 | **不变** |

**为什么传输幂等会失效**：它的定义就是「同一批**推**两次」。同库没有「推」，所以没有「推两次」。剩下的只有**文件重复导入**——那属于文件通道的批次去重，仍然需要，但不再是一条架构级的幂等层。

**「键命中但行集合不同」的处理必须改码**（需求文档 `:1788`）：现行是「一期无专用码，**暂借** `E-HEADER-INVALID`」。这个「借用」成立的前提是「反正报文头也会报这个码」——**同库后报文头这一类已经不存在了**（§2.1），`E-HEADER-INVALID` 只剩下一半语义，借用关系必须断开。

**建议**：把原本「建议二期新增」的 `E-IDEMPOTENT-KEY-CONFLICT`（幂等键冲突）**提前到一期落地**。它本来就是正确归属，同库后反而更有必要——因为「改单没走 `CHANGE`（改单）动作」这个错误在**同库直写**的形态下会更容易发生。

### 2.6 第九道检查：期初导入的 5 项校验（**独立一档，不在八道里**）

> 出处：需求文档 `:1270`（P14 期初余额导入页的 `[校验]` 按钮）；通俗版 `:1267`；`原型页面与需求文档反向核对_v1.0.md` `:72–75`（文档侧只落 4 项、恒等式未写全的既有差距）

**5 项**：① 四轴完整性；② `owner_l2`（二级产权人）必填；③ 精度（数量 4 / 金额 2 / 单价 6）；④ 行内恒等式 `init_qty × init_unit_price = init_amount`（期初数量 × 期初单价 = 期初金额）；⑤ 期间未锁账（`E-PERIOD-CLOSED`）。

**同库后逐项**：

| 项 | 同库后 |
|---|---|
| ① 四轴完整性 | **加强**（NOT NULL） |
| ② `owner_l2` 必填 | **加强**（NOT NULL） |
| ③ 精度 | **加强**（列精度） |
| ④ `init_qty × init_unit_price = init_amount` | **保留**——这是**会计恒等式**，不是装载规则。同库后可由生成列 / CHECK 承担 |
| ⑤ 期间未锁账 | **保留**，落点问题同 §2.4 |

**要点**：期初导入是**从文件进来**的（`initial_balance_import_template.xlsx` + `[下载期初导入模板]`），**它的表头校验判据（列名与顺序）必须保留**（需求文档 `:1268`「列名与顺序即表头校验判据」）。**这 5 项一个都不失效**——这也从侧面印证了 §六 拍板项 2：**期初这条文件通道必须留**，而它的存在本身就把 §2.1 的表头校验这一块**钉住**了。

**连带**：`G-02`（`object` 枚举没有期初余额的位置，`出入库场景与数据交接对照_v1.0.md` S-09 段）——同库后**`object` 枚举整个消失**（它是信封字段），`G-02` 这个既有缺口**自动闭合**，不需要单独解决。

## 三、14 个报文错误码的去向

> **权威出处**：《通用数据接口字段定义_v1.0》`§2.7` `:185–198`（**唯一权威定义**）。需求文档 `:1795–1808` 与通俗版对应表是**镜像**，改动时必须同改。
> 现行口径：「**14 个码全部在过账之前产生**——13 个在数据接入校验层（`FL-02` / `FL-04`），`E-NEGATIVE-QTY` 在计量前的负库存闸门」。
> **另有两处「聚合展示」也列了这 14 个码，改码时必须同步**：`产品架构图_v1.0.md` `:553–556`（按键值四分组归集）、`二级货主必填化变更影响清单_v1.0.md` `:129/:131`（P14 导入日志由 4 码扩到 5 码）。

| # | 错误码（中文） | 同库后 | 说明 |
|---|---|---|---|
| 1 | `E-HEADER-INVALID`（单头字段不完整） | **拆分** | ①「报文字段名 / 顺序 / `record_count` 不符」→ **失效**；②「幂等键命中但行集合不同」→ **改码**为 `E-IDEMPOTENT-KEY-CONFLICT`（§2.5） |
| 2 | `E-SCHEMA-VERSION`（报文版本不支持） | **失效** | `schema_version` 是报文版本号，同库无报文 |
| 3 | `E-MASTER-MISSING`（主数据缺失） | **保留** | 主通道由外键强制（理论上不可达，留作兜底）；文件通道仍靠它 |
| 4 | `E-OWNER-L1-MISSING`（一级货主缺失） | **保留** | NOT NULL + A 级检查 |
| 5 | `E-OWNER-L2-ORPHAN`（二级货主无所属） | **保留** | 自引用外键 |
| 6 | `E-OWNER-L2-MISSING`（二级货主缺失） | **保留** | NOT NULL |
| 7 | `E-ENUM-INVALID`（枚举取值非法） | **保留** | CHECK / ENUM / 字典外键 |
| 8 | `E-UNIT-CONV-MISSING`（单位换算缺失） | **保留** | 不做 1:1 兜底 |
| 9 | `E-QTY-MISMATCH`（数量不匹配） | **保留** | `qty × convert_rate ≠ base_qty` |
| 10 | `E-CROSS-LEGAL-ENTITY`（跨法人单据非法） | **保留，语义升级** | 现行是「行级拒绝 + 回执要求业务改推 `OWNER_TRANSFER`」（一级货权转移）——**同库后应在业务模块提交前就拦住**，不再等到财务接收入口 |
| 11 | `E-PRICE-MISSING`（取价缺失） | **保留** | `transfer_price` / `internal_price` |
| 12 | `E-PERIOD-CLOSED`（期间已锁账） | **保留** | 落点问题见 §2.4 |
| 13 | `E-NEGATIVE-QTY`（负库存超容差） | **保留，判定更可靠** | 同事务 + 行锁 |
| 14 | `E-SRC-DOC-MISSING`（源单缺失） | **保留** | `orig_doc` 定位 |

**汇总：2 个失效（`E-SCHEMA-VERSION`、`E-HEADER-INVALID` 子项①）、1 个改码（子项② → `E-IDEMPOTENT-KEY-CONFLICT`）、1 个语义升级（`E-CROSS-LEGAL-ENTITY`）、10 个保留。**

### ⚠️ 但「保留」不等于「原样」——错误码的**投递方式**整体要重写

这 14 个码的现行存在意义是**回执**：字段定义 `:200` 原文「**回执是业务侧唯一能看到『为什么被拒』的地方**」。同库后：

- **如果业务模块与财务引擎在同一进程**（见 §六 拍板项 1 的口径 A）→ 错误码变成**函数返回值 / 异常**，`Receipt` 这个结构体消失，但错误码本身作为**错误分类**保留；
- **如果财务侧直接读业务表**（口径 B）→ 校验发生在**过账时**，错误码仍作为**过账失败原因**保留。

两种口径下，**错误码集合基本不变，变的是它外面那层「回执 / 信封」**。所以 §五 的文档影响清单里，「错误码表」多为**保留 + 补注**，「信封 / 回执 / 适配层」才是**成块删除**。

**另注**：这 14 个码与引擎侧 `E-01` – `E-12`（引擎决策项）**是两套互不相干的命名空间**（《一级与二级货主双维度结存设计方案_v1.0.md》`:267` 已写死）。本次复核**不动引擎侧编号**。

## 四、变化最大的一处：对账（FL-12）

这是全部校验规则里**改动最重**的一类，单列一节。

### 4.1 现行设计

| 对账 | 对手方 | 依据 | 出处 |
|---|---|---|---|
| **数量对账** | **业务库存中心的日切快照** | `basis = BIZ_SNAPSHOT` | 详细设计 `:1765–1784`；单据全流程图 `:68/:183/:184` |
| **金额对账** | **金蝶总账** | `basis = GL_BALANCE` | 同上；契约 `:18` |
| 差异处理 | 差异定位报告 → **业务方确认 / 补单** | 容差 SLA 双方书面确认 | 单据全流程图 `:185`；契约 `:23/:337` |

配套：`biz_inv_qty`（业务库存可用总数）、`diff = 本系统账面值 − 业务系统值`、容差、`OK / DIFF / MISS / EXTRA` 四种状态（P10 核对表，通俗版 `:1104/:1109`）。

以及 `O-07`——「业务库存中心**是否也建货主维度**」，契约全文称之为「**本契约唯一的外部依赖项**」（契约 `:700–715`、字段定义 `:252`、详细设计 `:2727/:2935`）。

### 4.2 同库后怎么变

**数量对账**：从「跨系统日切对账」变成**同一库内、两个模块之间的一致性校验**。三个连带变化：

1. **`as_of` 时点口径问题基本消失**。现行要三方（业务快照、财务账面、开账日）对齐 `as_of`（契约 `:248`「`as_of` 三处同口径」），是因为两个库的快照时点会错开。同库只有一个「现在」，不存在快照时点差。
2. **差异来源被重新分类**。旧差异来源主要有二：接口时序（还没推过来）、快照时点（`as_of` 不同）。同库后前者消失，只剩后者的一种新形态——**业务模块写了自己的数量表、财务侧投影没跟上**。也就是说，**差异从「两个系统不一致」变成「同一批数据的两个投影不一致」**，性质上是 bug 而非时序，**容差可大幅收紧，甚至改为「任何差异都必须定位到原因」**。
3. **补单的操作对象变了**。旧：通知业务侧补推单据。新：**内部补录 / 修正**。差异定位报告（单据全流程图 `:185`）的读者从「业务方」变成「内部」。

**金额对账**：对手方是**金蝶总账**，金蝶仍是**外部系统**，**完全不变**。

**`O-07`**：从「待与业务团队谈判的外部依赖」**降级为内部设计决策**——「要不要建货主维度」现在由本项目自己拍板。这是本次前提变化里**消解掉的第二个对外依赖**（第一个是 §2.3 的两级主数据清单）。

### 4.3 需要保留还是取消？

**保留**，但**定位降级**。理由：即使同库，业务模块仍可能维护自己的数量视图（业务管实物、财务管价值），并发下的中间态仍会产生差异，月末仍需要一道网。但它的性质从「**跨系统对账**（第二道网）」变成「**模块间一致性校验**」。

**⚠️ 需要拍板的点**：P10 核对表的 `biz_inv_qty`（业务库存可用总数）与「四种状态 `OK / DIFF / MISS / EXTRA`」是否保留原样，取决于 §六 拍板项 3（数量的唯一权威是谁）。

### 4.4 连带消解：契约的「数据分级」有一半失去对象

契约把字段按 A / B / C 三级约定一致性要求：**A 级**（编码、数量、日期、批次、货主）「**错一个就是事故**」（契约 `:347`、`:326–330`）；B 级含对账容差 SLA（`:337`）；C 级（库存金额）「不要求与业务一致，但需能解释差额构成」（`:341`）。

**A 级的「事故」判定前提是「数据跨了一道边界」**——两道之间传错才叫事故。同库后只剩一份数据，**A 级的多数条目自动成立**（编码、日期、批次、货主不可能「不一致」，因为没有第二个副本），只有**数量**仍然可能不一致（如果 §六 拍板项 3 的答案是两个模块各持一份）。

**结论**：契约分级表**大幅缩水**，只剩「数量」这一条还实质有效。这进一步支持 §4.2 的判断——**对账这一层在新形态下只剩「数量是否一致」一个真问题。**

另注 `事例拆解` `:515` 的既有口径「`diff_qty`（数量差异）**一律以财务侧账面算**，业务侧 `book_qty` 只用于**比对告警**（G-07）」——这条口径**恰好就是同库形态的正确写法**，可以**直接沿用**，不需要改。

| **A · 保留进程内接口** | 业务模块仍通过一个应用层接口把单据交给核算引擎（`InventoryDataAdapter` 降格为**内部接口**） | **信封 / 协议 / `Receipt` / `pull_*` 全部失效**，但「单据交给引擎」这个动作、以及「交什么字段」仍然有定义。校验主体留在**引擎入口** |
| **B · 财务侧直接读业务表** | 核算引擎直接查询业务模块写的表（同库 join） | **适配层整层消失**。校验主体移到**过账时**，行级校验改由**外键 / NOT NULL** 承担。「事件」从「收到的报文」变成「业务表上的一行」 |

**差别**：A 保留了一个「事件边界」，B 连这个也没有。**A 更容易保持引擎的纯函数契约（`measure(event, ctx) -> Posting`）不变**——因为仍然有明确的「事件」对象。B 需要重新定义「什么触发过账」。

> **倾向**：**A**。理由是详细设计 `:2463/:2465` 已经把「边界划在接口上」定为原则，A 是这条原则在同库形态下的自然延续；而且它保住了引擎契约不动，改动面最小。

### 拍板项 2：Excel / CSV 导入通道，留不留？

- **期初导入（P14）几乎肯定要留**——期初余额本来就来自文件。
- **单据导入**（`doc_change_{date}.xlsx` / `doc_void_{date}.xlsx` 两个动作文件 + 10 个模板，通俗版 `:284`）留不留？

| 口径 | 后果 |
|---|---|
| **留** | §2.1 的表头校验、`t_import_error_log` + `raw_payload`（`payload` 原文）、文件绑定中文列名（详细设计 §7.2）、传输幂等（作为导入批次去重键）**全部保留**——但适用范围**缩到这一条通道**，「API 未就绪期间的正式通道」这个定位删除 |
| **不留** | 上述整块删除 |

### 拍板项 3：**数量的唯一权威是谁？**

同库后，业务模块和财务余额表**都可能持有数量**。必须写死：

1. **谁是数量的权威**——业务表，还是财务余额表？（决定 §4 对账「谁对谁」）
2. **谁负责保证一致**——业务模块写入时同步财务投影，还是财务侧异步投影 + 对账兜底？
3. **对账差异算 bug 还是算容差**——同库后时点差消失（§4.2），容差是否收紧到「任何差异都必须定位原因」？

这一条同时决定：P10 核对表的 `biz_inv_qty` / `OK·DIFF·MISS·EXTRA` 四种状态是否保留原样，以及 §2.4 期间闸门悬挂态怎么处理。

## 七、一句话结论

**同库之后，校验规则不是「变少」，而是「换位置」**：

- **搬运类**（信封 / 列名顺序 / `record_count` / `schema_version` / 适配层 / `Receipt` / 传输幂等）——**失效**，因为它们校验的是「数据在路上的样子」；
- **业务类**（主数据 / 枚举 / 四轴 / 二级货主必填 / 换算率 / 单位换算 / 跨法人 / 取价 / 源单 / 期间 / 负库存）——**保留并加强**，从「判定后回执」升级为**同事务、同锁、外键强制**；
- **会计不变量**（V3 对平 / F12 / F13 / 批次行均价 / 单据完整性 / 事件与结果幂等 / `E-01` – `E-12`）——**完全不变**；
- **对账（FL-12）**——**改造**，从跨系统日切对账变成模块间一致性校验，并**消解掉 `O-07` 这个对外依赖**；
- **期初导入的 5 项校验**——**一项都不失效**（§2.6），其中表头判据的存在**反证了文件通道必须保留**；
- **顺带收益**——「两级主数据清单不一致」这个历史失败模式**从根上消失**；契约的 A/B/C 数据分级只剩「数量」一条实质有效（§4.4）；`G-02`（`object` 枚举缺期初位置）**自动闭合**；
- **唯一需要新增设计的地方**——期间闸门在「业务单据已落库、财务过不了账」时的**悬挂态**处理（§2.4）。
