# 一级与二级货主双维度结存设计方案 v1.0

> **版本**：v1.0 ｜ 2026-09-30
> **定位**：**设计稿**。本文档**不改动任何既有文档**——`§七` 列出「若要落地，需要同步改哪些既有文档」，**待批准后**再动。
> **回答的问题**：一级货主、二级货主两个维度都要算结存，方案怎么设计。
> **两个已拍板的前提**：① 二级结存**物化**成一张余额表；② 二级维度的「结存金额」**只给会计口径一列**（`alloc_amount`），内部结算口径 `internal_amount_l2` **不上任何页面、不进任何对平**。
> **一处有意的例外**：`§四` 把悬置缺口 **`G-06`**（二级分摊账的展开规则与符号未定义）一并关闭——不关它，二级结存的**数量符号**就没法定，物化表建不起来。这一条我给了**明确建议**，但它本来是 W1 的待决项，**请你复核**。

## 〇、一句话结论

**一级结存已经有了，二级结存只差一张物化表。**

新增 **`t_owner_balance_l2`（二级货主结存表）**，主键 = **核算单元 `(商品, 仓库, 一级货主)` + `owner_l2`（二级产权人）**，**只存 `qty`（结存数量）一列**。二级的结存金额 `alloc_amount`（二级分摊金额）**不落库**，查询时按

```
alloc_amount = t_owner_balance_l2.qty × 该核算单元的当期一级结存均价
```

**派生**。这样做的收益是三重的：

1. **V3 对平等式由构造保证**，且**退化为 V1**（数量守恒）——不再是一条需要额外维护的等式；
2. **R3 / R4 / R5 三条红线一行不动**——二级仍然**没有自己的均价池**（同一个核算单元内多个二级货主**共用一个均价**，这条既有规则自动成立，不靠纪律靠结构）；
3. 顺带把 `G-06` 的符号问题**收敛到一个地方**（分摊账的 `qty` 符号），而不是每个查询各写一套。

### 1.2 缺的三件

### 1.3 一个必须先纠正的读法：**分摊账不是「只记二级重分配」**

这一点是**全案的支点**，先把它钉死。

`详细设计文档` `§4.2.4` 有一句「**二级重分配同时写分摊账**」，容易被读成「只有 `OWNER_REASSIGN` 才写 `t_owner_allocation`」。**读法错了。** 三处证据指向相反的方向：

| 证据 | 原文 | 说明 |
|---|---|---|
| `单据处理全流程图` `:506` | FL-09 记账流程图节点：`apply_alloc_deltas → 写 t_owner_allocation`，**与 `balance += delta` 并列**成为记账的下一步 | 这是**每次勾稽都执行**的一步，函数名就叫 `apply_alloc_**deltas**`（增量），与余额表同构 |
| `单据处理全流程图` `:830` | FL-09 落表：`t_inventory_balance`（`+= delta` + `version`）、`t_calc_log`、…、**`t_owner_allocation`** | 与余额表、`t_calc_log` **并列**在同一格 |
| `需求文档` `:498` | 记账层输出：`t_inventory_balance`、`t_calc_log`、**`t_owner_allocation`**、凭证草稿 | 同上，「记账层的输出」是**通用**表述，不是「重分配单的输出」 |
| `单据处理全流程图` `:831` | FL-08 出口校验：「硬校验 `Σ alloc = 一级层`」 | 出口校验是**每次事件**跑的那道闸（`V3` 引用的「引擎出口硬校验①」） |

`§4.2.4` 那句「二级重分配同时写分摊账」讲的是**重分配这笔业务的特殊性**——一笔业务写**两处**（`t_document_line` 记「货权变更」这一*动作*，`t_owner_allocation` 记二级层的*两个金额*），**不是**说重分配是分摊账的唯一来源。

> **结论**：`t_owner_allocation` **已经是二级层的发生额账**，性质与 `t_calc_log` 对一级层完全相同。它缺的不是"要不要记账"，而是"**结存从它汇总出来之后落到哪**"。

**这条结论直接决定了本方案的形状**：新增的不是"一套新算法"，而是"**二级层的物化投影**"——一级层早有这一步（`t_calc_log → t_inventory_balance`），二级层只是补上。

## 三、核心设计

### 3.1 全案的支点：两层账的类比

| 层级 | 发生额账（事件为真相源，只增不删） | 结存账（物化投影，`+= delta` + `version`） |
|---|---|---|
| **一级** | `t_calc_log`（计算过程留痕表） | `t_inventory_balance_unit` + `t_inventory_balance_batch` |
| **二级** | `t_owner_allocation`（二级货权重分配表）——**已存在** | **`t_owner_balance_l2`（二级货主结存表）——本方案新增** |

右列两张表是**同一件事的两个粒度**，都由左列**重放**得到（`核算引擎设计要点` `:199/201`；`详细设计文档` `:2707–2720`：重放 ≡ 投影，不一致即报错）。补齐这一格，二级层才第一次拥有与一级层同等的可审计性。

### 3.2 新表设计（DDL 草案）

```sql
-- 二级货主结存表：核算单元的二级分摊结存（物化投影）
-- 全表唯一的"存储型结存字段"就是 qty —— 金额与单价一律派生，见 3.3
CREATE TABLE t_owner_balance_l2 (
  material_code  VARCHAR(32)  NOT NULL COMMENT '商品编码',
  warehouse_code VARCHAR(32)  NOT NULL COMMENT '仓库编码',
  owner_l1       VARCHAR(32)  NOT NULL COMMENT '一级货主（法人主体）编码',
  owner_l2       VARCHAR(32)  NOT NULL COMMENT '二级产权人编码（可为个人 / 部门 / 事业部 / 代采项目）',
  asset_type     CHAR(2)      NOT NULL COMMENT '资产类型：OWN（自有）/ CONSIGNMENT（受托代管）',
  qty            DECIMAL(18,4) NOT NULL DEFAULT 0 COMMENT '结存数量（带符号；负=超分摊，即负库存）',
  version        INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本（与余额表同一套重试机制）',
  updated_at     DATETIME     NOT NULL COMMENT '最后更新时间',
  PRIMARY KEY (material_code, warehouse_code, owner_l1, owner_l2, asset_type)
) COMMENT '二级货主结存表：核算单元的二级分摊结存，物化投影，可由 t_owner_allocation 重放重建';
```

**设计要点逐条**：

| 项 | 决定 | 理由 |
|---|---|---|
| **主键** | 核算单元 `(商品, 仓库, 一级货主)` **+ `owner_l2`** **+ `asset_type`** | 与 `需求文档` `§一.5.2` 二级聚合键一致（`(amiba_owner_id, legal_owner_id, warehouse_code, sku_code, asset_type)`，只是把顺序按核算单元排列）。⚠️ **不要拿 `财务库存方案.md` 的 `uk_account_dim`（`legal_owner_id, amiba_owner_id, warehouse_code, sku_code, asset_type`）来类比**——那是**另一代设计（口径 B）**，那把键建在 `inv_account_balance`（存货账户实时余额表）上，等于「每个二级货主各持有一份结存均价」，即**在二级层自建均价池**，与 R3 / R4 直接冲突（`二级货主必填化变更影响清单_v1.0` `§6` 已把它列为**唯一未决项、至今未拍板**）。它与本表**列形相近、意图相反**：本表是**从属投影、不带均价列**，这正是它能建在二级层的原因。**`owner_l2` 进的是这张表的键，不是核算单元的键**——R3 / R4 / R5 说的是后者，两者不冲突。`asset_type` 与一级货主维度、仓库维度的聚合键同款携带（三 tab 必须同拆分粒度） |
| **不含批次** | 主键无 `batch_no` | `需求文档` `§一.5.2` 明写「批次号在结存余额口径下**三个维度都恒为 `—`**」；批次明细留在发生额账（`t_owner_allocation` 有 `batch_no` 列）里 |
| **只存 `qty`** | 无 `alloc_amount`、无 `unit_price`、无 `internal_amount_l2` | 见 `§3.3`——这是本方案最关键的一条 |
| **`qty` 带符号** | 转出为负、转入为正 | 见 `§四`；不带符号 `SUM` 取不出结存 |
| **`version`** | 与余额表同一套乐观锁 | 记账层「`balance += delta WHERE 键 = key AND version = expected`，影响行数为 0 则重试」这套机制**照搬**，不新发明 |
| **`has_negative`** | **不落库**，查询时 `qty < 0` 派生 | 需求文档 P05 二级字段表明写「**按二级货主汇总后**结余量小于 0 时显示」——它的语义就是 `qty < 0`，存一列反而可能不一致 |

### 3.3 为什么**只存 `qty`**：两种读法必须二选一

二级结存的「金额」有两种算法，**它们不是等价的**，必须在设计上选定一种：

| | **读法 A（本方案采纳）** | 读法 B（否决） |
|---|---|---|
| 算法 | `alloc_amount = 二级结存数量 × 该核算单元的**当期**一级均价` | `alloc_amount = Σ` 分摊账发生额里的 `alloc_amount`（逐笔快照价直接求和） |
| 那 `alloc_amount` 是 | **派生值**（每次读时算） | **存储值**（逐笔累加） |
| Σ 二级 = 一级层金额？（V3） | **恒成立**，且退化为 V1 | 也成立（逐笔恒等式telescope） |
| 同一核算单元内多个二级货主**单价是否相同** | **必然相同**（同一个一级均价） | **可以不同**（各自入账时点不同，隐含单价不同） |
| 与 `§一.5.2` 的既有规则是否相容 | **相容** | **冲突** |

**决定性的那一行是倒数第二行。** `需求文档` `§一.5.3` 的注解原文：

> 「同一核算单元内多个二级货主**共用同一个均价**」

读法 B 会**破坏这条规则**：同一核算单元里，A 在价格 10 时入账、B 在价格 12 时入账，读法 B 下 A 行的隐含单价 10、B 行 12——**两个二级货主在同一个核算单元里各自有一个均价**，这正是 R3「存货均价池只在一级层建立」要禁止的形态。它不违反 R3 的字面（没有真的建第二个均价池），但违反了 R3 的**实质**。

读法 A 则让这条规则**由构造成立**——二级的金额与单价都是"借"一级的，二级层**没有任何一个属于它自己的价格**，想违反 R3 都没有余地。

> **所以：二级余额表不能有金额列，也不能有单价列。** 有了一列，就一定会有人往里面写；写了，二级层就有了自己的价格。**把"不该有的字段"从表里拿掉，比写一条"不要用这个字段"的纪律可靠。**

**顺带得到的简化**：读法 A 下

```
Σ_owner_l2 (qty × 一级当期均价) = (Σ_owner_l2 qty) × 一级当期均价 = 一级结存数量 × 一级当期均价 = 一级结存金额
```

即 **V3**（Σ 二级维度金额 = 一级层金额）**不再是一条需要维护的等式**——它等价于 **V1**（数量守恒）。**一条硬校验，同时守住两个等式。**

### 3.4 二级结存金额与均价怎么出

二级维度**不读一级余额表**这句既有表述仍然成立——它读的是**自己的**结存表，再 **JOIN** 一级余额表拿均价：

```sql
SELECT b.owner_l2, b.owner_l1, b.warehouse_code, b.material_code, b.asset_type,
       b.qty                       AS current_qty,        -- 存储值（P05「当前结存数量」）
       b.qty * u.unit_price        AS current_total_cost,  -- 派生（P05「当前结存总额」，即 alloc_amount 口径）
       u.unit_price                AS current_unit_cost,   -- 继承（P05「当前结存均价」，R3）
       u.pricing_method            AS pricing_method,      -- 继承
       (b.qty < 0)                 AS has_negative,        -- 派生
       b.updated_at                AS updated_at
FROM   t_owner_balance_l2 b
JOIN   t_inventory_balance_unit u
  ON   u.material_code  = b.material_code
 AND   u.warehouse_code = b.warehouse_code
 AND   u.owner_l1       = b.owner_l1
 AND   u.asset_type     = b.asset_type;
```

`u.unit_price` 是**派生值**（`详细设计文档` `:1497`：结存单价 = 结存金额 ÷ 结存数量），所以"二级金额 = 数量 × 一级均价"这条读法是**跟着一级层均价自动重估的**——一级层调价（新入库改变移动平均）后，二级各行的金额**自动跟着变**，不需要重算、不会漂移。这正是「二级继承一级均价」应有的行为。

> **一个必须写进文档的推论**：二级维度的 `current_total_cost` **不是"历史成本"**，而是"**按一级层当期均价重估后的分摊金额**"。它随一级层均价变动而变动。这不是缺陷，是 R3 的必然结果——**二级层没有自己的历史成本**。P05 的列表口径应据此加注。

### 3.5 二级的「结存单价」为什么不独立出列

`§一.5.2`「维度间的口径差异」表已写：二级 `current_unit_cost` **不独立建均价池，继承所属一级层核算单元**；该单元为 `SI` 时**同样继承 `--`**。本方案**不改这条**，只补全三档分流（与仓库维度的合并行规则同源）：

| 所继承的一级单元方法 | 二级 `current_unit_cost` 展示 |
|---|---|
| `MA`（移动加权平均） | 派生均价（原行为） |
| `FIFO`（先入先出法） | 派生均价 + 标注「派生 · 非计价依据」 |
| `SI`（个别计价） | **`--`**（该单元逐件成本差异最大，均价最误导）+ 下钻 P08 SN 资产台账 |

**为什么不是"引用来的所以能显示"**：`SI` 单元的均价在任何维度下都是误导性的；"继承"改变的是**数据从哪来**，不改变**这个数能不能给人看**。原文档这一点已经写对了。

### 3.6 R3 / R4 / R5 红线核对

**逐条核，一条都不动**：

| 红线 | 原文 | 本方案下 |
|---|---|---|
| **R3** | 存货均价池**只在**一级货主层建立；二级另维护内部结算价 | ✅ **仍成立**。新表无均价列；二级均价靠 JOIN 一级余额表继承。二级的"另一个价"是 `internal_price`（内部结算价），**不参与任何会计口径的数**，本方案不碰 |

## 四、`G-06` 关闭（**本方案唯一越出"设计"的部分，请复核**）

`G-06` 原文（`出入库场景与数据交接对照` `:730` / `:1035`）：**分摊账的展开规则与符号未定义**。它卡住的正是二级结存的**数量符号**。原文档把三件事留给了 W1，我在此给出**明确建议**。

### 4.1 建议的三条

| # | 问题 | **建议** | 理由 |
|---|---|---|---|
| **①** | 展开为几行 | **两行**（转出方一行 + 转入方一行，共用同一个 `doc_no` / `line_no`） | 表结构是「一行一个 `owner_l2` + 数量」，这是唯一能让「按 `owner_l2` 汇总」取到正确结果的写法。只写一行则**转出方结存永不减**，`V1` 当场破 |
| **②** | `qty` 的符号 | **带符号**：转出方**负**（−200）、转入方**正**（+200） | 这样 `SELECT owner_l2, SUM(qty) ... GROUP BY owner_l2` **直接就是该二级货主的结存数量**——不需要任何"看方向再决定加还是减"的附加规则，公式就是一行 SQL。且成对两行 `Σ qty = 0` → 一级数量不变 → **`V1` 由构造成立** |
| **③** | `internal_pl` 按行读还是净额读 | **按行存、只记"增值的一行"**：**转入行**记 `internal_pl_l2 = internal_amount_l2 − alloc_amount = qty × (internal_price − 一级均价)`；**转出行记 `0`** | 唯一能取回框架案例 7.2 期望值的读法，见 `§4.2` |

### 4.2 用 `G-06` 自己的例子验算

`G-06` 给的例子：数量 200、`alloc_amount` 200（一级均价 1.0）、`internal_amount_l2` 220（内部结算价 1.1）。**框架案例 7.2 期望「二级内部损益 +20.00」。**

**按建议的三条写出来**：

| 行 | `owner_l2` | `qty` | `alloc_amount` | `internal_amount_l2` | `internal_pl_l2` |
|---|---|---|---|---|---|
| 转出行 | A | **−200** | −200 | −220 | **0**（转出即不再持有，不确认内部损益） |
| 转入行 | B | **+200** | +200 | +220 | **+20** |
| **Σ** | | **0** ✅ | **0** ✅ | **0** ✅ | **+20** ✅ |

- `Σ qty = 0` → 一级层数量不变 → **`V1` 成立**
- `Σ alloc_amount = 0` → 会计口径零和 → **`V3` 成立**
- `Σ internal_amount_l2 = 0` → **新增一条有用的不变量**：内部结算账**自身也必须零和**（否则"不出凭证、不动一级"就说不通）
- `Σ internal_pl_l2 = +20.00` → **与框架案例 7.2 逐字对上** ✅

**`G-06` 原文说"取不出来"，症结在哪**：原文设的是**两行都写** `internal_pl`（转出行 −20、转入行 +20），净额自然是 0。本建议把**转出行置 0**——因为**内部未实现毛利是"持有方"的属性**：货在谁手上，这部分加价就压在谁的账上，未实现（货还在集团内）；转出方转出后不再持有，其内部账按**同一 `internal_price`** 冲减，差额为 0。待货最终**对外售出**，这 20 随存货一同结转，实现为毛利。

**被否决的两种读法**：

| 备选 | 结果 | 否决理由 |
|---|---|---|
| 两行都写 `internal_pl`（±20） | `Σ internal_pl = 0` | **取不出 7.2 期望的 +20**，就是 `G-06` 记录的现象本身 |
| 只写一行（净额一行） | 转出方 `qty` 永不减 | **`V1` 当场破**，且与物化表的按 `owner_l2` 汇总直接冲突 |

### 4.3 `G-06` 关闭后，`§一.5.2` 那条警告怎么处理

`需求文档` `:202` 的 `⚠️ 二级维度取数依赖一项未决口径` 整段，在 `G-06` 闭合 + 物化表落地后，**整段替换**为：

> **二级维度的结存数量**由 `t_owner_balance_l2`（二级货主结存表）按二级货主直接读出（该表由记账层每次事件按 `apply_alloc_deltas` 增量维护，符号约定见 `§4.x`）；**结存金额**按 `数量 × 该核算单元当期一级结存均价` 派生，**不落库**。

## 六、三个维度的聚合算法该写在文档哪里

**现状问题**（`§1.2` 缺口三）：三个维度的聚合**只写在展示章 `§一.5.2`**，而 `§二.3 计算逻辑` 里只有核算单元级的 F1–F5。实现方按计算章干活会漏掉整个维度层。

**建议**：把聚合算法**从展示章提升到计算章**，`§一.5.2` 保留"三个 tab 怎么展示、列怎么合并、均价怎么压成 `--`"这类**展示规则**，算法本体写进 `§二.3`，**逐维写死**：

```
# ① 仓库维度：跨货主合并（同一查询范围内，所有货主合并成一行）
SELECT sku_code, warehouse_code, asset_type,
       SUM(qty)                                        AS current_qty,
       SUM(amount)                                     AS current_total_cost,
       CASE WHEN SUM(qty) = 0 THEN NULL
            ELSE SUM(amount) / SUM(qty) END            AS current_unit_cost,   -- 加权，非算术平均
       <方法聚合：全同→该方法 / 混合→'混合' / 含 SI→'--'>  AS pricing_method,
       MAX(updated_at)                                 AS updated_at
FROM   t_inventory_balance_unit
GROUP  BY sku_code, warehouse_code, asset_type;

# ② 一级货主维度：不合并，一个核算单元一行
SELECT legal_owner_id, warehouse_code, sku_code, asset_type,
       qty, amount, unit_price, pricing_method, has_negative, updated_at
FROM   t_inventory_balance_unit;          -- 直接取，无聚合

# ③ 二级产权人维度：不合并，读物化表 + 继承一级均价（不动一级任何表）
SELECT b.owner_l2, b.owner_l1, b.warehouse_code, b.material_code, b.asset_type,
       b.qty                                    AS current_qty,
       b.qty * u.unit_price                     AS current_total_cost,
       u.unit_price                             AS current_unit_cost,
       u.pricing_method, (b.qty < 0) AS has_negative, b.updated_at
FROM   t_owner_balance_l2 b
JOIN   t_inventory_balance_unit u
  USING (material_code, warehouse_code, owner_l1, asset_type);
```

> **口径标注是展示层要求，不是取数要求**：`需求文档` `§一.5.3` 要求库存金额标 `（存货口径·一级货主层·is_internal = 1）`、数量标 `（权属口径）` 或 `（物理口径·仓库）`。**三个维度的取数范围一致**（都含 `is_internal = 0`），否则 `V2` / `V3` 立刻不平——标注是**给读数的人看的**，不是筛选条件。

> **一处已补齐（2026-09-30，经用户确认后执行）**：`需求文档` `§一.5.2` 的二级聚合键原为 `(amiba_owner_id, legal_owner_id, warehouse_code, sku_code)`，**漏了 `asset_type`**，而仓库维度与一级货主维度**都有**——这是 §一.5.2 **内部自相矛盾**：同一节的三 tab 字段表（`:837`）**本来就在显示 `资产类型` 这一列**，聚合键表却没把它列为分组键。
>
> **判为漏写而非有意省略的证据**：① 三个 tab 的字段表**都**列了 `asset_type`（`:764` / `:800` / `:837`）；② **旁证（弱）**：`财务库存方案.md` `:954` 的 `uk_account_dim`（`二级货主必填化变更影响清单_v1.0.md` `:98`）**也含 `asset_type`**——但那是**口径 B 的键**（见上文 ⚠️），**不作口径 A 的先例**，只说明「把 `asset_type` 纳入二级账键」这个做法在同族设计里出现过；③ 不留 `asset_type` 会把自有资产与受托代管混进同一行，而另两个 tab 是分开的。
