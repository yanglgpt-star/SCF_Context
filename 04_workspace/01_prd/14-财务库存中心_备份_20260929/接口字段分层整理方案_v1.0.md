# 接口字段分层整理方案 v1.0

> **用途**：回答「接口字段抽出统一字段、每个单据类型增加对应字段，应该怎么整理」。
> **性质**：整理方案，供拍板；拍板后再落改文档与 DDL。
> **日期**：2026-09-29
> **依据**：`通用数据接口字段定义_v1.0.md` · `出入库场景与数据交接对照_v1.0.md` · `详细设计文档.md` · `业务与财务库存中心数据交接清单与一致性约定_v1.2.md` · `产品架构图_v1.0.md`

---

## 0. 两个结论先说

**① 方向对，但眼下不是「整理问题」，是「缺落点」。**

11 类单据里 **9 类的差异化字段在物理层零命中**——`out_warehouse_code` / `in_warehouse_code`（调拨）、`actual_qty`（盘点）、`orig_po_doc` / `orig_so_doc`（退货）、`adjust_reason`（补录）、`reason`（其他出入库）在《详细设计文档》里**出现 0 次**（详见 §1.2）。所以这次「整理」必须**同时给它们建落点**，只重排文档不解决任何问题。

**② 不是「两层」，是「五层」，且单据类型之下还有一层。**

实际结构是 **统一层（信封 / 头 / 行）+ 单据类型扩展层 + 子场景扩展层**。其他入库拆 5 类（`IN-1`–`IN-5`）、其他出库拆 6 类（`OUT-1`–`OUT-6`），**它们都不是独立 `doc_type`，靠 `reason` 区分**。只按 `doc_type` 分组会**整批漏掉 `G-08` 那 11 个字段**——这是本次整理最容易踩的坑。

## 1. 现状：同一个字段能出现在四个地方

### 1.1 四处散落，定义质量三档

| # | 位置 | 装什么 | 定义质量 |
|---|---|---|---|
| 1 | 字段定义 `§4.1` + `§4.2` | 统一字段（头 8 + 行 17） | ★★★ 有类型 / 必填 / 说明 |
| 2 | 字段定义 `§4.3` | 11 类差异化字段 | ★ **只有字段名，塞在一个单元格里**——无类型、无必填、无语义 |
| 3 | 字段定义 `§4.5` + `§4.6` | 作价字段 / 二级两个金额 | ★★★ 但**独立成表，不在 `§4.3` 的归口里**，读者要跳两节才找全 |
| 4 | 对照稿 `§2.0` / `S-05` / `S-12` | 子场景字段（`IN-x` / `OUT-x`） | ★★ 只在这份文档里，字段定义与契约**都没有** |
| 5 | 产品架构图 `A-03` 表 | `G-10` / `G-12` 建议字段 | ★ 只在那里，属**待定** |

**同一个字段集有两份副本**：字段定义 `§4.1`/`§4.2` 与对照稿 `§2.0`。它们**已经在漂**——对照稿说「`§4.2` 单据行（14 项）」，而字段定义 `§4.2` 现为 **17 行**（本轮加了 `owner_l2` 必填等）。两份副本必须收敛成一份。

### 1.2 ⚠️ 物理层没有落点（最要紧的一条）

| 单据类型 | 差异化字段 | 在《详细设计文档》的命中 |
|---|---|---|
| `TRANSFER` 调拨 | `out_warehouse_code` / `in_warehouse_code` | **0** |
| `STOCKTAKE` 盘点 | `actual_qty`（`book_qty` 命中 1 次，在正文不在表内） | **0** |
| `PO_RET` 采购退货 | `orig_po_doc` | **0** |
| `SO_RET` 销售退货 | `orig_so_doc` | **0** |
| `OTHER_IN` / `OTHER_OUT` | `reason` | **表内 0**（2 处命中均为 `last_reopen_reason`，无关） |
| `PERIOD_ADJUST` 期间补录 | `adjust_reason` | **0** |
| `OWNER_TRANSFER` / `OWNER_REASSIGN` | `from_owner_l1` / `to_owner_l1` / `transfer_price` / `price_source` / `is_accounting_event` / `is_related_party` / `settle_doc_no` | ✅ **有**——独立表 `t_owner_transfer`（`§4.2.3`） |

**唯一的正面例子是货权变更**：它有一张自己的扩展表 `t_owner_transfer`，键为 `(doc_no, line_no)`——**这恰好证明「类型扩展表」这个模式是对的**，但它只覆盖了 2 类。其余 9 类**目前无处落**。

> 换句话说：**`t_owner_transfer` 是意外做对的一个，不是设计出来的一个。**

### 1.3 `reason` 是自由文本，子场景这一层根本不成立

对照稿给出了 `RETURN_BORROW` / `GIFT_RECEIVED` / `CONSIGNMENT_IN` / `SCRAP_DAMAGE` / `LEND_OUT` / `SHIP_FOR_OWNER` 等取值，但**这些取值表在字段定义里不存在**——`reason` 在 `§4.3` 里只是一个光秃秃的字段名，**无类型、无必填标记、无枚举取值表**。

后果：**`valuation_source` 该不该必填、该取哪个值，系统无法判定。** 同一句 `reason = "无对价杂项"` 里写的是"找回货"还是"无原单退回"，直接决定金额走 `ORIG_DOC` 回冲还是 `FINANCE_ESTIMATE` 财务估价——**靠自由文本判不出来**。

→ **子场景字段要能挂上去，`reason` 必须先升为受控枚举。这是整件事的拱心石。**

## 2. 分层模型：五层 + 归层三问

| 层 | 装什么 | 字段数 | 载体 |
|---|---|---|---|
| **L0 信封** | 传输批号 / 来源系统 / 字段定义版本 / 业务对象 / 推送时间 / 记录条数 / 记录数组 | 7 | 字段定义 `§2.1` |
| **L1 头级统一** | 单据号 / 单据类型 / 业务日期 / 状态 / 法人 / 往来单位 / 审核留痕 / 备注 | 8 | 字段定义 `§4.1` |
| **L2 行级统一** | 行号 / 物料 / 仓库 / 方向 / 一级货主 / 二级货主 / 批次 / 数量族 / 金额族 / 分摊 / 暂估族 / 关联方 | 17 | 字段定义 `§4.2` |
| **L3 单据类型扩展** | 只有该 `doc_type` 才有的字段 | 见 `§4.1` | **本次新建** |
| **L4 子场景扩展** | 同一 `doc_type` 内按 `reason` 再分的字段 | 见 `§4.2` | **本次新建** |

**归层三问**（判据，可复用）：

1. **11 类每一类都必填、且含义完全相同？** 是 → `L1` / `L2`；只有部分类型有 → `L3`。
2. **同一个 `doc_type` 内不同子场景取值不同？** 是 → `L4`（且该 `doc_type` 的 `reason` 必须是受控枚举）。
3. **参与 SQL 校验 / 对账 / 报表吗？** 参与 → 物理层**加列**；不参与（纯核算内部属性）→ 可留专表。

## 3. 三个轴必须分开（最容易混的一处）

你说的是「每个单据类型增加对应的字段」——这句话同时压着三个**互相独立**的决定，必须拆开谈，否则会用一个轴的选择去回答另一个轴的问题。

| 轴 | 问题 | 推荐 |
|---|---|---|
| **轴一 · 文档与规则怎么组织** | 字段清单、必填矩阵、校验规则按什么分组 | **按 `doc_type` 分组，组内再分「行级扩展 / 子场景扩展」两段** ← 直接回答你的问题 |
| **轴二 · 报文怎么承载** | JSON 里是扁平 key，还是嵌套子对象 | **扁平 key + 语义分组**（分组是文档与规则的事，不进报文结构） |
| **轴三 · 物理层怎么落** | 加列 / 扩展表 / JSON 列 | **加列 + `reason` 受控枚举 + 一张类型规则表** |

### 3.1 轴二：三种承载方式的取舍

| | ① 扁平 · 全字段可选 | ② `ext` 通用包（JSON） | ③ 具名嵌套块 |
|---|---|---|---|
| 形态 | 所有字段平铺在 `records[]`，按类型定必填 | 统一字段 + `ext{}` 键值包 | 统一字段 + `transfer:{}` / `stocktake:{}` 具名块 |
| 加字段的代价 | 加一列（文档 + DDL） | 零 DDL | 改该类型 schema |
| **必填能否校验** | ✅ 规则表驱动 | ❌ 包内无法声明必填 | ✅ 每类独立 schema |
| **枚举能否约束** | ✅ | ❌ | ✅ |
| **能否建索引 / SQL 校验** | ✅ | ❌ | ✅（落库后） |
| 对账 / 报表 | ✅ 直接 SQL | ❌ 要解 JSON | ✅ |
| 文件绑定是否仍等价 | ✅ | ⚠️ 列为空 vs 键缺失语义要额外约定 | ⚠️ 展平规则要额外约定 |

**推荐 ①（扁平）**，理由三条：

1. 本系统的要害是 **校验前移 + 三层幂等 + 对账**（`§2.5` A/B/C 三档、`§2.6`）。JSON 包**绕不过这三样就会削弱这三样**——包内字段既不能声明必填，也不能建索引。
2. `ext` 包会让字段**绕过 `§2.2` 的类型与精度规范**（数量 4 位 / 金额 2 位 / 单价 6 位），而这套精度是 `F1`/`F2`/`F3` 与对账的共同基础。
3. `§9.3` 已写死「**文件绑定 = 同一字段集的另一种绑定**」。嵌套会让 Excel 侧必须约定一套"展平规则"，**这条等价性就被破坏了**——而这条等价性是「保留导入入口不产生两套逻辑」的全部理由。

> 代价要认：扁平后 `t_document_line` 会从约 30 列涨到约 60 列，大部分行大部分列为 `NULL`。这是**可接受的**——MySQL 的 `NULL` 存储开销极小，而换来的是「一次 join 就能出报表、一条 SQL 就能校验」。

### 3.2 轴三：物理层落点三选一

| | A 加列到 `t_document_line`（**推荐**） | B 具名扩展表（沿 `t_owner_transfer` 先例） | C `ext` JSON 列 |
|---|---|---|---|
| 做法 | 类型扩展字段全部成为 `t_document_line` 的列，按类型定必填 | 为 11 类各建一张 `t_document_line_<type>` | 一列 `JSON` 装全部扩展 |
| 优势 | 一次 join 出全部；SQL 可校验；与 `§4.2` 统一字段同表 | 窄表、类型隔离干净 | 零 DDL |
| 代价 | 宽表（~60 列，多 NULL） | **9 张新表 + 每次查询多 11 路选 join**，报表与对账全要改 | 不能建索引、不能 SQL 校验、报表要解 JSON |
| 结论 | ✅ 采用 | ❌ 仅适合字段极少且与其他类型完全无关者 | ❌ 同 `§3.1` 理由 |

**推荐 A**，并按 `§2` 的归层三问第 3 条处理既有先例：把 `t_owner_transfer` 的**行级字段并回** `t_document_line`（`from_owner_l1` / `to_owner_l1` / `transfer_price` / `price_source` / `is_related_party` / `settle_doc_no`），**`t_owner_transfer` 只保留核算侧属性**（`is_accounting_event` 等）与二级分摊展开逻辑。

> 判据：**参与 SQL 校验 / 对账 / 报表的字段 → 进 `t_document_line`；纯核算内部属性 → 可留专表。** 前者是"这笔业务是什么"，后者是"这笔业务怎么记"。

## 4. 归位表（核心交付）

### 4.1 `L3` 单据类型扩展字段（11 类逐类）

| `doc_type` | 中文名 | 扩展字段（`L3`） | 归口说明 |
|---|---|---|---|
| `PO_IN` | 采购入库 | `supplier_code` · `settle_status` · `estimate_ref_doc` | `settle_status`/`estimate_ref_doc` 是暂估冲回入口；`L2` 已列，本行标出它是 `PO_IN` 的实际使用者 |
| `PO_RET` | 采购退货 | **`orig_po_doc`** | 必须可追溯原单；无原单则拒绝 |
| `SO_OUT` | 销售出库 | `customer_code` | **出库成本由系统算，不采信传入成本** |
| `SO_RET` | 销售退货 | **`orig_so_doc`** | 按原出库成本回冲，**不重算** |
| `TRANSFER` | 调拨 | **`out_warehouse_code`** · **`in_warehouse_code`** | 调出调入必须同一 `owner_l1`，否则回执 `E-CROSS-LEGAL-ENTITY` |
| `STOCKTAKE` | 盘点 | **`book_qty`** · **`actual_qty`** | 差异**自动生盘盈/盘亏单**，不直接改余额 |
| `OTHER_IN` | 其他入库 | `reason`（受控枚举，见 `§4.2`） | **本类型的扩展字段全部在 `L4`** |
| `OTHER_OUT` | 其他出库 | `reason`（受控枚举，见 `§4.2`） | **本类型的扩展字段全部在 `L4`** |
| `OWNER_TRANSFER` | 一级货权转移 | **`from_owner_l1`** · **`to_owner_l1`** · **`transfer_price`** · **`price_source`** · `is_related_party` | 作价必填，是**交易数据**不是配置 |
| `OWNER_REASSIGN` | 二级重分配 | **`from_owner_l2`** · **`to_owner_l2`** · **`internal_price`** · **`price_type`** · `price_source` · `price_base` · `markup_rate` · `price_value` | 作价必填，是**政策数据**（取 `t_internal_price` 价目表） |
| `PERIOD_ADJUST` | 期间补录 | **`adjust_reason`** · `orig_doc_type` | **必审**；一律按当期口径量价 |

> **`§4.5` 作价字段与 `§4.6` 二级两金额在此归口**：作价字段挂 `OWNER_TRANSFER` 与 `OWNER_REASSIGN` 两行（见上）；`alloc_amount` / `internal_amount` / `internal_pl` 挂 `OWNER_REASSIGN` 的回传结构（`§4.6`），**它们是二级层回传字段，不是单据输入字段**，建议在字段定义里**从 `§4` 移到 `§6`/新增 `§7`**，避免与输入字段混在一节。

### 4.2 `L4` 子场景扩展字段（其他入库 5 类）

`reason` 受控枚举：`RETURN_BORROW` / `RETURN_SAMPLE` / `GIFT_RECEIVED` / `CONSIGNMENT_IN` / `BORROW_IN` / `RECOVERED_STOCK` / `UNMATCHED_RETURN`。
**★ = `G-08` 建议新增、现契约没有。**

| 子场景 | `reason` 取值 | 扩展字段（`L4`） | 说明与举例 |
|---|---|---|---|
| **`IN-1`** 原物归还 | `RETURN_BORROW` / `RETURN_SAMPLE` | ★ `orig_doc_no` · `orig_qty` · ★ `valuation_source` | `valuation_source` 恒为 `ORIG_DOC`（原单回冲）；`orig_doc_no` 例 `OT-202601-0005` |
| **`IN-2`** 受赠入库 | `GIFT_RECEIVED` | `counterparty_code` · ★ `valuation_source` · ★ `valuation_basis` | `EXTERNAL`；依据例「供应商开票价 1,000.00」 |
| **`IN-3`** 受托代销·寄售 | `CONSIGNMENT_IN` | `owner_l1`（须为外部法人）· ★ `valuation_source` · ★ `valuation_basis` | `EXTERNAL`；依据例「对账单 2026-01#3，单价 10.00」 |
| **`IN-4`** 借入他方货物 | `BORROW_IN` | `owner_l1`（须为外部法人）· ★ `valuation_source` · ★ `valuation_basis` | `EXTERNAL` |
| **`IN-5`** 无对价杂项 | `RECOVERED_STOCK` / `UNMATCHED_RETURN` | ★ `valuation_source` · ★ `valuation_basis` | **五类里唯一用 `FINANCE_ESTIMATE`**；依据须含**估价人** |

### 4.3 `L4` 子场景扩展字段（其他出库 6 类）

`reason` 受控枚举：`INTERNAL_USE` / `SCRAP_DAMAGE` / `SCRAP_EXPIRED` / `GIFT_OUT` / `SAMPLE_OUT` / `LEND_OUT` / `CONSIGNMENT_OUT` / `SHIP_FOR_OWNER`。

| 子场景 | `reason` 取值 | 扩展字段（`L4`） | 说明与举例 |
|---|---|---|---|
| **`OUT-1`** 内部领用·自用 | `INTERNAL_USE` | `dept_code` | 决定费用科目，例 `D-ADMIN` → 管理费用 |
| **`OUT-2`** 报废·毁损 | `SCRAP_DAMAGE` / `SCRAP_EXPIRED` | ★ `residual_amount` · ★ `residual_source` | 残值抵减损失，例残料入库 `50.00` / 保险赔付 `300.00` |
| **`OUT-3`** 赠出·送样 | `GIFT_OUT` / `SAMPLE_OUT` | `counterparty_code` | 受赠方 / 送样对象 |
| **`OUT-4`** 借出（可归还） | `LEND_OUT` | ★ `is_recoverable` · `counterparty_code` · ★ `due_date` | `is_recoverable = 1` **是 `OUT-4` 与 `OUT-3` 唯一的分界线**；`due_date` 用于超期清单 |
| **`OUT-5`** 委托代销发出 | `CONSIGNMENT_OUT` | `counterparty_code` · ★ `account_subject` | 本类恒为 `发出商品`；**一级货主仍是我方，不变** |
| **`OUT-6`** 货权已转·实物才出 | `SHIP_FOR_OWNER` | `owner_l1`（外部法人）· ★ `orig_owner_transfer_doc` · `amount_ex_tax` | **`amount_ex_tax` 显式填 `0.00`**，不是留空——留空 = 待财务结转，填 0 = 本单不结转 |

> **三个分界点**：`is_recoverable`（`OUT-4` vs `OUT-3`）· `account_subject`（`OUT-5` vs `OUT-1`–`OUT-3`）· `amount_ex_tax = 0`（`OUT-6` vs 其余五类）。**三个字段现在都不存在，业务只能靠 `reason` 里写自由文本**——这正是 `G-08` 要求补的全部原因。

### 4.4 三个「跨界」字段要单独说清

这三个字段**不能简单标 Y/N**，它们的必填性由另外的东西决定：

| 字段 | 现所在层 | 问题 | 处理建议 |
|---|---|---|---|
| `counterparty_code` | `L1` 头级 | 8 个类型都要，但**含义随类型变**（供应商 / 客户 / 委托方 / 借出对象 / 受赠方 / 受托方） | 保持 `L1`，但在 `§4.3` 规则表里加**「按 `doc_type` 的取值域」**列，不新增交易对手类字段 |
| `amount_ex_tax` | `L2` 行级 | `L2` 标 `Y`，但**出库类不给金额**（`OUT-1`–`OUT-5` 留空），`OUT-6` 要显式 `0` | 必填性改为**「按 `doc_type` × 出入方向」的条件必填**，规则表里写清三态：`必填` / `可不填（由财务结转）` / `必填且恒为 0` |
| `batch_no` | `L2` 行级（可空） | 可空没错，但 **SI/FIFO 单元 + `is_batch_managed` 物料**下它不是可选的 | 保持可空，必填性由**物料主数据 + 单元计价方法**驱动——这是**主数据驱动的条件必填**，**不是单据类型驱动**，不要写进 `L3` 规则表 |

> **这条判据值得单独记**：必填性的来源有三种——**类型驱动**（进 `L3`）、**子场景驱动**（进 `L4`）、**主数据驱动**（不进 `L3`/`L4`，由适配层查主数据判定）。把主数据驱动的塞进类型表，会在换物料时静默失效。

### 4.5 仍未归位的两个（`G-10` / `G-12`）

| 字段 | 建议层 | 理由 |
|---|---|---|
| `has_physical_movement`（有无实物移动） | **`L1` 头级**（或 `L2` 行级） | 它是**事实声明**，不属任何单据类型——`XY-1`/`XY-2`/`XY-3` 三类都可能"货没动"。**财务侧不采信其真伪、只采信其声明并留痕**（"不声明比声明错更危险"） |
| `link_doc_no`（直发配对键） | **`L2` 行级** | 直发是"入库 + 出库"两笔，配对键要在行级才能关联；没有它，"入库 = 出库"这条校验做不了，**数量对账会漏掉一笔** |

## 5. 落地形态：一张机器可读的规则表

整理后的产物**不只是给人看的文档**，应是**适配层直接可读的一张规则表**（代码内置或配置表），形态：

```
doc_type: PO_IN
  方向: 入
  L3 必填:   [supplier_code]
  L3 可选:   [settle_status, estimate_ref_doc]
  L2 条件必填:
    amount_ex_tax: 必填
    batch_no:      依主数据（is_batch_managed = 1 时必填）
  reason 枚举: 无（本类型不分子场景）

doc_type: OTHER_OUT
  方向: 出
  reason 枚举: [INTERNAL_USE, SCRAP_DAMAGE, SCRAP_EXPIRED, GIFT_OUT,
                SAMPLE_OUT, LEND_OUT, CONSIGNMENT_OUT, SHIP_FOR_OWNER]
  L2 条件必填:
    amount_ex_tax: 依子场景（OUT-6 = 必填且恒为 0；OUT-1~OUT-5 = 可不填）
  L4 按 reason:
    INTERNAL_USE:  { 必填: [dept_code] }
    SCRAP_DAMAGE:  { 必填: [reason], 可选: [residual_amount, residual_source], 条件: 填 residual_amount 则 residual_source 必填 }
    LEND_OUT:      { 必填: [is_recoverable, counterparty_code, due_date] }
    CONSIGNMENT_OUT: { 必填: [counterparty_code, account_subject] }
    SHIP_FOR_OWNER:  { 必填: [owner_l1, orig_owner_transfer_doc, amount_ex_tax] }
```

**三个必须落进规则表的约定**：

1. **`reason` 是枚举，未见值即拒绝**（`E-ENUM-INVALID` 枚举取值非法）——否则 `L4` 挂不上去。
2. **`residual_source` 是条件必填**（填了 `residual_amount` 才必填）——规则表要支持**字段间依赖**，不能只有"必填字段列表"。
3. **`amount_ex_tax` 的三态**（必填 / 可不填 / 必填恒为 0）必须显式表达；用 `N` 表示"可不填"会在 `OUT-6` 上放行一个错账。
