# 简易版需求文档规范（PRD-E）

本规范适用于**日常迭代、小功能改动、单模块需求**等轻量级场景，追求快速清晰，避免过度设计。与完整版 PRD（prd-q）相比，本模板结构更扁平，章节更少，适合单页呈现。

---

## 一、文档结构总览

```
1. 需求标题
   1.1 背景 & 问题        【强制】
   1.2 目标收益           【强制】
   1.3 方案描述
       【用例简述】        【强制】
       【菜单路径】        【强制】
       【功能要点】        【强制】
       功能描述            【强制】
       接口定义            【选择】
       【权限要求】        【选择】
       【上线初始化】      【选择】
       【数据支持】        【选择】
       【测试重点】        【选择】
```

---

## 二、各章节说明

### 1.1 背景 & 问题【强制】

- **从业务角度**描述当前现状及存在的痛点，明确说明"为什么做"。
- 避免技术视角，聚焦用户/业务受影响的场景。

### 1.2 目标收益【强制】

- 简述本次需求完成后，业务/用户/系统层面的预期改善。
- 可量化则量化（如：减少操作步骤 X 步、提升效率 X%）。

### 1.3 方案描述

#### 【用例简述】【强制】

- 如果是**新功能页面**：简述功能要点（概述功能的主要能力）。
- 如果是**对现有功能的调整**：说明改动点，避免重复描述未变内容。

示例：
> 在收货单列表新增"批量关闭"按钮，支持勾选多条未完成收货单后批量执行关闭操作。

#### 【菜单路径】【强制】

- 标记该用例在系统中的完整导航路径。

示例：
> 仓储管理 → 收货管理 → 收货单列表

#### 【功能要点】【强制】

- 视情况书写：**流程图、原型、需求描述、业务规则、接口定义**等。

**流程图【推荐】**
- 简单改动可省略；流程层次多、分支复杂、难以用文字说清时必须补充。
- 可用 UML 建模图、数据流转图或状态流转图。

**界面原型【推荐】**
- 原型上标注改动点，跳转界面用细线引导并在原型旁加注释。
- 涉及查询条件和列表时，按以下样式说明查询条件：

| 序号 | 界面元素 | 是否必须 | 模糊查询 | 备注 | 取值说明 |
|------|---------|---------|---------|------|---------|
| 1 | （示例）波次模板 | 是 | 否 | 下拉选择框 | 来源接口或实体；数据排序说明；是否有默认值 |
| 2 | （示例）客户编码 | 否 | 否 | 批量查询 | |
| 3 | （示例）路线 | 否 | 否 | 下拉多选 | |

#### 功能描述【强制】

需求描述和业务规则是核心内容，书写时需遵循以下原则：

1. **可读性**：主谓宾结构，人事物规则说清楚，具体化，避免抽象概念；重点信息用颜色、下划线、「」符号、编号等标记突出。
2. **逻辑性**：阐述系统如何做，前后端如何交互，数据结构及处理方式，与其他模块的信息流转。
3. **完整性**：输入对应输出，上下游如何交互反馈，是否涉及财务等外域数据处理，异常场景处理方式，表单导入导出格式。
4. **友好性**：考虑用户体验，描述报错信息、操作防错、防呆处理。
5. **拓展性**：遵循 MVP 原则，分清主次，分步分期实现，标注当前范围和后续计划。

#### 接口定义【选择】

涉及主要接口时列举说明，每个接口包含：

- **接口名称 & 描述**（功能用途、调用方、被调用方）
- **请求参数**：字段名称、描述、示例、校验规则（必填/非必填）
- **返回参数**：字段名称、描述、示例、备注
- **响应要求**（超时、错误码等）

#### 【权限要求】【选择】

- 说明对权限控制的要求，如按钮管控、数据层面管控。
- 示例：新菜单应分配给哪些角色；某操作仅管理员可见。

#### 【上线初始化】【选择】

- 有新增字段或历史取值逻辑变更时，需说明历史数据处理方案。
- 检查清单：
  1. 是否需要初始化数据？如需要则说明方案。
  2. 历史数据是否需要特殊处理？如需要则说明。
  3. 涉及报表取值逻辑变更，需通知数据团队。

#### 【数据支持】【选择】

- 需要大数据团队支持的单独说明。
- 说明报表格式、内容、字段口径等。

#### 【测试重点】【选择】

- 列出需要测试重点关注的场景或逻辑。
- 示例：更新后库存是否准确、金额计算是否正确、并发操作是否安全等。

## 三、写作质量检查清单

在交付文档前，逐项确认：

- [ ] 背景问题说清楚"为什么做"（业务视角，非技术视角）
- [ ] 目标收益可感知、尽量可量化
- [ ] 用例简述一句话能概括改动点
- [ ] 菜单路径完整准确
- [ ] 功能描述遵循"可读、逻辑、完整、友好、拓展"五原则
- [ ] 异常/边界场景已覆盖
- [ ] 选填项按实际需要取舍，不填充无意义内容

## 四、与完整版 PRD（prd-q）的区别

| 维度 | 简易版（prd-e） | 完整版（prd-q） |
|------|--------------|--------------|
| 适用场景 | 日常迭代、小改动、单模块 | 新系统、复杂业务、跨团队协作 |
| 文档长度 | 单页为主 | 多页，章节完整 |
| 业务蓝图 | 不要求 | 必选 |
| UML时序图 | 推荐（复杂时） | 必选 |
| 用例规约 | 简化（功能描述替代） | 完整字段（15+项） |
| 版本管理 | 轻量（文档标题注明版本即可） | 版本表格管理 |
| 非功能性需求 | 合并到功能描述或上线初始化 | 独立章节 |

> 当需求复杂度上升、跨团队协作增多、或文档需正式审批时，应切换至 prd-q 完整版规范。
